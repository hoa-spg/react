Lektion 2.6 — Teil 2: React Praxis

Testen mit Vitest + React Testing Library

React ca. 90 min

Lernziele

  • Testpyramide für React-Projekte einordnen
  • Vitest im Vite-Projekt konfigurieren
  • Mit React Testing Library benutzerzentriert testen
  • Interaktionen mit @testing-library/user-event abdecken
  • @testing-library/jest-dom Matchers sinnvoll einsetzen
  • Integrationstests mit API-Mocks (MSW) kurz einordnen

1. Warum testen?

Tests sind für React-Projekte kein Selbstzweck. Sie reduzieren Regressionen, geben beim Refactoring Sicherheit und dokumentieren implizit, wie Komponenten genutzt werden sollen.

In diesem Kapitel setzen wir den Fokus klar auf Komponententests. Sie laufen schnell, sind lokal stabil und liefern den größten Lerneffekt für den UI-Alltag.

ℹ
Genau ein Test-Kapitel in Teil 2

Teil 2 hat absichtlich nur dieses eine Test-Kapitel. Spätere Kapitel bleiben auf Feature-Umsetzung fokussiert; die Test-Grundlage nehmen wir aber weiter mit.

2. Setup mit Vitest, RTL und jest-dom

Wir nutzen das Beispiel unter beispiele/2.6. Das Setup ist bewusst leichtgewichtig und bleibt nahe an Vite.

Terminal Bash 
npm install -D vitest jsdom @testing-library/react @testing-library/user-event @testing-library/jest-dom

# einmalig ausführen
npm run test

# beim Entwickeln
npm run test:watch
vite.config.ts TypeScript 
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';

export default defineConfig({
  plugins: [react()],
  test: {
    environment: 'jsdom',
    globals: true,
    setupFiles: './src/test/setup.ts',
  },
});
💡
jsdom statt Browser

Vitest nutzt für Komponententests eine DOM-Simulation. Das reicht für Rendering, Klicks, Eingaben und die meisten Formular-Workflows.

3. Erster Komponententest

React Testing Library testet aus Sicht von Nutzerinnen und Nutzern. Deshalb fragen wir Elemente bevorzugt über Rollen, Labels und sichtbaren Text ab – nicht über CSS-Selektoren oder Implementierungsdetails.

src/components/flight-form.test.tsx TypeScript 
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import FlightForm from './FlightForm';

test('sendet Callback mit Formdaten', async () => {
  const user = userEvent.setup();
  const onCreate = vi.fn();

  render(<FlightForm onCreate={onCreate} />);

  await user.type(screen.getByLabelText(/flugnummer/i), 'LH123');
  await user.type(screen.getByLabelText(/airline/i), 'Lufthansa');
  await user.click(screen.getByRole('button', { name: /flug anlegen/i }));

  expect(onCreate).toHaveBeenCalledWith({
    flightNumber: 'LH123',
    airline: 'Lufthansa',
  });
});

4. Kurzer Integrationsteil: Komponente + State + Mock

Nur kurz zur Einordnung: Ein Integrationstest verbindet mehrere Bausteine, etwa Formular + Liste + Filter-Logik oder UI + API-Aufruf.

Im Kapitel bleibt das bewusst klein: eine Seite mit Eingabe und gefilterter Liste. Für API-Tests kannst du zusätzlich MSW einsetzen, um Endpunkte realistisch zu mocken.

src/integration/flight-board.integration.test.tsx TypeScript 
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import FlightBoardPage from '../pages/FlightBoardPage';

test('filtert die Liste nach Eingabe', async () => {
  const user = userEvent.setup();
  render(<FlightBoardPage />);

  await user.type(screen.getByRole('searchbox', { name: /suche/i }), 'LH');

  expect(screen.getByText('LH123')).toBeInTheDocument();
  expect(screen.queryByText('OS404')).not.toBeInTheDocument();
});
ℹ
MSW nur als Ausblick

Vollständige API-Integrationsstrategien mit MSW vertiefen wir hier bewusst nicht weiter. Ziel ist, die Grundlagen in einem Kapitel sauber zu etablieren.

Projektschritt

Projektschritt 2.6

Test-Basis für FlugBoard einziehen

  1. Testabhängigkeiten installieren und Scripts in package.json ergänzen.
  2. src/test/setup.ts mit @testing-library/jest-dom erstellen.
  3. Einen Komponententest für ein Formular oder ein Badge schreiben.
  4. Einen kurzen Integrationstest für Suche + Liste ergänzen.
  5. Alle Tests grün halten, bevor du zu Router/Backend weitergehst.

Häufige Fehler

Fehler: Falsche Query-Methode

Tests nutzen getByTestId für alles und ignorieren Rollen/Labels. Dadurch werden Tests fragiler und weniger aussagekräftig.

Fix: Bevorzuge getByRole, getByLabelText und getByText in dieser Reihenfolge.

Fehler: userEvent ohne await

Eingaben und Klicks werden bei userEvent asynchron verarbeitet. Ohne await treten Race Conditions auf.

Fix: const user = userEvent.setup() und alle Interaktionen mit await ausführen.

Fehler: Integrationstest wird zu E2E-Test

Im Komponententest wird versucht, komplette Browser-Navigation und externe Dienste abzudecken. Das macht die Tests langsam und instabil.

Fix: In Teil 2 lokal bleiben (Komponenten + kurze Integrationen). E2E mit Playwright folgt in Teil 3.

Aufgaben

Aufgabe 1 Vitest einrichten
  • Füge Testabhängigkeiten und Scripts hinzu.
  • Konfiguriere vite.config.ts mit jsdom und Setup-Datei.
  • Prüfe, dass npm run test lokal durchläuft.
Aufgabe 2 Komponententest schreiben
  • Teste ein Formular oder eine Filter-Komponente aus FlugBoard.
  • Simuliere Eingabe und Klick mit userEvent.
  • Verifiziere den Callback mit den erwarteten Daten.
Aufgabe 3 Kurzer Integrationstest
  • Teste eine kleine Benutzerstrecke: Sucheingabe → gefilterte Liste.
  • Verifiziere sichtbare und nicht sichtbare Einträge.
  • Optional: Mocke API-Response mit MSW als kurzen Zusatz.
Bonus Test-Helfer abstrahieren
  • Erstelle eine eigene renderWithProviders()-Funktion.
  • Nutze sie in mindestens zwei Tests.
  • Vergleiche Lesbarkeit vor/nach der Abstraktion.
