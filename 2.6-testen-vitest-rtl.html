Lektion 2.6 — Teil 2: React Praxis

Testen mit Vitest + React Testing Library

React ca. 90 min

Lernziele

  • Testpyramide für React-Projekte einordnen
  • Vitest im Vite-Projekt konfigurieren
  • Mit React Testing Library benutzerzentriert testen
  • Interaktionen mit @testing-library/user-event abdecken
  • @testing-library/jest-dom Matchers sinnvoll einsetzen
  • Komponenten über Labels und Rollen testbar (und barrierefrei) machen
  • Im Integrationstest das Backend durch einen fetch-Mock ersetzen

1. Warum testen?

Tests sind für React-Projekte kein Selbstzweck. Sie reduzieren Regressionen, geben beim Refactoring Sicherheit und dokumentieren implizit, wie Komponenten genutzt werden sollen.

In diesem Kapitel setzen wir den Fokus klar auf Komponententests. Sie laufen schnell, sind lokal stabil und liefern den größten Lerneffekt für den UI-Alltag.

ℹ
Genau ein Test-Kapitel in Teil 2

Teil 2 hat absichtlich nur dieses eine Test-Kapitel. Spätere Kapitel bleiben auf Feature-Umsetzung fokussiert; die Test-Grundlage nehmen wir aber weiter mit.

2. Setup mit Vitest, RTL und jest-dom

Wir erweitern das FlugBoard aus Lektion 2.5 um Tests (fertiges Beispiel: beispiele/2.6). An der App selbst ändert sich fast nichts – dazu kommen nur Pakete, Konfiguration und Testdateien.

Terminal Bash 
npm install -D vitest jsdom @testing-library/react @testing-library/user-event @testing-library/jest-dom

# einmalig ausführen
npm run test

# beim Entwickeln: Tests laufen bei jeder Änderung neu
npm run test:watch
package.json (Scripts) JSON 
"scripts": {
  "dev": "vite",
  "build": "vite build",
  "preview": "vite preview",
  "test": "vitest run",
  "test:watch": "vitest"
}

Vitest liest seine Einstellungen aus vite.config.ts. Damit TypeScript den Block test kennt, kommt defineConfig jetzt aus vitest/config statt aus vite:

vite.config.ts TypeScript 
import { defineConfig } from 'vitest/config';
import react from '@vitejs/plugin-react';

export default defineConfig({
  plugins: [react()],
  test: {
    environment: 'jsdom',
    globals: true,
    setupFiles: './src/test/setup.ts',
  },
  optimizeDeps: {
    esbuildOptions: {
      sourcemap: false,
    },
  },
});

Mit globals: true stehen test, expect und vi ohne Import zur Verfügung. Damit auch der Editor sie kennt, ergänzen wir in tsconfig.json unter compilerOptions:

tsconfig.json (Ergänzung) JSON 
"types": ["vitest/globals"]

Die Setup-Datei läuft vor jedem Test. Sie bindet die zusätzlichen Matcher von jest-dom ein (z.B. toBeInTheDocument()) und stellt einen einfachen localStorage bereit, den unsere Hooks useLocalStorage und ThemeProvider brauchen:

src/test/setup.ts TypeScript 
import '@testing-library/jest-dom/vitest';

// Einfacher localStorage im Arbeitsspeicher für alle Tests.
// Grund: Ab Node 25 gibt es ein eigenes globales localStorage, das ohne
// Speicherdatei nicht funktioniert und das localStorage von jsdom überdeckt.
const data = new Map<string, string>();
const memoryStorage: Storage = {
  get length() { return data.size; },
  clear: () => data.clear(),
  getItem: (key) => data.get(key) ?? null,
  key: (index) => [...data.keys()][index] ?? null,
  removeItem: (key) => { data.delete(key); },
  setItem: (key, value) => { data.set(key, String(value)); },
};
Object.defineProperty(globalThis, 'localStorage', { value: memoryStorage, configurable: true });
💡
jsdom statt Browser

Vitest nutzt für Komponententests eine DOM-Simulation. Das reicht für Rendering, Klicks, Eingaben und die meisten Formular-Workflows.

3. Komponenten testbar machen: Labels und Rollen

React Testing Library testet aus Sicht von Nutzerinnen und Nutzern. Deshalb fragen wir Elemente bevorzugt über Rollen, Labels und sichtbaren Text ab – nicht über CSS-Selektoren oder Implementierungsdetails.

Das funktioniert nur, wenn die Elemente richtig beschriftet sind. In unserem Formular standen <label> und <input> bisher nur nebeneinander – verknüpft sind sie erst über htmlFor und id. Das Suchfeld und die Filter-Selects hatten gar keine Beschriftung; sie bekommen ein aria-label, das Suchfeld außerdem type="search" (Rolle searchbox).

src/components/AddFlightForm.tsx (Ausschnitt) TypeScript 
        <div className="form-field">
          <label className="form-label" htmlFor="add-flight-number">Flugnummer *</label>
          <input
            id="add-flight-number"
            className={inputClass('flightNumber')}
            value={flightNumber}
            onChange={(e) => setFlightNumber(e.target.value)}
            placeholder="z.B. OS123"
          />
          {errors.flightNumber && (
            <span className="form-error">{errors.flightNumber}</span>
          )}
        </div>
src/components/SearchBar.tsx (Ausschnitt) TypeScript 
      <input
        type="search"
        aria-label="Flüge suchen"
        className="search-input"
        value={value}
        placeholder={placeholder}
        onChange={(e) => onChange(e.target.value)}
      />
ℹ
Barrierefrei = gut testbar

Screenreader finden Elemente über genau dieselben Beschriftungen wie getByLabelText und getByRole. Was sich schlecht testen lässt, ist oft auch schlecht zugänglich – und umgekehrt.

4. Komponententests

Ein Komponententest rendert eine einzelne Komponente mit festen Props und prüft, was sichtbar ist. Der einfachste Fall: Zeigt das Badge zum Status das richtige Label?

src/components/FlightStatusBadge.test.tsx TypeScript 
import { render, screen } from '@testing-library/react';

import FlightStatusBadge from './FlightStatusBadge';

test('zeigt das deutsche Label zum Status', () => {
  render(<FlightStatusBadge status="delayed" />);

  expect(screen.getByText('Verspätet')).toBeInTheDocument();
});

Beim Formular simulieren wir Eingaben und Klicks mit userEvent. Statt einer echten Callback-Funktion übergeben wir eine Attrappe (vi.fn()) und prüfen, ob und womit sie aufgerufen wurde:

src/components/AddFlightForm.test.tsx TypeScript 
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';

import AddFlightForm from './AddFlightForm';

test('zeigt Fehler und ruft onAdd nicht auf, wenn Pflichtfelder fehlen', async () => {
  const user = userEvent.setup();
  const onAdd = vi.fn();

  render(<AddFlightForm onAdd={onAdd} onCancel={vi.fn()} />);

  await user.click(screen.getByRole('button', { name: 'Hinzufügen' }));

  expect(screen.getByText('Flugnummer ist erforderlich.')).toBeInTheDocument();
  expect(onAdd).not.toHaveBeenCalled();
});

test('ruft onAdd mit den eingegebenen Daten auf', async () => {
  const user = userEvent.setup();
  const onAdd = vi.fn();

  render(<AddFlightForm onAdd={onAdd} onCancel={vi.fn()} />);

  await user.type(screen.getByLabelText(/flugnummer/i), 'os123');
  await user.type(screen.getByLabelText(/airline/i), 'Austrian Airlines');
  await user.type(screen.getByLabelText(/abflugzeit/i), '10:30');
  await user.type(screen.getByLabelText(/ziel/i), 'London Heathrow (LHR)');
  await user.click(screen.getByRole('button', { name: 'Hinzufügen' }));

  expect(onAdd).toHaveBeenCalledWith(
    expect.objectContaining({
      flightNumber: 'OS123', // wird in Großbuchstaben umgewandelt
      airline: 'Austrian Airlines',
      type: 'departure',
      scheduledTime: '10:30',
      airport: 'London Heathrow (LHR)',
    }),
  );
});

5. Integrationstest: App + State + gemocktes Backend

Ein Integrationstest verbindet mehrere Bausteine. Hier rendern wir die ganze App: useFlights lädt die Daten, useFlightFilters filtert, FlightBoard zeigt sie an. Nur das Backend ersetzen wir: vi.stubGlobal('fetch', ...) tauscht das globale fetch gegen eine Funktion aus, die immer unsere Testflüge liefert.

src/App.integration.test.tsx TypeScript 
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';

import App from './App';
import { ThemeProvider } from './context/ThemeContext';
import { Flight } from './types/flight';

const testFlights: Flight[] = [
  {
    id: 1, flightNumber: 'OS123', airline: 'Austrian Airlines', type: 'departure',
    scheduledTime: '10:30', status: 'boarding', airport: 'London Heathrow (LHR)', terminal: 'T3',
  },
  {
    id: 2, flightNumber: 'LH456', airline: 'Lufthansa', type: 'departure',
    scheduledTime: '11:15', status: 'on-time', airport: 'Frankfurt (FRA)', terminal: 'T2',
  },
  {
    id: 3, flightNumber: 'EK789', airline: 'Emirates', type: 'arrival',
    scheduledTime: '09:45', status: 'landed', airport: 'Dubai (DXB)', terminal: 'T1',
  },
];

beforeEach(() => {
  localStorage.clear(); // gespeicherte Filter aus useLocalStorage entfernen
  // fetch durch eine Attrappe ersetzen: Statt des Backends kommen immer die Testflüge
  vi.stubGlobal('fetch', vi.fn(async () => new Response(JSON.stringify(testFlights))));
});

afterEach(() => {
  vi.unstubAllGlobals();
});

// App braucht den ThemeProvider – wie in main.tsx
const renderApp = () =>
  render(
    <ThemeProvider>
      <App />
    </ThemeProvider>,
  );

test('zeigt die Flüge aus dem Backend an', async () => {
  renderApp();

  // findBy… wartet, bis die Daten geladen sind
  expect(await screen.findByText('OS123')).toBeInTheDocument();
  expect(screen.getByText('EK789')).toBeInTheDocument();
});

test('Suche filtert die Tabelle, ohne Treffer erscheint der Empty State', async () => {
  const user = userEvent.setup();
  renderApp();
  await screen.findByText('OS123');

  const search = screen.getByRole('searchbox', { name: 'Flüge suchen' });
  await user.type(search, 'Frankfurt');

  expect(screen.getByText('LH456')).toBeInTheDocument();
  expect(screen.queryByText('OS123')).not.toBeInTheDocument();

  await user.clear(search);
  await user.type(search, 'xyz');

  // Abflüge und Ankünfte sind leer → zwei Empty States mit Reset-Button
  expect(screen.getAllByText('Keine Flüge gefunden')).toHaveLength(2);

  await user.click(screen.getAllByRole('button', { name: 'Filter zurücksetzen' })[0]);

  expect(screen.getByText('OS123')).toBeInTheDocument();
});
💡
getBy, queryBy, findBy

getBy… erwartet, dass das Element jetzt da ist, sonst schlägt der Test fehl. queryBy… liefert null statt eines Fehlers – ideal für „ist nicht da“. findBy… wartet, bis das Element erscheint – nötig, wenn Daten erst asynchron geladen werden.

ℹ
MSW nur als Ausblick

Für größere Projekte gibt es MSW (Mock Service Worker), das echte HTTP-Endpunkte nachbildet. Für unser Projekt reicht der einfache fetch-Mock.

Projektschritt

Projektschritt 2.6

Test-Basis für FlugBoard einziehen

  1. Testpakete installieren, Scripts in package.json ergänzen.
  2. vite.config.ts auf vitest/config umstellen und den Block test einfügen; "types": ["vitest/globals"] in tsconfig.json ergänzen.
  3. src/test/setup.ts anlegen.
  4. Komponenten beschriften: htmlFor/id in AddFlightForm, aria-label für Suchfeld und Filter-Selects, Suchfeld als type="search".
  5. Die Tests FlightStatusBadge.test.tsx, AddFlightForm.test.tsx und App.integration.test.tsx anlegen.
  6. npm run test: Alle Tests müssen grün sein, bevor du mit Lektion 2.7 weitermachst.

Häufige Fehler

5 Fehler · zum Aufklappen klicken
Fehler: Falsche Query-Methode

Tests nutzen getByTestId für alles und ignorieren Rollen/Labels. Dadurch werden Tests fragiler und weniger aussagekräftig.

Fix: Bevorzuge getByRole, getByLabelText und getByText in dieser Reihenfolge.

Fehler: userEvent ohne await

Eingaben und Klicks werden bei userEvent asynchron verarbeitet. Ohne await treten Race Conditions auf.

Fix: const user = userEvent.setup() und alle Interaktionen mit await ausführen.

Fehler: getByLabelText findet das Feld nicht

Unable to find a label with the text of: Flugnummer – das <label> steht zwar neben dem Feld, ist aber nicht damit verknüpft.

Fix: <label htmlFor="add-flight-number"> und <input id="add-flight-number"> – oder das Feld in das <label> hineinschreiben.

Fehler: getBy statt findBy bei geladenen Daten

Direkt nach render() sind die Daten aus fetch noch nicht da. screen.getByText('OS123') schlägt deshalb fehl, obwohl die App funktioniert.

Fix: Auf das erste asynchron geladene Element mit await screen.findByText(...) warten.

Fehler: Integrationstest wird zu E2E-Test

Im Komponententest wird versucht, komplette Browser-Navigation und externe Dienste abzudecken. Das macht die Tests langsam und instabil.

Fix: In Teil 2 lokal bleiben (Komponenten + kurze Integrationen). E2E mit Playwright folgt in Teil 3.

Aufgaben

3 Aufgaben + Bonus · zum Aufklappen klicken
Aufgabe 1 Vitest einrichten
  • Füge Testabhängigkeiten und Scripts hinzu.
  • Konfiguriere vite.config.ts mit jsdom und Setup-Datei.
  • Prüfe, dass npm run test lokal durchläuft.
Aufgabe 2 Komponententest schreiben
  • Teste SearchBar: Eine Eingabe ruft onChange mit dem Text auf.
  • Ist ein Wert gesetzt, löscht der Button „Suche löschen“ ihn (onChange('')).
  • Ohne Wert gibt es keinen Löschen-Button (queryByRole liefert null).
Aufgabe 3 Kurzer Integrationstest
  • Erweitere App.integration.test.tsx um einen Test für den Status-Filter.
  • Wähle im Select „Nach Status filtern“ den Wert „Pünktlich“ (user.selectOptions(...)).
  • Prüfe: LH456 ist sichtbar, OS123 (Boarding) nicht.
Bonus Test-Helfer abstrahieren
  • Erstelle eine eigene renderWithProviders()-Funktion, die eine Komponente in ThemeProvider einwickelt.
  • Nutze sie in mindestens zwei Tests.
  • Vergleiche Lesbarkeit vor/nach der Abstraktion.

Quiz

5 Fragen · zum Aufklappen klicken

Frage 1 Worüber fragt die React Testing Library Elemente bevorzugt ab?

Mehrere Antworten sind richtig.

Erklärung: Die Testing Library fragt aus Sicht der Benutzer:innen ab: über Rollen (getByRole), Labels (getByLabelText) und sichtbaren Text (getByText). CSS-Klassen, Komponentennamen und State sind Implementierungsdetails, die Benutzer:innen nicht sehen.

Frage 2 Warum findet getByLabelText('Flugnummer') das Eingabefeld nicht?

Erklärung: Was für Screenreader richtig beschriftet ist, ist auch gut testbar – barrierefrei und testbar gehen Hand in Hand.

Frage 3 Welcher Matcher stammt aus @testing-library/jest-dom?

Erklärung: jest-dom ergänzt DOM-spezifische Matcher wie toBeInTheDocument, toBeDisabled oder toHaveValue. Die Setup-Datei bindet sie vor jedem Test ein.

Frage 4 Welche Aussagen über getBy… und queryBy… sind richtig?

Mehrere Antworten sind richtig.

Erklärung: getBy… wirft einen Fehler, wenn das Element fehlt – praktisch, wenn es sicher da sein muss. queryBy… liefert dann null; damit prüft man, dass ein Element nicht vorhanden ist. Auf Elemente, die erst später erscheinen, wartet queryBy… nicht.

Frage 5 In welcher Umgebung laufen die Komponententests mit Vitest?

Erklärung: Das reicht für Rendering, Klicks und Formulare. Tests in echten Browsern folgen mit Playwright (Lektion 3.5).
