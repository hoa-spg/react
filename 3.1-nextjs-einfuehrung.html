Lektion 3.1 — Teil 3: Next.js

Einführung Next.js

Next.js ca. 90 min

Lernziele

Nach dieser Lektion kannst du folgendes:

  • Den Unterschied zwischen React und Next.js erklären
  • CSR, SSR und SSG voneinander unterscheiden und den richtigen Ansatz für FlugBoard wählen
  • Ein neues Next.js-Projekt mit create-next-app erstellen
  • Die Projektstruktur des App Routers verstehen
  • app/page.tsx als Einstiegspunkt und layout.tsx als globales Layout einsetzen
  • TypeScript-Typen aus dem React-Projekt wiederverwenden

1 — React vs. Next.js

React ist eine UI-Bibliothek. Sie kümmert sich ausschließlich darum, wie Daten in DOM-Elemente umgewandelt werden. Alles andere — Routing, Datenabruf, Build-Setup, Server-Logik — musst du selbst zusammenbauen oder separate Bibliotheken einbinden.

Next.js ist ein Full-Stack-Framework, das auf React aufbaut. Es bringt all diese Zutaten direkt mit und trifft bereits viele Architekturentscheidungen für dich. Das bedeutet: weniger Konfiguration, mehr Konvention.

ℹ
Next.js ist kein Ersatz für React

Next.js verwendet React intern. Du schreibst weiterhin React-Komponenten mit JSX, Props und Hooks — Next.js fügt nur Schichten hinzu, die React allein nicht bietet. Alles, was du in Teil 1 gelernt hast, gilt hier weiterhin.

Vergleichstabelle: React SPA vs. Next.js

Merkmal React SPA (Vite) Next.js (App Router)
Routing Manuell via React Router Dateibasiert — jede page.tsx = URL
Rendering Nur Client-Side Rendering (CSR) CSR, SSR, SSG, ISR — pro Seite wählbar
Backend Externes Backend nötig (z. B. Deno) API Routes direkt im Projekt (route.ts)
SEO Eingeschränkt — leeres HTML für Crawler Vollständiges HTML vom Server, optimale SEO
Bilder / Fonts Keine automatische Optimierung next/image & next/font eingebaut
Deployment Statische Dateien, beliebiger Hoster Vercel (optimal), Node-Server oder statisch
TypeScript Möglich, aber manuell einrichten Out-of-the-box, vollständige Unterstützung

2 — CSR, SSR und SSG verstehen

Die größte Stärke von Next.js ist die Flexibilität beim Rendering. Du kannst für jede Seite individuell entscheiden, wie HTML erzeugt wird.

Client-Side Rendering (CSR)

Der Server liefert eine leere HTML-Datei. Der Browser lädt das JavaScript-Bundle herunter, führt es aus und rendert die Seite erst dann. Das war unser Ansatz in Teil 1 mit Vite. Nachteil: Suchmaschinen und langsame Verbindungen sehen zunächst nichts.

Server-Side Rendering (SSR)

Der Server rendert das vollständige HTML bei jedem Request. Der Browser erhält sofort lesbaren Inhalt. Ideal für Daten, die sich häufig ändern — zum Beispiel Abflugzeiten eines Flughafens.

Static Site Generation (SSG)

Das HTML wird einmalig beim Build erzeugt und dann als statische Datei ausgeliefert. Blitzschnell, da kein Server-Rendering nötig. Ideal für Inhalte, die sich selten ändern, wie eine Über-uns-Seite.

Incremental Static Regeneration (ISR)

Eine Kombination: die Seite wird statisch ausgeliefert, aber nach einer definierten Zeit (revalidate) im Hintergrund neu generiert. Der Besucher erhält immer eine gecachte Version — aber nie älter als X Sekunden.

ℹ
FlugBoard & SSR

Unser FlugBoard zeigt Live-Flugdaten: Abflüge und Ankünfte ändern sich ständig. SSR mit revalidate: 30 ist deshalb der perfekte Ansatz — aktuelle Daten, ohne unnötige Server-Last bei jedem Request.

3 — Projekt erstellen

Next.js bringt ein offizielles CLI-Tool mit, das alle nötigen Dateien und Konfigurationen automatisch einrichtet. Führe folgende Befehle in deinem Terminal aus:

Terminal Bash 
npx create-next-app@latest flugboard-next

Der Setup-Wizard stellt folgende Fragen — wähle genau diese Antworten:

create-next-app Wizard Bash 
✔ Would you like to use TypeScript?          › Yes
✔ Would you like to use ESLint?              › Yes
✔ Would you like to use Tailwind CSS?        › No
✔ Would you like your code inside a `src/` directory?  › Yes
✔ Would you like to use App Router?          › Yes
✔ Would you like to use Turbopack?           › No
✔ Would you like to customize the import alias?        › No

Anschließend das Projekt starten:

Terminal Bash 
cd flugboard-next
npm run dev
# → Lokaler Entwicklungsserver: http://localhost:3000
✓
Turbopack vs. Webpack

Turbopack ist der neue, schnellere Bundler von Vercel. Für diesen Kurs deaktivieren wir ihn, da er noch experimentell ist und gelegentlich inkompatibel mit älteren Plugins sein kann. Im Alltag kannst du ihn bedenkenlos aktivieren.

4 — Projektstruktur verstehen

Nach dem Setup hat create-next-app folgende Struktur erzeugt. Die wichtigsten Ordner und Dateien auf einen Blick:

Projektstruktur Bash 
flugboard-next/
├── src/
│   └── app/
│       ├── layout.tsx          ← Globales Layout (HTML-Rahmen)
│       ├── page.tsx            ← Startseite → http://localhost:3000/
│       ├── globals.css         ← Globale CSS-Stile
│       ├── departures/
│       │   └── page.tsx        ← Abflüge → /departures
│       ├── arrivals/
│       │   └── page.tsx        ← Ankünfte → /arrivals
│       └── flight/
│           └── [id]/
│               └── page.tsx    ← Detailseite → /flight/LH123
├── public/
│   └── favicon.ico
├── next.config.ts
├── tsconfig.json
└── package.json

Der entscheidende Unterschied zu React Router: jede Datei namens page.tsx wird automatisch zu einer öffentlichen URL. Du musst kein <Routes>-Setup schreiben — die Ordnerstruktur ist das Routing.

Wichtige Regeln für den App Router

  • Nur page.tsx, layout.tsx, loading.tsx usw. sind „reservierte“ Dateinamen mit besonderer Bedeutung.
  • Eigene Komponenten (z. B. FlightCard.tsx) kannst du im selben Ordner ablegen — sie werden nicht zu URLs.
  • Ordner in eckigen Klammern ([id]) sind dynamische Segmente.
  • Ordner in runden Klammern ((board)) sind Route Groups — sie gruppieren Seiten, tauchen aber nicht in der URL auf.
ℹ
Pages Router vs. App Router

Next.js hatte früher den Pages Router (pages/-Ordner). Seit Next.js 13 gibt es den moderneren App Router (app/-Ordner). In diesem Kurs verwenden wir ausschließlich den App Router. Ältere Tutorials nutzen oft noch den Pages Router — achte auf diesen Unterschied beim Recherchieren.

5 — app/page.tsx und layout.tsx

Die zwei wichtigsten Dateien beim Start sind page.tsx (die Startseite) und layout.tsx (der HTML-Rahmen, der alle Seiten umschließt).

layout.tsx — Globaler HTML-Rahmen

layout.tsx definiert das <html>- und <body>-Tag für die gesamte Anwendung. Zusätzlich kannst du hier das metadata-Objekt exportieren, das automatisch in <meta>-Tags umgewandelt wird — ideal für SEO.

src/app/layout.tsx TypeScript 
import type { Metadata } from 'next';
import './globals.css';

export const metadata: Metadata = {
  title: {
    template: '%s | FlugBoard',
    default: 'FlugBoard – Flughafen München',
  },
  description:
    'Echtzeit-Abflug- und Ankunftstafel für den Flughafen München.',
  keywords: ['Flug', 'Abflug', 'Ankunft', 'München', 'Airport'],
};

export default function RootLayout({
  children,
}: {
  children: React.ReactNode;
}) {
  return (
    <html lang="de">
      <body>
        {children}
      </body>
    </html>
  );
}

Das template-Feld im title sorgt dafür, dass jede Unterseite automatisch „Abflüge | FlugBoard“ als Titel bekommt, wenn sie title: 'Abflüge' in ihrer eigenen Metadata definiert.

page.tsx — Die Startseite

Im Gegensatz zum React-Projekt mit Vite ist page.tsx standardmäßig eine Server Component. Das bedeutet: kein 'use client', kein useState, kein useEffect — der Code läuft auf dem Server und liefert fertiges HTML.

src/app/page.tsx TypeScript 
import Link from 'next/link';
import type { Metadata } from 'next';

export const metadata: Metadata = {
  title: 'Startseite',
};

export default function HomePage() {
  return (
    <main className="home-container">
      <h1>✈ FlugBoard München</h1>
      <p className="home-subtitle">
        Ihre Echtzeit-Flugtafel für alle Abflüge und Ankünfte.
      </p>
      <nav className="home-nav">
        <Link href="/departures" className="home-btn">
          ➔ Abflüge
        </Link>
        <Link href="/arrivals" className="home-btn home-btn--secondary">
          ➔ Ankünfte
        </Link>
      </nav>
    </main>
  );
}
⚠
<Link> statt <a>

In Next.js verwendest du immer import Link from 'next/link' für interne Navigation. Ein normales <a href="/departures"> funktioniert zwar, lädt aber die gesamte Seite neu. <Link> nutzt client-seitiges Navigation und prälädt Seiten im Hintergrund.

6 — TypeScript-Typen wiederverwenden

Einer der größten Vorteile beim Wechsel zu Next.js: du kannst deine bestehenden TypeScript-Typen aus dem React-Projekt eins zu eins übernehmen. Kopiere einfach die Datei src/types/flight.ts in das neue Next.js-Projekt.

src/types/flight.ts TypeScript 
export type FlightStatus =
  | 'on-time'
  | 'delayed'
  | 'boarding'
  | 'departed'
  | 'landed'
  | 'cancelled';

export type FlightType = 'departure' | 'arrival';

export interface Flight {
  id: number;
  flightNumber: string;
  airline: string;
  airport: string;
  scheduledTime: string;
  expectedTime?: string;
  gate?: string;
  terminal: string;
  status: FlightStatus;
  type: FlightType;
}

Statt lokaler Testdaten greifen wir direkt auf den Datenbankzugriff aus Lektion 2.8 auf. In Next.js kannst du dafür entweder die bestehenden API-Endpunkte nutzen oder später in Server Components direkt auf die Datenbank zugreifen.

Terminal — Dateien kopieren Bash 
# Aus dem bestehenden Projekt Typen und Komponenten übernehmen
cp ../flugboard/src/types/flight.ts   src/types/flight.ts

# Ordner anlegen falls noch nicht vorhanden
mkdir -p src/types src/lib src/components

Projektschritt

Projektschritt 3.1

FlugBoard-Next-Projekt aufsetzen

In diesem Projektschritt erstellen wir das Next.js-Fundament für FlugBoard. Am Ende hast du ein laufendes Next.js-Projekt mit korrekten Metadaten und einer funktionierenden Startseite.

  1. Projekt erstellen: Führe npx create-next-app@latest flugboard-next aus und wähle die oben gezeigten Optionen.
  2. Typen & DB-Utility vorbereiten: Übertrage src/types/flight.ts und richte eine zentrale Datenzugriffsdatei unter src/lib/ ein.
  3. layout.tsx aktualisieren: Setze Title-Template, Description und Keywords wie im Beispiel oben.
  4. page.tsx ersetzen: Schreibe die Startseite mit Überschrift, Untertitel und Links zu /departures und /arrivals.
  5. Platzhalter-Seiten: Lege src/app/departures/page.tsx und src/app/arrivals/page.tsx mit einfachen “Kommt bald”-Texten an.
  6. Testen: Starte den Dev-Server und navigiere zwischen den Seiten. Prüfe in den Browser-DevTools den <title>-Tag.
src/app/departures/page.tsx TypeScript 
import type { Metadata } from 'next';
import { listFlights } from '@/lib/flights-db';

export const metadata: Metadata = {
  title: 'Abflüge',
};

export default function DeparturePage() {
  const departures = listFlights('departure');

  return (
    <main>
      <h1>Abflüge — {departures.length} Flüge</h1>
      <ul>
        {departures.map(flight => (
          <li key={flight.id}>
            {flight.flightNumber} – {flight.airport} – {flight.status}
          </li>
        ))}
      </ul>
    </main>
  );
}

Häufige Fehler

Fehler: Pages Router-Syntax im App Router verwendet

Du schreibst export default function Page({ params }) {} im pages/-Ordner, obwohl du den App Router (app/) verwendest. Oder du verwendest getServerSideProps, das im App Router nicht existiert.

Fix: Stelle sicher, dass alle Seiten im src/app/-Ordner liegen. Im App Router gibt es kein getServerSideProps — stattdessen sind async Server Components der neue Ansatz (Lektion 3.1).

Fehler: <a href> statt <Link href>

Interne Links werden mit <a href="/departures"> geschrieben. Die Navigation funktioniert, aber die Seite wird vollständig neu geladen — kein SPA-Verhalten, kein Prefetching.

Fix: Immer import Link from 'next/link' für interne Navigation verwenden. <a> nur für externe URLs (z. B. https://...).

Fehler: Port-Konflikt 5173 vs. 3000

Du versuchst den Dev-Server zu starten, aber Port 3000 ist bereits belegt — oft weil der alte Vite-Dev-Server noch läuft (Port 5173) oder ein anderer Next.js-Prozess aktiv ist.

Fix: Beende alle laufenden Dev-Server (Ctrl+C) oder starte Next.js auf einem anderen Port: npm run dev -- -p 3001.

Fehler: <img> statt next/image

Du verwendest ein normales <img src="...">. Next.js zeigt eine ESLint-Warnung und das Bild wird nicht optimiert.

Fix: import Image from 'next/image' und <Image src="..." alt="..." width={200} height={100} />. Next.js konvertiert das Bild automatisch in WebP und lazy-loadt es.

Aufgaben

Aufgabe 1 Projekt erstellen und layout.tsx anpassen

Erstelle das flugboard-next-Projekt mit den empfohlenen Einstellungen und passe anschließend layout.tsx an.

  • Führe npx create-next-app@latest flugboard-next aus
  • Ersetze den Standard-Inhalt in layout.tsx durch das FlugBoard-Metadata-Objekt
  • Setze lang="de" im <html>-Tag
  • Starte den Dev-Server und überprüfe http://localhost:3000
Aufgabe 2 Startseite mit Links und DB-Vorschau

Erstelle eine ansprechende Startseite in src/app/page.tsx.

  • Kopiere src/types/flight.ts und richte src/lib/flights-db.ts ein
  • Zeige auf der Startseite 3 Flüge aus der Datenbank als Vorschau-Liste an
  • Füge zwei <Link>-Buttons für /departures und /arrivals ein
  • Exportiere ein passendes metadata-Objekt für die Seite
Aufgabe 3 Platzhalterseiten für alle Routen anlegen

Lege die Grundstruktur für alle Seiten des FlugBoards an.

  • Erstelle src/app/departures/page.tsx mit Liste der Abflüge aus listFlights('departure')
  • Erstelle src/app/arrivals/page.tsx mit Liste der Ankünfte
  • Erstelle src/app/flight/[id]/page.tsx als Platzhalter (Flug-ID anzeigen)
  • Navigiere zwischen allen Seiten und prüfe, ob die URLs korrekt sind
Aufgabe 4 — Bonus 404-Seite mit not-found.tsx

Next.js erlaubt eine benutzerdefinierte 404-Seite über die Datei not-found.tsx.

  • Erstelle src/app/not-found.tsx mit einer freundlichen Fehlermeldung
  • Füge einen <Link href="/">-Button zum Zurücknavigieren ein
  • Teste die Seite, indem du eine nicht existierende URL aufrufst (z. B. /foo)
  • Exportiere ein metadata-Objekt mit title: '404 – Seite nicht gefunden'
