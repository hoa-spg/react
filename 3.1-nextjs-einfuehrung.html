  • Ein neues Next.js-Projekt mit create-next-app erstellen
  • Die Projektstruktur des App Routers verstehen
  • app/page.tsx als Einstiegspunkt und layout.tsx als globales Layout einsetzen

1 — React vs. Next.js

React ist eine UI-Bibliothek. Sie kümmert sich ausschließlich darum, wie Daten in DOM-Elemente umgewandelt werden. Alles andere — Routing, Datenabruf, Build-Setup, Server-Logik — musst du selbst zusammenbauen oder separate Bibliotheken einbinden.

Next.js ist ein Full-Stack-Framework, das auf React aufbaut. Es bringt all diese Zutaten direkt mit und trifft bereits viele Architekturentscheidungen für dich. Das bedeutet: weniger Konfiguration, mehr Konvention.

ℹ
Next.js ist kein Ersatz für React

Next.js verwendet React intern. Du schreibst weiterhin React-Komponenten mit JSX, Props und Hooks — Next.js fügt nur Schichten hinzu, die React allein nicht bietet. Alles, was du in Teil 1 und 2 gelernt hast, gilt hier weiterhin.

Für FlugBoard bedeutet das: Wir legen ein neues Projekt an. Mit dabei sind die Typen aus src/types/flight.ts, das Datenbankschema aus Lektion 2.8 und später unsere Komponenten. Wegfallen werden Vite, React Router (Next.js routet über Ordner) und das eigene Deno-Backend (Next.js liest die Datenbank selbst und bringt eigene API-Routen mit).

Vergleichstabelle: React SPA vs. Next.js

Merkmal React SPA (Vite) Next.js (App Router)
Routing Manuell via React Router Dateibasiert — jede page.tsx = URL
Rendering Nur Client-Side Rendering (CSR) CSR, SSR, SSG, ISR — pro Seite wählbar
Backend Externes Backend nötig (z. B. Deno) API Routes direkt im Projekt (route.ts)
SEO Eingeschränkt — leeres HTML für Crawler Vollständiges HTML vom Server, optimale SEO
Bilder / Fonts Keine automatische Optimierung next/image & next/font eingebaut
Deployment Statische Dateien, beliebiger Hoster Vercel (optimal), Node-Server oder statisch
TypeScript Möglich, aber manuell einrichten Out-of-the-box, vollständige Unterstützung

2 — CSR, SSR und SSG verstehen

Die größte Stärke von Next.js ist die Flexibilität beim Rendering. Du kannst für jede Seite individuell entscheiden, wie HTML erzeugt wird.

Client-Side Rendering (CSR)

Der Server liefert eine leere HTML-Datei. Der Browser lädt das JavaScript-Bundle herunter, führt es aus und rendert die Seite erst dann. Das war unser Ansatz in Teil 1 mit Vite. Nachteil: Suchmaschinen und langsame Verbindungen sehen zunächst nichts.

Server-Side Rendering (SSR)

Der Server rendert das vollständige HTML bei jedem Request. Der Browser erhält sofort lesbaren Inhalt. Ideal für Daten, die sich häufig ändern — zum Beispiel Abflugzeiten eines Flughafens.

Static Site Generation (SSG)

Das HTML wird einmalig beim Build erzeugt und dann als statische Datei ausgeliefert. Blitzschnell, da kein Server-Rendering nötig. Ideal für Inhalte, die sich selten ändern, wie eine Über-uns-Seite.

Incremental Static Regeneration (ISR)

Eine Kombination: die Seite wird statisch ausgeliefert, aber nach einer definierten Zeit (revalidate) im Hintergrund neu generiert. Der Besucher erhält immer eine gecachte Version — aber nie älter als X Sekunden.

ℹ
FlugBoard & SSR

Unser FlugBoard zeigt Live-Flugdaten: Abflüge und Ankünfte ändern sich ständig. Dafür eignet sich SSR (immer aktuell) oder ISR mit revalidate: 30 (höchstens 30 Sekunden alt, aber weniger Server-Last). Wie man das pro Seite einstellt, sehen wir in Lektion 3.3.

4 — Projektstruktur verstehen

Nach dem Setup hat create-next-app folgende Struktur erzeugt. Die wichtigsten Ordner und Dateien auf einen Blick:

Projektstruktur Bash

Der entscheidende Unterschied zu React Router: jede Datei namens page.tsx wird automatisch zu einer öffentlichen URL. Du musst kein <Routes>-Setup schreiben — die Ordnerstruktur ist das Routing.

Wichtige Regeln für den App Router

  • Nur page.tsx, layout.tsx, loading.tsx usw. sind „reservierte“ Dateinamen mit besonderer Bedeutung.
  • Eigene Komponenten (z. B. FlightCard.tsx) kannst du im selben Ordner ablegen — sie werden nicht zu URLs.
  • Ordner in eckigen Klammern ([id]) sind dynamische Segmente.
  • Ordner in runden Klammern ((board)) sind Route Groups — sie gruppieren Seiten, tauchen aber nicht in der URL auf.
ℹ
Pages Router vs. App Router

Next.js hatte früher den Pages Router (pages/-Ordner). Seit Next.js 13 gibt es den moderneren App Router (app/-Ordner). In diesem Kurs verwenden wir ausschließlich den App Router. Ältere Tutorials nutzen oft noch den Pages Router — achte auf diesen Unterschied beim Recherchieren.

5 — app/page.tsx und layout.tsx

Die zwei wichtigsten Dateien beim Start sind page.tsx (die Startseite) und layout.tsx (der HTML-Rahmen, der alle Seiten umschließt).

layout.tsx — Globaler HTML-Rahmen

layout.tsx definiert das <html>- und <body>-Tag für die gesamte Anwendung. Zusätzlich kannst du hier das metadata-Objekt exportieren, das automatisch in <meta>-Tags umgewandelt wird — ideal für SEO.

src/app/layout.tsx TypeScript 
import type { Metadata } from 'next';
import Link from 'next/link';
import './globals.css';

export const metadata: Metadata = {
  title: {
    template: '%s | FlugBoard',
    default: 'FlugBoard – Flughafen Wien',
  },
  description: 'Aktuelle Abflüge und Ankünfte – Flughafen Wien-Schwechat',
  keywords: ['Flug', 'Abflug', 'Ankunft', 'Wien', 'Airport'],
  icons: {
    icon: "data:image/svg+xml,%3Csvg xmlns='http://www.w3.org/2000/svg' viewBox='0 0 64 64'%3E%3Ctext y='50' font-size='48'%3E%E2%9C%88%EF%B8%8F%3C/text%3E%3C/svg%3E",
  },
};

export default function RootLayout({
  children,
}: {
  children: React.ReactNode;
}) {
  return (
    <html lang="de">
      <body>
        {/* Kopfzeile erscheint auf jeder Seite */}
        <header className="app-header">

Das template-Feld im title sorgt dafür, dass jede Unterseite automatisch „Abflüge | FlugBoard“ als Titel bekommt, wenn sie title: 'Abflüge' in ihrer eigenen Metadata definiert.

ℹ
globals.css und CSS Modules

globals.css wird im Root-Layout importiert und gilt für alle Seiten – wie das Komponenten-CSS im Vite-Projekt. Wir bleiben auch hier bei global gültigen, eindeutig benannten Klassen. Next.js unterstützt aber ebenso CSS Modules (*.module.css, siehe Exkurs in Lektion 1.3), wenn du Styles auf eine Komponente beschränken willst.

page.tsx — Die Startseite

Im Gegensatz zum React-Projekt mit Vite ist page.tsx standardmäßig eine Server Component. Das bedeutet: kein 'use client', kein useState, kein useEffect — der Code läuft auf dem Server und liefert fertiges HTML. Deshalb kann die Startseite die nächsten Abflüge direkt aus der Datenbank lesen — ohne fetch, ohne Ladezustand (listFlights kommt in Abschnitt 6).

⚠
<Link> statt <a>

In Next.js verwendest du immer import Link from 'next/link' für interne Navigation. Ein normales <a href="/departures"> funktioniert zwar, lädt aber die gesamte Seite neu. <Link> nutzt client-seitiges Navigation und prälädt Seiten im Hintergrund.

6 — TypeScript-Typen wiederverwenden

Einer der größten Vorteile beim Wechsel zu Next.js: du kannst deine bestehenden TypeScript-Typen aus dem React-Projekt eins zu eins übernehmen. Kopiere einfach die Datei src/types/flight.ts in das neue Next.js-Projekt.

Datenzugriff: src/lib/flights-db.ts

Statt eines eigenen Backends liest Next.js die Datenbank direkt. Tabelle, mapFlight und Beispielflüge übernehmen wir aus backend/db.ts von Lektion 2.8. Zwei Dinge sind anders:

Lektion 2.8 (Deno)Ab 3.1 (Next.js / Node)
Treiber @libsql/client — asynchron (await) better-sqlite3 — synchron (.all(), .get(), .run())
Datei backend/flugboard.db flugboard.sqlite im Projektordner
Funktionen createFlight, updateFlightStatus, deleteFlight insertFlight, updateFlight (beliebige Felder), removeFlight

better-sqlite3 ist in Node.js der übliche SQLite-Treiber und funktioniert in Next.js ohne Zusatzkonfiguration. Weil er synchron arbeitet, brauchen unsere Datenbankfunktionen kein await. Die globale Variable __flugboardDb sorgt dafür, dass der Dev-Server beim Neuladen nicht jedes Mal eine neue Verbindung öffnet.

const mapFlight = (row: Row): Flight => ({
  id: row.id,
  flightNumber: row.flightNumber,
  airline: row.airline,
  type: row.type as Flight['type'],
  scheduledTime: row.scheduledTime,

  // eslint-disable-next-line no-var
  var __flugboardDb: Database.Database | undefined;
}

const sqlite = global.__flugboardDb ?? new Database('flugboard.sqlite');
if (!global.__flugboardDb) {
  global.__flugboardDb = sqlite;
}

const db = drizzle(sqlite);

sqlite.exec(`
  CREATE TABLE IF NOT EXISTS flights (
    id INTEGER PRIMARY KEY,
    flight_number TEXT NOT NULL,
    airline TEXT NOT NULL,
    type TEXT NOT NULL,
    scheduled_time TEXT NOT NULL,
    expected_time TEXT,
    status TEXT NOT NULL,
    airport TEXT NOT NULL,
    terminal TEXT NOT NULL,
    gate TEXT
  );
`);

const countRow = sqlite.prepare('SELECT COUNT(*) as count FROM flights').get() as
  | { count: number }
  | undefined;

if (!countRow || countRow.count === 0) {
  db.insert(flightsTable).values(
    seedFlights.map((flight) => ({
      id: flight.id,
      flightNumber: flight.flightNumber,
      airline: flight.airline,
      type: flight.type,
      scheduledTime: flight.scheduledTime,
      expectedTime: flight.expectedTime ?? null,
      status: flight.status,
      airport: flight.airport,
      terminal: flight.terminal,
      gate: flight.gate ?? null,
    }))
  )
    // Beim Build rendern mehrere Prozesse gleichzeitig und sehen alle eine leere
    // Tabelle – bereits vorhandene IDs daher einfach überspringen
    .onConflictDoNothing()
    .run();
}

export const listFlights = (type?: string, status?: string): Flight[] => {
  const filters = [];
  if (type) filters.push(eq(flightsTable.type, type));
  if (status) filters.push(eq(flightsTable.status, status));
  const rows = filters.length
    ? db.select().from(flightsTable).where(and(...filters)).all()
    : db.select().from(flightsTable).all();
  return rows.map(mapFlight);
};

export const getFlightById = (id: number): Flight | null => {
  const row = db.select().from(flightsTable).where(eq(flightsTable.id, id)).get();
  return row ? mapFlight(row) : null;
};

export const insertFlight = (input: Omit<Flight, 'id' | 'status'>): Flight => {
  const newFlight: Flight = {
    id: Date.now(),
    status: 'on-time',
    ...input,
  };

  db.insert(flightsTable)
    .values({
      id: newFlight.id,
      flightNumber: newFlight.flightNumber,
      airline: newFlight.airline,
      type: newFlight.type,
      scheduledTime: newFlight.scheduledTime,
      expectedTime: newFlight.expectedTime ?? null,
      status: newFlight.status,
      airport: newFlight.airport,
      terminal: newFlight.terminal,
      gate: newFlight.gate ?? null,
    })
    .run();

  return newFlight;
};

export const removeFlight = (id: number): Flight | null => {
  const flight = getFlightById(id);
  if (!flight) return null;
  db.delete(flightsTable).where(eq(flightsTable.id, id)).run();
  return flight;
};

export const updateFlight = (id: number, payload: Partial<Flight>): Flight | null => {
  const current = getFlightById(id);
  if (!current) return null;

  db.update(flightsTable)
    .set({
      flightNumber: payload.flightNumber ?? current.flightNumber,
      airline: payload.airline ?? current.airline,
      type: payload.type ?? current.type,
      scheduledTime: payload.scheduledTime ?? current.scheduledTime,
      expectedTime: payload.expectedTime ?? current.expectedTime ?? null,
      status: payload.status ?? current.status,
      airport: payload.airport ?? current.airport,
      terminal: payload.terminal ?? current.terminal,
      gate: payload.gate ?? current.gate ?? null,
    })
    .where(eq(flightsTable.id, id))
    .run();

  return getFlightById(id);
};

Häufige Fehler

4 Fehler · zum Aufklappen klicken
Fehler: Pages Router-Syntax im App Router verwendet

Du schreibst export default function Page({ params }) {} im pages/-Ordner, obwohl du den App Router (app/) verwendest. Oder du verwendest getServerSideProps, das im App Router nicht existiert.

Fix: Stelle sicher, dass alle Seiten im src/app/-Ordner liegen. Im App Router gibt es kein getServerSideProps — stattdessen sind async Server Components der neue Ansatz (Lektion 3.3).

Fehler: <a href> statt <Link href>

Interne Links werden mit <a href="/departures"> geschrieben. Die Navigation funktioniert, aber die Seite wird vollständig neu geladen — kein SPA-Verhalten, kein Prefetching.

Fix: Immer import Link from 'next/link' für interne Navigation verwenden. <a> nur für externe URLs (z. B. https://...).

Fehler: Port-Konflikt 5173 vs. 3000

Du versuchst den Dev-Server zu starten, aber Port 3000 ist bereits belegt — oft weil der alte Vite-Dev-Server noch läuft (Port 5173) oder ein anderer Next.js-Prozess aktiv ist.

Fix: Beende alle laufenden Dev-Server (Ctrl+C) oder starte Next.js auf einem anderen Port: npm run dev -- -p 3001.

Fehler: <img> statt next/image

Du verwendest ein normales <img src="...">. Next.js zeigt eine ESLint-Warnung und das Bild wird nicht optimiert.

Fix: import Image from 'next/image' und <Image src="..." alt="..." width={200} height={100} />. Next.js konvertiert das Bild automatisch in WebP und lazy-loadt es.

Erstelle das flugboard-next-Projekt mit den empfohlenen Einstellungen und passe anschließend layout.tsx an.

  • Führe npx create-next-app@15 flugboard-next aus
  • Ersetze den Standard-Inhalt in layout.tsx durch das FlugBoard-Metadata-Objekt
  • Setze lang="de" im <html>-Tag
  • Starte den Dev-Server und überprüfe http://localhost:3000
Aufgabe 2 Startseite mit Links und DB-Vorschau

Erstelle eine ansprechende Startseite in src/app/page.tsx.

  • Kopiere src/types/flight.ts und richte src/lib/flights-db.ts ein
  • Zeige auf der Startseite 3 Flüge aus der Datenbank als Vorschau-Liste an
  • Füge zwei <Link>-Buttons für /departures und /arrivals ein
  • Exportiere ein passendes metadata-Objekt für die Seite
Aufgabe 3 Platzhalterseiten für alle Routen anlegen

Lege die Grundstruktur für alle Seiten des FlugBoards an.

  • Erstelle src/app/departures/page.tsx mit Liste der Abflüge aus listFlights('departure')
  • Erstelle src/app/arrivals/page.tsx mit Liste der Ankünfte
  • Erstelle src/app/flight/[id]/page.tsx als Platzhalter (Flug-ID anzeigen)
  • Navigiere zwischen allen Seiten und prüfe, ob die URLs korrekt sind
Aufgabe 4 — Bonus 404-Seite mit not-found.tsx

Next.js erlaubt eine benutzerdefinierte 404-Seite über die Datei not-found.tsx.

  • Erstelle src/app/not-found.tsx mit einer freundlichen Fehlermeldung
  • Füge einen <Link href="/">-Button zum Zurücknavigieren ein
  • Teste die Seite, indem du eine nicht existierende URL aufrufst (z. B. /foo)
  • Exportiere ein metadata-Objekt mit title: '404 – Seite nicht gefunden'

5 Fragen · zum Aufklappen klicken

Frage 1 Wie verhält sich Next.js zu React?

Erklärung: Man schreibt weiterhin React-Komponenten mit JSX, Props und Hooks. Next.js ergänzt, was React als reine UI-Bibliothek nicht bietet.

Frage 2 Was passiert beim Client-Side Rendering (CSR)?

Erklärung: So arbeitete unsere Vite-App in Teil 1. Nachteil: Suchmaschinen und langsame Verbindungen sehen zunächst nichts.

Frage 3 Für welche Seite passt Static Site Generation (SSG) am besten?

Erklärung: Bei SSG wird das HTML einmal beim Build erzeugt und als statische Datei ausgeliefert – sehr schnell, aber nicht aktuell bei häufigen Änderungen.

Frage 4 Was bedeutet ISR mit revalidate: 30?

Erklärung: Incremental Static Regeneration kombiniert die Geschwindigkeit statischer Seiten mit regelmäßiger Aktualisierung – für FlugBoard eine gute Wahl.

Frage 5 Warum eignet sich für das FlugBoard SSR oder ISR?

Erklärung: SSR ist immer aktuell, ISR mit revalidate: 30 ist höchstens 30 Sekunden alt, verursacht aber weniger Server-Last.
