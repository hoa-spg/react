Lektion 3.4 — Teil 3: Next.js

API Routes & Datenabruf

Next.js ca. 90 min

Lernziele

Nach dieser Lektion kannst du folgendes:

  • Route Handlers (API-Endpunkte) direkt im Next.js-Projekt erstellen
  • GET- und POST-Handler mit NextRequest und NextResponse implementieren
  • Query-Parameter aus der URL lesen und zur Filterung einsetzen
  • Dynamische Route Handler für GET und DELETE nach ID erstellen
  • Server Actions als Alternative zu API Routes für Formulare verwenden
  • Server Components direkt importieren statt über fetch abzurufen

1 — Was sind Route Handlers?

Route Handlers sind API-Endpunkte, die direkt im Next.js-Projekt leben. Anstatt ein separates Backend (wie unser Deno-Server aus Teil 1) zu betreiben, definierst du deine API-Logik in route.ts-Dateien innerhalb von src/app/api/.

Vorteile gegenüber einem separaten Backend

  • Geteilte Typen: Flight-Interface in API und Frontend identisch
  • Kein CORS: Gleiche Domain — kein Cross-Origin-Problem
  • Automatisches Deployment: API und Frontend werden zusammen deployt
  • Direkter Datenzugriff: Server Components können Daten direkt importieren

Route Handler vs. Server Action

Route Handlers (route.ts) eignen sich für REST-APIs, die auch von außen aufgerufen werden sollen — z. B. von einer mobilen App. Server Actions ('use server') sind einfacher für Formulare innerhalb der Next.js-App selbst. Beide Ansätze lernst du in dieser Lektion.

2 — GET-Endpunkt mit Query-Parametern

Der GET-Handler für /api/flights soll alle Flüge zurückgeben. Zusätzlich unterstützt er die Query-Parameter type (departure / arrival) und status zur Filterung.

src/app/api/flights/route.ts TypeScript 
import { NextRequest, NextResponse } from 'next/server';
import { insertFlight, listFlights } from '@/lib/flights-db';
import type { Flight } from '@/types/flight';

export async function GET(request: NextRequest) {
  const { searchParams } = request.nextUrl;
  const type   = searchParams.get('type');
  const status = searchParams.get('status');
  const query  = searchParams.get('q');

  let result: Flight[] = listFlights(type ?? undefined, status ?? undefined);

  // Volltextsuche in Flugnummer, Airport, Airline
  if (query) {
    const q = query.toLowerCase();
    result = result.filter(f =>
      f.flightNumber.toLowerCase().includes(q) ||
      f.airport.toLowerCase().includes(q) ||
      f.airline.toLowerCase().includes(q)
    );
  }

  // Sortierung: früheste Flüge zuerst
  result.sort((a, b) =>
    a.scheduledTime.localeCompare(b.scheduledTime)
  );

  return NextResponse.json(result, {
    headers: {
      'Cache-Control': 'public, s-maxage=30, stale-while-revalidate=60',
    },
  });
}

3 — POST-Handler mit Validierung

Der POST-Handler erzeugt einen neuen Flug. Er liest den Request-Body als JSON, validiert die Pflichtfelder und gibt bei Erfolg den neuen Flug mit HTTP 201 zurück.

src/app/api/flights/route.ts — POST hinzufügen TypeScript 
// ... (GET-Handler wie oben)

export async function POST(request: NextRequest) {
  let body: unknown;

  try {
    body = await request.json();
  } catch {
    return NextResponse.json(
      { error: 'Ungültiger JSON-Body' },
      { status: 400 }
    );
  }

  // Typprüfung und Validierung
  if (
    typeof body !== 'object' ||
    body === null ||
    !('flightNumber' in body) ||
    !('airline'      in body) ||
    !('airport'      in body) ||
    !('scheduledTime' in body) ||
    !('type'         in body)
  ) {
    return NextResponse.json(
      {
        error: 'Fehlende Pflichtfelder',
        required: ['flightNumber', 'airline', 'airport', 'scheduledTime', 'type'],
      },
      { status: 422 }
    );
  }

  const input = body as Record<string, unknown>;

  const newFlight = insertFlight({
    flightNumber: String(input.flightNumber),
    airline: String(input.airline),
    type: (input.type as Flight['type']) ?? 'departure',
    scheduledTime: String(input.scheduledTime),
    expectedTime: typeof input.expectedTime === 'string'
      ? input.expectedTime
      : undefined,
    airport: String(input.airport),
    terminal: typeof input.terminal === 'string' ? input.terminal : 'T1',
    gate: typeof input.gate === 'string' ? input.gate : undefined,
  });

  return NextResponse.json(newFlight, { status: 201 });
}

4 — Dynamischer Route Handler für [id]

Für Operationen auf einem einzelnen Flug erstellen wir einen Route Handler unter src/app/api/flights/[id]/route.ts. Auch hier gilt: in Next.js 15 ist params ein Promise!

src/app/api/flights/[id]/route.ts TypeScript 
import { NextRequest, NextResponse } from 'next/server';
import { getFlightById, removeFlight, updateFlight } from '@/lib/flights-db';

interface RouteContext {
  params: Promise<{ id: string }>;
}

// GET /api/flights/:id
export async function GET(
  _request: NextRequest,
  { params }: RouteContext
) {
  const { id } = await params;
  const flight = getFlightById(Number(id));

  if (!flight) {
    return NextResponse.json(
      { error: `Flug mit ID "${id}" nicht gefunden` },
      { status: 404 }
    );
  }

  return NextResponse.json(flight);
}

// DELETE /api/flights/:id
export async function DELETE(
  _request: NextRequest,
  { params }: RouteContext
) {
  const { id } = await params;
  const deleted = removeFlight(Number(id));

  if (!deleted) {
    return NextResponse.json(
      { error: `Flug mit ID "${id}" nicht gefunden` },
      { status: 404 }
    );
  }

  return NextResponse.json({
    message: `Flug ${deleted.flightNumber} wurde gelöscht`,
    deleted,
  });
}

// PATCH /api/flights/:id – Status aktualisieren
export async function PATCH(
  request: NextRequest,
  { params }: RouteContext
) {
  const { id }  = await params;
  const body    = await request.json() as { status?: string };
  const flight  = getFlightById(Number(id));

  if (!flight) {
    return NextResponse.json(
      { error: 'Nicht gefunden' },
      { status: 404 }
    );
  }

  const updated = updateFlight(Number(id), { status: body.status });
  return NextResponse.json(updated);
}

5 — Server Actions für Formulare

Server Actions sind eine Alternative zu Route Handlers für Formular-Submissions. Sie sind einfacher einzusetzen, weil kein fetch nötig ist — das Formular ruft die Funktion direkt auf.

src/actions/flight-actions.ts TypeScript 
'use server';

import { revalidatePath } from 'next/cache';
import { insertFlight, removeFlight } from '@/lib/flights-db';
import type { Flight } from '@/types/flight';

const FLIGHT_NUMBER_PATTERN = /^[A-Z]{2}\d{3,4}$/;

export async function addFlight(formData: FormData) {
  // FormData-Werte auslesen
  const flightNumber  = String(formData.get('flightNumber') ?? '').trim().toUpperCase();
  const airline       = formData.get('airline') as string;
  const airport       = formData.get('airport') as string;
  const scheduledTime = formData.get('scheduledTime') as string;
  const terminal      = formData.get('terminal') as string | null;
  const gate          = formData.get('gate') as string | null;

  // Einfache Validierung
  if (!flightNumber || !airline || !airport || !scheduledTime) {
    throw new Error('Bitte alle Pflichtfelder ausfüllen.');
  }

  if (!FLIGHT_NUMBER_PATTERN.test(flightNumber)) {
    throw new Error('Flugnummer muss genau 2 Buchstaben und 3 oder 4 Ziffern enthalten (z.B. OS123).');
  }

  const newFlight: Omit<Flight, 'id' | 'status'> = {
    flightNumber,
    airline,
    type:          'departure',
    scheduledTime,
    airport,
    terminal:      terminal ?? 'T1',
    gate:          gate ?? undefined,
  };

  insertFlight(newFlight);

  // Seite neu validieren – zeigt sofort den neuen Flug
  revalidatePath('/departures');
}

export async function deleteFlight(id: string) {
  removeFlight(Number(id));
  revalidatePath('/departures');
  revalidatePath('/arrivals');
}

✓
revalidatePath — Cache invalidieren

Nach einer mütierenden Operation (POST, DELETE, PATCH) rufst du revalidatePath('/departures') auf, um den Cache für diese Route zu löschen. Beim nächsten Seitenaufruf werden die Daten frisch vom Server geladen. Ohne revalidatePath würde die Seite noch die alten gecachten Daten zeigen.

6 — Server Components importieren statt fetchen

Das Schönste am Next.js-Ansatz: In Server Components kannst du Daten direkt importieren, ohne einen HTTP-Request zu machen. Das ist nicht nur einfacher, sondern auch deutlich schneller — kein Netzwerk-Overhead.

Direkter Import vs. fetch — Vergleich TypeScript 
// ✅ BESSER: Direkter Daten-Import in Server Components
import { listFlights } from '@/lib/flights-db';

export default async function DeparturePage() {
  const departures = listFlights('departure');
  return <FlightTable flights={departures} />;
}

// ⚠️ Nur nötig für Client Components oder externe APIs
export default async function DeparturePage() {
  // Nur wenn Daten von einer externen Quelle kommen:
  const res = await fetch('https://api.flughafen.de/flights');
  const flights = await res.json();
  return <FlightTable flights={flights} />;
}

Wann welchen Ansatz verwenden?

Datenquelle Empfohlener Ansatz Begründung
Seed-Daten in SQLite Direkter Import Einfachst, kein Overhead
Eigene Route Handler im selben Projekt Direkter Import (bevorzugt) Kein nötiger HTTP-Roundtrip
Externe REST-APIs fetch mit Cache-Option Kein direkter Zugriff möglich
Datenbank (Prisma, Drizzle) Direkte DB-Abfrage in Server Component Kein API-Layer nötig
Client Components fetch('/api/...') Kein direkter Serverzugriff möglich

Projektschritt

Projektschritt 3.4

Next.js API Routes auf Drizzle + SQLite umstellen

In diesem Projektschritt bleibt die Datenbank das Zentrum der Anwendung. Wir verlagern den Datenzugriff in Next.js Route Handlers, aber arbeiten weiterhin mit Drizzle + SQLite.

  1. GET + POST Route Handler: Erstelle src/app/api/flights/route.ts mit GET (Query-Params) und POST (mit Validierung und 201-Antwort).
  2. Dynamischer Handler: Erstelle src/app/api/flights/[id]/route.ts mit GET, DELETE und PATCH.
  3. Server Components anpassen: Ersetze in page.tsx alle In-Memory-Zugriffe durch DB-Funktionen aus @/lib/flights-db.
  4. Client Components anpassen: Ersetze in Client Components alle Fetch-URLs durch /api/flights (relativ, kein Hostname nötig).
  5. Server Action: Erstelle src/actions/flight-actions.ts mit addFlight und deleteFlight. Baue ein AddFlightForm.tsx ein.
  6. Datenbankdatei prüfen: Verifiziere, dass neue Flüge in flugboard.sqlite persistent gespeichert werden.

Häufige Fehler

Fehler: fetch mit relativem Pfad in Server Components schlägt fehl

Du schreibst fetch('/api/flights') in einer Server Component. Im Browser funktioniert das — auf dem Server gibt es keinen Hostname, daher schlägt der Request fehl: „TypeError: Failed to parse URL from /api/flights“.

Fix: Entweder den absoluten Pfad verwenden (fetch('http://localhost:3000/api/flights')) oder — noch besser — Daten direkt importieren: import {'{ listFlights }'} from '@/lib/flights-db'. Letzteres ist einfacher und performanter.

Fehler: Datenbankdatei wird nicht gefunden

Der Handler startet, aber alle Requests schlagen mit 500 fehl, weil der Pfad zur SQLite-Datei nicht stimmt oder Schreibrechte fehlen.

Fix: Verwende einen stabilen Dateipfad und initialisiere die Tabelle beim Start. Für echtes Hosting ohne lokales Filesystem auf managed DB wechseln.

Fehler: Route Handler ohne Großbuchstaben-Export

Du schreibst export async function get() statt export async function GET(). Next.js erkennt den Handler nicht und gibt eine 405-Antwort (Method Not Allowed) zurück.

Fix: HTTP-Methoden in Route Handlers werden als Großbuchstaben exportiert: GET, POST, PUT, PATCH, DELETE. Kleinschreibung wird ignoriert.

Fehler: params nicht awaited im Route Handler

Du verwendest const { id } = params im Route Handler ohne await. In Next.js 15 ist das ein Fehler — id ist dann ein unaufgelöstes Promise-Objekt, und dein Datenzugriff (z. B. getFlightById()) trifft nie die richtige ID.

Fix: const { id } = await params; — genau wie in Page Components. Der Route Handler muss ebenfalls async sein.
