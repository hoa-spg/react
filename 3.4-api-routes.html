Lektion 3.4 — Teil 3: Next.js

API Routes & Datenabruf

Next.js ca. 90 min

Lernziele

Nach dieser Lektion kannst du folgendes:

  • Route Handlers (API-Endpunkte) direkt im Next.js-Projekt erstellen
  • GET- und POST-Handler mit NextRequest und NextResponse implementieren
  • Query-Parameter aus der URL lesen und zur Filterung einsetzen
  • Dynamische Route Handler für GET, PATCH und DELETE nach ID erstellen
  • Server Actions mit revalidatePath für Formulare verwenden
  • Entscheiden, wann eine Seite die Datenbank direkt nutzt und wann fetch nötig ist

1 — Was sind Route Handlers?

Route Handlers sind API-Endpunkte, die direkt im Next.js-Projekt leben. Anstatt ein separates Backend (wie unseren Deno-Server aus Teil 2) zu betreiben, definierst du die API in Dateien namens route.ts innerhalb von src/app/api/. Jede exportierte Funktion heißt wie eine HTTP-Methode (GET, POST, PATCH, DELETE) und beantwortet genau diese Requests.

Vorteile gegenüber einem separaten Backend

  • Geteilte Typen: Flight-Interface in API und Frontend identisch
  • Kein CORS: Gleiche Domain — kein Cross-Origin-Problem
  • Gemeinsames Deployment: API und Frontend werden zusammen deployt
  • Gemeinsame DB-Schicht: API und Seiten verwenden dieselben Funktionen aus @/lib/flights-db

Route Handler Dateistruktur

API-Struktur für FlugBoard Bash 
src/app/api/
└── flights/
    ├── route.ts           → GET    /api/flights
    │                      → POST   /api/flights
    └── [id]/
        └── route.ts       → GET    /api/flights/1
                           → PATCH  /api/flights/1
                           → DELETE /api/flights/1
ℹ
Wer braucht die API?

Unsere Board-Seiten nicht: Sie sind Server Components und lesen seit Lektion 3.3 direkt mit listFlights aus der Datenbank. Die API ist für Aufrufer gedacht, die nicht auf dem Server laufen — curl, Client Components im Browser oder später eine mobile App (Teil 4). Für Formulare innerhalb der App gibt es mit Server Actions (Abschnitt 5) einen noch einfacheren Weg.

2 — GET-Endpunkt mit Query-Parametern

Der GET-Handler für /api/flights gibt alle Flüge zurück. Mit den Query-Parametern type (departure / arrival) und status lässt sich die Liste filtern.

src/app/api/flights/route.ts TypeScript 
import { NextRequest, NextResponse } from 'next/server';
import { insertFlight, listFlights } from '@/lib/flights-db';

// GET /api/flights?type=departure&status=delayed
export async function GET(request: NextRequest) {
  const { searchParams } = request.nextUrl;
  const type = searchParams.get('type'); // null, wenn nicht angegeben
  const status = searchParams.get('status');

  const flights = listFlights(type ?? undefined, status ?? undefined);
  return NextResponse.json(flights);
}
  • NextRequest ist der eingehende Request. request.nextUrl.searchParams enthält die Query-Parameter; get('type') liefert den Wert oder null.
  • listFlights erwartet undefined für „kein Filter“ — deshalb type ?? undefined.
  • NextResponse.json(daten) erzeugt eine JSON-Antwort mit Status 200.

Endpunkt testen

GET-Requests kannst du direkt im Browser aufrufen (http://localhost:3000/api/flights) oder mit curl:

Terminal — curl Tests Bash

# Nur Abflüge

# Verspätete Abflüge

3 — POST-Handler mit Validierung

Der POST-Handler in derselben Datei erzeugt einen neuen Flug. Er liest den Request-Body als JSON, prüft die Pflichtfelder und gibt bei Erfolg den neuen Flug mit HTTP 201 (Created) zurück.

src/app/api/flights/route.ts — POST hinzufügen TypeScript 
// ... (Imports und GET-Handler wie oben)

// POST /api/flights – neuen Flug anlegen
export async function POST(request: NextRequest) {
  try {
    const body = await request.json();
    if (!body.flightNumber || !body.airline || !body.scheduledTime || !body.airport) {
      return NextResponse.json(
        { error: 'Pflichtfelder fehlen: flightNumber, airline, scheduledTime, airport' },
        { status: 400 },
      );
    }
    const newFlight = insertFlight({
      flightNumber: body.flightNumber,
      airline: body.airline,
      type: body.type ?? 'departure',
      scheduledTime: body.scheduledTime,
      expectedTime: body.expectedTime,
      airport: body.airport,
      terminal: body.terminal ?? 'T1',
      gate: body.gate,
    });
    return NextResponse.json(newFlight, { status: 201 });
  } catch {
    // request.json() wirft, wenn der Body kein gültiges JSON ist
    return NextResponse.json({ error: 'Ungültiger Request-Body' }, { status: 400 });
  }
}
  • await request.json() liest den Body. Ist er kein gültiges JSON, wirft die Methode einen Fehler — den fängt catch ab und antwortet mit 400.
  • Fehlt ein Pflichtfeld, antwortet der Handler ebenfalls mit 400 (Bad Request) und einer Fehlermeldung.
  • Das zweite Argument von NextResponse.json setzt den Statuscode: { status: 201 }.
  • insertFlight aus Lektion 2.8 speichert den Flug in SQLite und vergibt ID und Status.

Warum fehlt der Flug noch im Board?

Die Abflugseite wird wegen export const revalidate = 30 (Lektion 3.3) höchstens alle 30 Sekunden neu erzeugt. Ein Flug, der über die API angelegt wird, erscheint also mit bis zu 30 Sekunden Verzögerung. Wie man die Seite sofort aktualisiert, zeigt Abschnitt 5.

4 — Dynamischer Route Handler für [id]

Für Operationen auf einem einzelnen Flug kommt ein Ordner [id] dazu — genau wie bei der dynamischen Detailseite aus Lektion 3.2. Die ID steckt im zweiten Parameter des Handlers, und auch hier ist params in Next.js 15 ein Promise.

src/app/api/flights/[id]/route.ts TypeScript 
import { NextRequest, NextResponse } from 'next/server';
import { getFlightById, removeFlight, updateFlight } from '@/lib/flights-db';

interface RouteParams {
  params: Promise<{ id: string }>;
}

// GET /api/flights/1
export async function GET(_request: NextRequest, { params }: RouteParams) {
  const { id } = await params;
  const flight = getFlightById(Number(id));
  if (!flight) {
    return NextResponse.json({ error: `Flug ${id} nicht gefunden` }, { status: 404 });
  }
  return NextResponse.json(flight);
}

// DELETE /api/flights/1
export async function DELETE(_request: NextRequest, { params }: RouteParams) {
  const { id } = await params;
  const deleted = removeFlight(Number(id));
  if (!deleted) {
    return NextResponse.json({ error: `Flug ${id} nicht gefunden` }, { status: 404 });
  }
  return NextResponse.json(deleted);
}

// PATCH /api/flights/1 – nur die mitgeschickten Felder ändern
export async function PATCH(request: NextRequest, { params }: RouteParams) {
  const { id } = await params;
  const body = await request.json();
  const updated = updateFlight(Number(id), body);
  if (!updated) {
    return NextResponse.json({ error: `Flug ${id} nicht gefunden` }, { status: 404 });
  }
  return NextResponse.json(updated);
}
  • Der Unterstrich in _request zeigt: Der Parameter wird nicht verwendet, muss aber an erster Stelle stehen.
  • PATCH gibt den Body an updateFlight weiter — geändert werden nur die Felder, die im Body stehen.
  • Gibt es den Flug nicht, antworten alle drei Handler mit 404.
Terminal — GET, PATCH und DELETE testen Bash 
# Einen Flug abrufen
curl http://localhost:3000/api/flights/1

# Status aktualisieren
curl -X PATCH http://localhost:3000/api/flights/2 \
  -H "Content-Type: application/json" \
  -d '{"status": "boarding"}'

# Einen Flug löschen
curl -X DELETE http://localhost:3000/api/flights/1

5 — Server Actions für Formulare

Eine Server Action ist eine Funktion, die auf dem Server läuft, aber direkt von einem Formular aufgerufen wird — ganz ohne fetch und ohne eigenen API-Endpunkt. Neu sind dabei drei Dinge:

  • 'use server' am Dateianfang macht alle exportierten Funktionen der Datei zu Server Actions.
  • Die Action bekommt die Formularfelder als FormData. formData.get('airline') liefert den Wert des Feldes mit name="airline".
  • revalidatePath('/departures') verwirft die zwischengespeicherte Abflugseite. Beim nächsten Aufruf wird sie neu erzeugt — der neue Flug ist sofort sichtbar, statt erst nach bis zu 30 Sekunden.
src/actions/flight-actions.ts TypeScript 
'use server';

import { revalidatePath } from 'next/cache';
import { insertFlight } from '@/lib/flights-db';

export async function addFlight(formData: FormData) {
  // Formularfelder über ihr name-Attribut auslesen
  const flightNumber = String(formData.get('flightNumber')).trim().toUpperCase();
  const airline = String(formData.get('airline'));
  const airport = String(formData.get('airport'));
  const scheduledTime = String(formData.get('scheduledTime'));
  const gate = String(formData.get('gate'));

  // Die Prüfung im Browser lässt sich umgehen – deshalb am Server noch einmal prüfen
  if (!/^[A-Z]{2}\d{3,4}$/.test(flightNumber)) {
    throw new Error('Flugnummer: 2 Buchstaben und 3–4 Ziffern, z. B. OS123');
  }

  insertFlight({
    flightNumber,
    airline,
    type: 'departure',
    scheduledTime,
    airport,
    terminal: 'T1',
    gate: gate || undefined,
  });

  // Abflugseite beim nächsten Aufruf neu erzeugen – der neue Flug erscheint sofort
  revalidatePath('/departures');
}

Wirft die Action einen Fehler, zeigt Next.js die error.tsx der Abflugseite an (Lektion 3.2).

Server Action in einem Formular einsetzen

Im Formular steht die Action im Attribut action. Beim Absenden schickt der Browser die Felder an den Server, und Next.js ruft addFlight auf. Das Formular selbst braucht dazu keinen State und kein 'use client'.

src/components/AddFlightForm.tsx TypeScript 
import { addFlight } from '@/actions/flight-actions';

// Kein 'use client' nötig: Das Formular ist eine Server Component
export default function AddFlightForm() {
  return (
    <form action={addFlight} className="add-flight-form">
      <div className="form-group">
        <label htmlFor="flightNumber">Flugnummer *</label>
        <input
          id="flightNumber"
          name="flightNumber"
          placeholder="z.B. OS123"
          pattern="[A-Za-z]{2}\d{3,4}"
          title="2 Buchstaben und 3 oder 4 Ziffern, z.B. OS123"
          required
        />
      </div>
      <div className="form-group">
        <label htmlFor="airline">Airline *</label>
        <input id="airline" name="airline" placeholder="z.B. Lufthansa" required />
      </div>
      <div className="form-group">
        <label htmlFor="airport">Ziel *</label>
        <input id="airport" name="airport" placeholder="z.B. Paris (CDG)" required />
      </div>
      <div className="form-group">
        <label htmlFor="scheduledTime">Abflugzeit *</label>
        <input id="scheduledTime" name="scheduledTime" type="time" required />
      </div>

Das Formular kommt auf die Abflugseite, über die Suche:

src/app/(board)/departures/page.tsx TypeScript 
import type { Metadata } from 'next';
import { listFlights } from '@/lib/flights-db';
import SearchWrapper from '@/components/SearchWrapper';
import AddFlightForm from '@/components/AddFlightForm';

export const metadata: Metadata = {
  title: 'Abflüge',
};

// Seite höchstens alle 30 Sekunden neu erzeugen (ISR).
// Ohne diese Zeile würde Next.js sie nur einmal beim Build rendern.
export const revalidate = 30;

export default function DeparturePage() {
  // Server Component: liest direkt aus der Datenbank – kein fetch, kein useEffect
  const departures = [...listFlights('departure')].sort((a, b) =>
    a.scheduledTime.localeCompare(b.scheduledTime),
  );

  return (
    <div>
      {/* Überschrift wird auf dem Server gerendert */}
      <h1 className="board-page-title">
        Abflüge ({departures.length})
      </h1>
      {/* Formular schickt die Daten an die Server Action addFlight */}
      <AddFlightForm />
      {/* Server Component übergibt serialisierbare Daten an die Client Component */}
      <SearchWrapper flights={departures} />
    </div>
  );
}

6 — Welcher Datenweg wofür?

Mit Route Handlers und Server Actions gibt es jetzt mehrere Wege, an Daten zu kommen. Faustregel: Was auf dem Server läuft, ruft die Datenbank-Funktionen direkt auf — ein HTTP-Request an die eigene API wäre nur ein Umweg.

Situation Empfohlener Weg Im FlugBoard
Server Component liest eigene Daten DB-Funktion direkt aufrufen listFlights('departure') in den Board-Seiten
Formular in der eigenen App Server Action addFlight in AddFlightForm
Client Component oder externes Programm fetch('/api/...') bzw. HTTP-Request curl, später die mobile App
Daten eines fremden Servers fetch auf dessen URL –

Projektschritt

Projektschritt 3.4

REST-API und Formular „Flug hinzufügen“

Die Seiten aus Lektion 3.3 bleiben unverändert. Dazu kommen eine REST-API für Aufrufer von außen und ein Formular auf der Abflugseite. Beides nutzt die DB-Schicht aus @/lib/flights-db.

  1. GET + POST: Erstelle src/app/api/flights/route.ts (Abschnitte 2 und 3) und teste beide Methoden mit curl.
  2. Dynamischer Handler: Erstelle src/app/api/flights/[id]/route.ts mit GET, PATCH und DELETE (Abschnitt 4).
  3. Server Action: Erstelle src/actions/flight-actions.ts mit addFlight (Abschnitt 5).
  4. Formular: Erstelle src/components/AddFlightForm.tsx, binde es in departures/page.tsx ein und ergänze die Styles in globals.css.
  5. Prüfen: Ein Flug aus dem Formular erscheint sofort in der Abflugliste. Nach einem Neustart des Servers ist er immer noch da — er steht in flugboard.sqlite.

Häufige Fehler

Fehler: fetch mit relativem Pfad in Server Components schlägt fehl

Du schreibst fetch('/api/flights') in einer Server Component. Im Browser funktioniert das — auf dem Server gibt es keinen Hostname, daher schlägt der Request fehl: „TypeError: Failed to parse URL from /api/flights“.

Fix: Entweder den absoluten Pfad verwenden (fetch('http://localhost:3000/api/flights')) oder — noch besser — Daten direkt importieren: import { listFlights } from '@/lib/flights-db'. Letzteres ist einfacher und performanter.

Fehler: Datenbankdatei wird nicht gefunden

Der Handler startet, aber alle Requests schlagen mit 500 fehl, weil der Pfad zur SQLite-Datei nicht stimmt oder Schreibrechte fehlen.

Fix: Verwende einen stabilen Dateipfad und initialisiere die Tabelle beim Start. Für echtes Hosting ohne lokales Filesystem auf managed DB wechseln.

Fehler: Route Handler ohne Großbuchstaben-Export

Du schreibst export async function get() statt export async function GET(). Next.js erkennt den Handler nicht und gibt eine 405-Antwort (Method Not Allowed) zurück.

Fix: HTTP-Methoden in Route Handlers werden als Großbuchstaben exportiert: GET, POST, PUT, PATCH, DELETE. Kleinschreibung wird ignoriert.

Fehler: params nicht awaited im Route Handler

Du verwendest const { id } = params im Route Handler ohne await. In Next.js 15 ist das ein Fehler — id ist dann ein unaufgelöstes Promise-Objekt, und dein Datenzugriff (z. B. getFlightById()) trifft nie die richtige ID.

Fix: const { id } = await params; — genau wie in Page Components. Der Route Handler muss ebenfalls async sein.

Aufgaben

Aufgabe 1 Suche über die API

Erweitere den GET-Handler um den Query-Parameter q.

  • q filtert die Flüge nach Flugnummer, Airline oder Airport (Groß-/Kleinschreibung egal)
  • Ohne q verhält sich der Handler wie bisher
  • Teste mit curl "http://localhost:3000/api/flights?q=lh" und kombiniert mit type
Aufgabe 2 Strengere Validierung beim POST

Der POST-Handler prüft bisher nur, ob die Pflichtfelder vorhanden sind.

  • type darf nur departure oder arrival sein
  • scheduledTime muss das Format HH:MM haben (z. B. mit /^\d{2}:\d{2}$/)
  • Bei ungültigen Werten antwortet der Handler mit 400 und einer passenden Fehlermeldung
  • Teste gültige und ungültige Requests mit curl und prüfe die Statuscodes
Aufgabe 3 Löschen-Button mit fetch

Verbinde den DELETE-Handler mit der Detailseite.

  • Erstelle eine Client Component DeleteFlightButton, die die Flug-ID als Prop bekommt
  • Beim Klick ruft sie fetch(`/api/flights/${id}`, { method: 'DELETE' }) auf
  • Danach führt sie mit useRouter().push('/departures') zurück zur Abflugliste
  • Binde den Button auf src/app/flight/[id]/page.tsx ein
Aufgabe 4 — Bonus Löschen als Server Action

Ersetze den fetch-Aufruf aus Aufgabe 3 durch eine Server Action.

  • Ergänze in flight-actions.ts eine Action deleteFlight(formData: FormData), die die ID aus einem versteckten Feld liest
  • Sie löscht den Flug mit removeFlight und ruft revalidatePath für /departures und /arrivals auf
  • Zum Schluss leitet sie mit redirect('/departures') aus next/navigation weiter
