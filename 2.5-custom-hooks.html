Custom Hooks

React ca. 90 min

Lernziele

  • Verstehen, was Custom Hooks sind und wann man sie einsetzt
  • Eigene Hooks mit dem use-Prefix erstellen
  • Logik aus Komponenten in wiederverwendbare Hooks extrahieren
  • useFlights-Hook für den Datenabruf bauen
  • useLocalStorage-Hook für persistente Einstellungen bauen
  • Die Hook-Regeln auf Custom Hooks anwenden

1. Was sind Custom Hooks?

Custom Hooks sind gewöhnliche JavaScript-Funktionen, deren Name mit use beginnt und die andere Hooks aufrufen dürfen. Sie erlauben es, zustandsbehaftete Logik aus einer Komponente herauszulösen und in eine wiederverwendbare Funktion zu verpacken.

Wichtig: Die Logik eines Custom Hooks läuft innerhalb der Komponente, die ihn aufruft. Jede Komponente, die denselben Hook aufruft, hat ihre eigene, separate Instanz des States. Custom Hooks teilen Logik – nicht State.

Custom Hooks einsetzen, wenn:

  • Dieselbe Logik in mehreren Komponenten dupliziert wird (DRY-Prinzip)
  • Komplexe Effekte mit State zusammengehören (z.B. Datenabruf, Event-Listener)
  • Eine Komponente unlesbar wird, weil Implementierungsdetails den eigentlichen Zweck verbergen
ℹ
Vorher & Nachher

Vorher: App.tsx hat 80 Zeilen, davon 50 für Fetch-Logik, Polling-Interval, AbortController, Error-Handling und Loading-State.
Nachher: App.tsx hat 30 Zeilen. Die Fetch-Logik lebt in useFlights.ts – isoliert, testbar, wiederverwendbar.

2. Einfacher Custom Hook: useWindowSize

Beginnen wir mit einem überschaubaren Beispiel: ein Hook, der die aktuelle Fenstergröße zurückgibt und sich bei resize-Events automatisch aktualisiert. Dieses Muster – Event-Listener registrieren und bei Cleanup abmelden – taucht in der Praxis sehr häufig auf.

src/hooks/useWindowSize.ts TypeScript 
import { useState, useEffect } from 'react';

interface WindowSize {
  width: number;
  height: number;
}

/**
 * Gibt die aktuelle Fenstergröße zurück.
 * Aktualisiert sich automatisch bei Resize-Events.
 *
 * @returns {WindowSize} Aktuelle Breite und Höhe des Browser-Fensters
 */
const useWindowSize = (): WindowSize => {
  const [size, setSize] = useState<WindowSize>({
    width: window.innerWidth,
    height: window.innerHeight,
  });

  useEffect(() => {
    const handleResize = () => {
      setSize({
        width: window.innerWidth,
        height: window.innerHeight,
      });
    };

    // Event-Listener registrieren
    window.addEventListener('resize', handleResize);

    // Cleanup-Funktion: Listener beim Unmount abmelden
    return () => window.removeEventListener('resize', handleResize);
  }, []); // Leeres Array: Effekt nur einmal beim Mount ausführen

  return size;
};

export default useWindowSize;

Verwendung in einer Komponente – denkbar einfach:

Verwendung in einer Komponente TypeScript 
import useWindowSize from '../hooks/useWindowSize';

const FlightBoard = ({ flights }: FlightBoardProps) => {
  const { width } = useWindowSize();

  // Kompakte Ansicht auf kleinen Bildschirmen
  const isCompact = width < 768;

  return (
    <section>
      {isCompact ? (
        <FlightListMobile flights={flights} />
      ) : (
        <FlightTable flights={flights} />
      )}
    </section>
  );
};
💡
Cleanup ist Pflicht

Ohne die Cleanup-Funktion (return () => removeEventListener(...)) bleibt der Event-Listener aktiv, auch nachdem die Komponente aus dem DOM entfernt wurde. Das führt zu Memory Leaks und dem Fehler „Can't perform a React state update on an unmounted component“. Immer aufräumen!

3. useFlights – Datenabruf-Hook

In Lektion 2.2 haben wir die Fetch-Logik direkt in App.tsx geschrieben. Mit zunehmendem Umfang (Polling, AbortController, Fehlerbehandlung, manuelles Refetch) wird diese Logik unhandlich. Wir extrahieren sie in einen dedizierten Hook.

src/hooks/useFlights.ts TypeScript 
import { useState, useEffect } from 'react';
import { Flight } from '../types/flight';

interface UseFlightsReturn {
  flights: Flight[];
  isLoading: boolean;
  error: string | null;
  refetch: () => void;
  lastUpdated: Date | null;
}

const API_URL = 'http://localhost:8000';

/**
 * Lädt alle Flüge vom Backend und aktualisiert sie alle 30 Sekunden.
 * Gibt Ladevorgangsstatus, Fehler und eine manuelle Aktualisierungsfunktion zurück.
 */
const useFlights = (): UseFlightsReturn => {
  const [flights, setFlights]         = useState<Flight[]>([]);
  const [isLoading, setIsLoading]     = useState<boolean>(true);
  const [error, setError]             = useState<string | null>(null);
  const [lastUpdated, setLastUpdated] = useState<Date | null>(null);

  // Trick für manuelles Refetch: refreshKey ändern triggert den Effekt erneut
  const [refreshKey, setRefreshKey]   = useState(0);

  useEffect(() => {
    // AbortController: bricht den laufenden Fetch beim Cleanup ab
    const controller = new AbortController();

    const fetchData = async () => {
      try {
        setIsLoading(true);
        setError(null);

        const response = await fetch(`${API_URL}/api/flights`, {
          signal: controller.signal,
        });

        if (!response.ok) {
          throw new Error(`HTTP-Fehler: ${response.status} ${response.statusText}`);
        }

        const data: Flight[] = await response.json();
        setFlights(data);
        setLastUpdated(new Date());
      } catch (err) {
        // AbortError ignorieren: Das ist kein echter Fehler, sondern unser Cleanup
        if (err instanceof Error && err.name === 'AbortError') return;
        setError(err instanceof Error ? err.message : 'Unbekannter Fehler');
      } finally {
        setIsLoading(false);
      }
    };

    // Sofortiger erster Fetch
    fetchData();

    // Automatische Aktualisierung alle 30 Sekunden
    const intervalId = setInterval(fetchData, 30_000);

    return () => {
      controller.abort();        // Laufenden Fetch abbrechen
      clearInterval(intervalId); // Polling stoppen
    };
  }, [refreshKey]); // refreshKey als Abhängigkeit: Änderung triggert Effekt

  const refetch = () => setRefreshKey(k => k + 1);

  return { flights, isLoading, error, refetch, lastUpdated };
};

export default useFlights;

Das Ergebnis in App.tsx spricht für sich:

src/App.tsx (nach Extraktion) TypeScript 
import useFlights from './hooks/useFlights';

function App() {
  // Vorher: ~40 Zeilen useState, useEffect, fetch-Logik
  // Nachher: eine Zeile
  const { flights, isLoading, error, refetch, lastUpdated } = useFlights();

  if (error)     return <ErrorMessage message={error} onRetry={refetch} />;

  return (
    <div className="app">
      <AirportHeader lastUpdated={lastUpdated} onRefresh={refetch} />
      {isLoading ? (
        <BoardLoading />
      ) : (
        <>
          <FlightBoard flights={flights.filter(f => f.type === 'departure')} />
          <FlightBoard flights={flights.filter(f => f.type === 'arrival')}   />
        </>
      )}
    </div>
  );
}
ℹ
Der refreshKey-Trick

setRefreshKey(k => k + 1) ändert eine Zahl in der useEffect-Abhängigkeitsliste. Da React änderungen in der Abhängigkeitsliste erkennt, wird der Effekt neu ausgeführt. Der Trick funktioniert immer, wenn man einen Effekt manuell neu triggern möchte, ohne dessen eigentliche Abhängigkeiten zu verändern.

4. useLocalStorage – Persistenz-Hook

Ein weiterer klassischer Custom Hook ist useLocalStorage: Er verhält sich wie useState, speichert den Wert aber zusätzlich im localStorage des Browsers. So bleiben Einstellungen auch nach einem Seitenneuladen erhalten.

Durch den Einsatz von TypeScript-Generics (<T>) ist der Hook typagnostisch und kann für beliebige serialisierbare Werte verwendet werden.

src/hooks/useLocalStorage.ts TypeScript 
import { useState } from 'react';

/**
 * useState-Ersatz mit localStorage-Persistenz.
 * Der Wert wird unter dem angegebenen Key gespeichert und
 * bleibt auch nach einem Seitenneuladen erhalten.
 *
 * @template T - Typ des gespeicherten Werts (muss JSON-serialisierbar sein)
 * @param key - Der localStorage-Key
 * @param initialValue - Standardwert, falls kein gespeicherter Wert vorhanden ist
 * @returns [gespeicherter Wert, Setter-Funktion] - wie useState
 */
const useLocalStorage = <T>(
  key: string,
  initialValue: T
): [T, (value: T) => void] => {

  const [storedValue, setStoredValue] = useState<T>(() => {
    try {
      const item = localStorage.getItem(key);
      // Gespeicherten Wert parsen, oder initialValue zurückgeben
      return item ? (JSON.parse(item) as T) : initialValue;
    } catch {
      // Bei Parse-Fehlern (z.B. korrumpierte Daten) initialValue verwenden
      console.warn(`useLocalStorage: Fehler beim Lesen von "${key}"`);
      return initialValue;
    }
  });

  const setValue = (value: T) => {
    try {
      setStoredValue(value);
      localStorage.setItem(key, JSON.stringify(value));
    } catch (error) {
      // localStorage kann voll sein (QuotaExceededError)
      console.error(`useLocalStorage: Fehler beim Schreiben von "${key}":`, error);
    }
  };

  return [storedValue, setValue];
};

export default useLocalStorage;

Verwendung – als direkter Ersatz für useState:

Verwendungsbeispiele TypeScript 
import useLocalStorage from '../hooks/useLocalStorage';

// Theme persistieren
const [theme, setTheme] = useLocalStorage<'dark' | 'light'>('theme', 'dark');

// Sprache persistieren
const [lang, setLang] = useLocalStorage<'de' | 'en'>('language', 'de');

// Filter-Einstellungen persistieren (komplexes Objekt)
const [filters, setFilters] = useLocalStorage<FilterState>(
  'flugboard-filters',
  DEFAULT_FILTERS
);

// Identischer Verwendungsstil wie useState:
setTheme('light');            // einfacher Wert
setFilters(prev => ({        // ABER: Vorsicht! Kein Setter-Callback wie bei useState
  ...prev,
  searchQuery: 'LH',
}));
⚠
Kein Setter-Callback!

Unser useLocalStorage-Hook akzeptiert im Setter keinen Callback wie setCount(prev => prev + 1). Um ein Objekt zu aktualisieren, muss der aktuelle Wert zuerst gelesen werden: setFilters({ ...filters, searchQuery: 'LH' }). Für eine robuste Implementierung könnte der Setter auf Callbacks erweitert werden (value: T | ((prev: T) => T)).

5. Hook-Regeln (Wiederholung & Custom Hooks)

Die zwei grundlegenden Regeln für Hooks gelten genauso für Custom Hooks:

✖
Regel 1: Hooks nur auf oberster Ebene aufrufen

Niemals Hooks in Schleifen, Bedingungen oder verschachtelten Funktionen aufrufen. React verlässt sich auf die Reihenfolge der Hook-Aufrufe, um den State korrekt zuzuordnen. Eine veränderliche Reihenfolge (durch if/for) führt zu inkonsistentem State.

✖
Regel 2: Hooks nur in React-Funktionskomponenten oder Custom Hooks aufrufen

Hooks dürfen nicht in gewöhnlichen JavaScript-Funktionen, Klassen oder asynchronen Funktionen aufgerufen werden.

Richtig vs. Falsch TypeScript 
// ✅ RICHTIG: Hook auf oberster Ebene
const useFlightFilters = () => {
  const [query, setQuery] = useLocalStorage('query', '');  // OK
  return { query, setQuery };
};

// ❌ FALSCH: Hook in Bedingung
const useBadHook = (enabled: boolean) => {
  if (enabled) {
    const [data, setData] = useState(null);  // FEHLER!
  }
};

// ❌ FALSCH: Hook in Schleife
const useAnotherBadHook = (ids: number[]) => {
  return ids.map(id => {
    const [data] = useState(null);  // FEHLER!
    return data;
  });
};

// ✅ RICHTIG: Custom Hook, der andere Hooks aufruft
const useFlightFilters = () => {
  const [searchQuery, setSearchQuery] = useLocalStorage('search', '');
  const [statusFilter, setStatusFilter] = useLocalStorage('status', 'all');
  // useMemo, useEffect etc. sind hier ebenfalls erlaubt
  return { searchQuery, setSearchQuery, statusFilter, setStatusFilter };
};
ℹ
ESLint-Plugin erzwingt die Regeln

eslint-plugin-react-hooks ist im Vite-React-Template bereits enthalten und prüft bei jedem Speichern, ob die Hook-Regeln eingehalten werden. Funktionen mit use-Prefix werden automatisch als Hooks erkannt und entsprechend geprüft. Das ist einer der Gründe, warum das Prefix so wichtig ist.

Schritt 2: useFlightFilters.ts erstellen

src/hooks/useFlightFilters.ts TypeScript 
import { useMemo } from 'react';
import { Flight, FlightStatus } from '../types/flight';
import useLocalStorage from './useLocalStorage';

interface UseFlightFiltersReturn {
  searchQuery: string;
  setSearchQuery: (q: string) => void;
  statusFilter: FlightStatus | 'all';
  setStatusFilter: (s: FlightStatus | 'all') => void;
  typeFilter: 'all' | 'departure' | 'arrival';
  setTypeFilter: (t: 'all' | 'departure' | 'arrival') => void;
  filteredDepartures: Flight[];
  filteredArrivals: Flight[];
}

/**
 * Verwaltet alle Filter-Einstellungen für die Flugsuche.
 * Filterzustand wird in localStorage persistiert.
 *
 * @param flights - Das ungefilterte Flug-Array
 */
const useFlightFilters = (flights: Flight[]): UseFlightFiltersReturn => {
  // Filter-State mit localStorage-Persistenz
  const [searchQuery, setSearchQuery] =
    useLocalStorage<string>('fb-search', '');

  const [statusFilter, setStatusFilter] =
    useLocalStorage<FlightStatus | 'all'>('fb-status', 'all');

  const [typeFilter, setTypeFilter] =
    useLocalStorage<'all' | 'departure' | 'arrival'>('fb-type', 'all');

  // useMemo: Gefilterte Listen nur neu berechnen, wenn sich
  // flights oder Filter-Werte ändern
  const filteredFlights = useMemo(() => {
    return flights.filter(flight => {
      const q = searchQuery.toLowerCase();
      const matchesSearch =
        !q ||
        flight.flightNumber.toLowerCase().includes(q) ||
        flight.airline.toLowerCase().includes(q) ||
        flight.airport.toLowerCase().includes(q);

      const matchesStatus =
        statusFilter === 'all' || flight.status === statusFilter;

      const matchesType =
        typeFilter === 'all' || flight.type === typeFilter;

      return matchesSearch && matchesStatus && matchesType;
    });
  }, [flights, searchQuery, statusFilter, typeFilter]);

  const filteredDepartures = useMemo(
    () => filteredFlights.filter(f => f.type === 'departure'),
    [filteredFlights]
  );

  const filteredArrivals = useMemo(
    () => filteredFlights.filter(f => f.type === 'arrival'),
    [filteredFlights]
  );

  return {
    searchQuery,    setSearchQuery,
    statusFilter,   setStatusFilter,
    typeFilter,     setTypeFilter,
    filteredDepartures,
    filteredArrivals,
  };
};

export default useFlightFilters;

Schritt 3: App.tsx – Vorher / Nachher

src/App.tsx (nach Refactoring) TypeScript 
import { useState } from 'react';
import { Flight, FlightStatus } from './types/flight';
import useFlights from './hooks/useFlights';
import useFlightFilters from './hooks/useFlightFilters';
import { useTheme } from './context/ThemeContext';

import AirportHeader from './components/AirportHeader';
import FlightBoard from './components/FlightBoard';
import FlightDetail from './components/FlightDetail';
import SearchBar from './components/SearchBar';
import FilterBar from './components/FilterBar';

// App.tsx ist jetzt deutlich übersichtlicher:
// Keine direkte useState/useEffect-Logik mehr für Daten & Filter.
function App() {
  const { theme } = useTheme();

  // Datenabruf-Logik komplett im Hook
  const { flights, isLoading, error, refetch, lastUpdated } = useFlights();

  // Filter-Logik komplett im Hook (inkl. localStorage-Persistenz)
  const {
    searchQuery, setSearchQuery,
    statusFilter, setStatusFilter,
    filteredDepartures, filteredArrivals,
  } = useFlightFilters(flights);

  // Nur App-spezifischer State bleibt hier
  const [selectedFlight, setSelectedFlight] = useState<Flight | null>(null);

  const handleStatusChange = (id: number, status: FlightStatus) => {
    // Direkte Mutation nicht möglich, da flights aus dem Hook kommt.
    // In der Praxis: API-Call + refetch(). Für lokale Demo: eigener State.
    console.log(`Status ändern: Flug ${id} -> ${status}`);
    refetch();
  };

  if (error)     return <div className="error">Fehler: {error}</div>;

  return (
    <div style={{ minHeight: '100vh', background: theme === 'dark' ? '#0d1117' : '#f6f8fa' }}>
      <AirportHeader lastUpdated={lastUpdated} onRefresh={refetch} />
      <main style={{ padding: '1.5rem' }}>
        <SearchBar value={searchQuery} onChange={setSearchQuery} />
        <FilterBar currentStatus={statusFilter} onStatusChange={setStatusFilter} />
        {isLoading ? (
          <div className="board-loading">Flüge werden geladen...</div>
        ) : (
          <>
            <FlightBoard
              title="Abflüge"
              flights={filteredDepartures}
              onFlightSelect={setSelectedFlight}
              selectedFlightId={selectedFlight?.id}
            />
            <FlightBoard
              title="Ankünfte"
              flights={filteredArrivals}
              onFlightSelect={setSelectedFlight}
              selectedFlightId={selectedFlight?.id}
            />
          </>
        )}
        {selectedFlight && (
          <FlightDetail
            flight={selectedFlight}
            onClose={() => setSelectedFlight(null)}
          />
        )}
      </main>
    </div>
  );
}

Häufige Fehler

Fehler: Hook ohne use-Prefix

Eine Funktion wie fetchFlights() ruft useState intern auf. React erkennt sie nicht als Hook und kann keine Verletzung der Hook-Regeln melden. Das ESLint-Plugin springt ebenfalls nicht an. Fehler entstehen still.

Fix: Immer das use-Prefix verwenden: useFetchFlights(). Das Prefix ist keine reine Konvention, sondern ein Signal an React und Linting-Tools.

Fehler: Hook in Bedingung aufrufen

if (isAdmin) { const [data] = useState(null); } bricht die Hook-Reihenfolge. React nummeriert Hooks intern in der Reihenfolge, in der sie aufgerufen werden. Wird ein Hook manchmal übersprungen, verschieben sich alle nachfolgenden Nummern – State wird falsch zugeordnet, Fehler sind schwer zu debuggen.

Fix: Hooks immer bedingungslos aufrufen. Die Bedingung in den Hook selbst verlagern: useEffect(() => { if (!isAdmin) return; ... }, [isAdmin]);

Fehler: Geteilter State aus Custom Hook erwartet

Zwei Komponenten rufen beide useFlights() auf und erwarten, dass sie die gleichen Daten teilen. Tatsächlich haben sie separate State-Instanzen. Jede Komponente lädt die Daten unabhängig vom Backend.

Fix: Für geteilten State den Context API verwenden (Lektion 2.4) oder den Hook nur in der gemeinsamen Elternkomponente aufrufen und die Daten als Props weitergeben.

Fehler: Zu komplexe Hooks ohne klare Verantwortung

Ein useApp()-Hook verwaltet Flights, Filter, Theme, Navigation und Nutzereinstellungen in einer Funktion. Der Hook wird unlesbar und schwer zu testen. Jede Änderung riskiert unbeabsichtigte Nebenwirkungen.

Fix: Jeder Hook sollte eine klar abgegrenzte Aufgabe haben. Lieber drei kleine Hooks (useFlights, useFilters, useTheme) als ein großer. Das Single-Responsibility-Prinzip gilt auch für Hooks.

Aufgaben

Aufgabe 1 useFlights implementieren

Extrahiere die gesamte Fetch-Logik aus App.tsx in einen Custom Hook.

  • Erstelle src/hooks/useFlights.ts wie im Theorieteil gezeigt
  • Der Hook soll zurückgeben: flights, isLoading, error, refetch(), lastUpdated
  • Verwende einen AbortController im Cleanup, um laufende Requests abzubrechen
  • Implementiere automatisches Polling alle 30 Sekunden mit setInterval
  • Zähle die Zeilen von App.tsx vorher und nachher – die Reduktion sollte spürbar sein
Aufgabe 2 useFlightFilters mit localStorage-Persistenz

Extrahiere die Filter-Logik in einen eigenen Hook und persistiere die Einstellungen.

  • Erstelle src/hooks/useLocalStorage.ts (generischer Hook)
  • Erstelle src/hooks/useFlightFilters.ts, der useLocalStorage nutzt
  • Der Filter-State (searchQuery, statusFilter, typeFilter) soll im localStorage gespeichert werden – beim Neuladen der Seite sind die letzten Einstellungen noch aktiv
  • Berechne filteredDepartures und filteredArrivals mit useMemo im Hook
Aufgabe 3 useDebounce-Hook

Implementiere einen useDebounce-Hook, der eine Suchanfrage erst nach einer kurzen Pause weitergibt. So werden bei schnellem Tippen keine unnötigen API-Anfragen ausgelöst.

  • Signatur: useDebounce<T>(value: T, delay: number): T
  • Implementierung: useEffect mit setTimeout und Cleanup per clearTimeout
  • Verwende ihn in SearchBar: const debouncedQuery = useDebounce(inputValue, 300) – debouncedQuery wird erst 300ms nach dem letzten Tastendruck aktualisiert
  • Teste: Tippe schnell „LH7“ – es sollte nur eine Filter-Berechnung ausgelöst werden, nicht drei
Bonus usePreviousValue-Hook mit useRef

Implementiere usePreviousValue<T>(value: T): T | undefined, der den vorherigen Wert einer Variable zurückgibt.

  • Verwende useRef: Ein Ref-Objekt behält seinen Wert zwischen Renders, löst aber kein Re-Render aus. Perfekt für „Gedächtnis“-Logik.
  • Schema: const ref = useRef<T>(undefined); useEffect(() => { ref.current = value; }); Der Effekt ohne Abhängigkeiten läuft nach jedem Render – daher ist ref.current während des Renders noch der alte Wert.
  • Nutze den Hook in FlightBoard: Vergleiche die aktuelle Fluganzahl mit der vorherigen und zeige einen Pfeil nach oben (↑) oder unten (↓) an
