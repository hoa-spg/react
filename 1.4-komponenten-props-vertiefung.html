Was ist eine Komponente?

Eine Komponente ist der wichtigste Baustein in React. Sie ist eine TypeScript-Funktion, die JSX zurückgibt und einen eigenständigen, wiederverwendbaren Teil der Benutzeroberfläche repräsentiert. Komponenten können verschachtelt werden: eine Komponente nutzt andere Komponenten – genau wie HTML-Elemente verschachtelt werden.

Die wichtigste Konvention: Komponenten-Namen beginnen immer mit einem Großbuchstaben (PascalCase).

Einfache Komponente TypeScript 
// Einfachste mögliche Komponente – gibt JSX zurück
const WelcomeMessage = () => {
  return <h1>Willkommen beim FlugBoard!</h1>;
};

// Kurzschreibweise mit implizitem Return:
const WelcomeMessage = () => <h1>Willkommen beim FlugBoard!</h1>;

// Verwendung in einer anderen Komponente:
function App() {
  return (
    <div>
      <WelcomeMessage />  {/* Großbuchstabe = eigene Komponente */}
      <p>Flughafen Wien-Schwechat</p>
    </div>
  );
}
ℹ
Groß- vs. Kleinbuchstabe ist entscheidend

React unterscheidet anhand des ersten Buchstabens: <div> ist ein nativer HTML-Tag, <Div> wäre eine benutzerdefinierte Komponente. Ein Komponentenname mit Kleinbuchstaben wird als HTML-Element behandelt und führt zu unerwartetem Verhalten.

💡
Hinweis zu Klassenkomponenten

Neben Funktionskomponenten gibt es in React auch historische Klassenkomponenten (class ... extends React.Component). Sie verwenden Lifecycle-Methoden wie componentDidMount statt Hooks. In modernem React werden neue Anwendungen fast immer mit Funktionskomponenten und Hooks gebaut. Deshalb verwenden wir in diesem Kurs konsequent den Funktionskomponenten-Ansatz.

Props: Eingabeparameter für Komponenten

Props (kurz für Properties) sind die Eingabeparameter einer Komponente – ähnlich wie Funktionsargumente. Sie fließen immer von oben nach unten (vom Eltern- zum Kindkind-Element). Props sind read-only: Eine Komponente darf ihre eigenen Props niemals verändern.

In TypeScript definieren wir Props mit einem Interface. Das gibt uns vollständige Typsicherheit: falsch geschriebene Prop-Namen oder falsche Typen werden sofort als Fehler markiert.

src/components/FlightStatusBadge.tsx TypeScript 
import './FlightStatusBadge.css';

// Typdefinition für den Flugstatus
type FlightStatus =
  | 'on-time'
  | 'delayed'
  | 'boarding'
  | 'departed'
  | 'landed'
  | 'cancelled';

// Props-Interface: Legt fest, welche Props die Komponente erwartet
interface FlightStatusBadgeProps {
  status: FlightStatus;
}

/**
 * Zeigt den Status eines Fluges als farbiges Badge an.
 * @param status - Der aktuelle Flugstatus
 */
const FlightStatusBadge = ({ status }: FlightStatusBadgeProps) => {
  // Konfigurationsobjekt: Status-Wert -> Label und CSS-Klasse
  const config: Record<FlightStatus, { label: string; className: string }> = {
    'on-time':   { label: 'Pünktlich', className: 'status-on-time' },
    'delayed':   { label: 'Verspätet', className: 'status-delayed' },
    'boarding':  { label: 'Boarding', className: 'status-boarding' },
    'departed':  { label: 'Gestartet',  className: 'status-departed' },
    'landed':    { label: 'Gelandet', className: 'status-landed' },
    'cancelled': { label: 'Gestrichen', className: 'status-cancelled' },
  };

  const { label, className } = config[status];
  return <span className={`status-pill ${className}`}>{label}</span>;
};

export default FlightStatusBadge;

Optionale Props und Default-Werte

In TypeScript markiert man optionale Props mit einem Fragezeichen (?). Im Funktionskopf können direkt Default-Werte angegeben werden. Das ist der idiomatische React+TypeScript-Weg – die früher gebräuchliche defaultProps-Eigenschaft ist veraltet.

Optionale Props mit Defaults TypeScript 
interface AirportHeaderProps {
  airportName: string;           // Pflichtfeld
  iataCode: string;              // Pflichtfeld
  subtitle?: string;             // Optional (mit ?)
  showTime?: boolean;            // Optional, Default: false
}

const AirportHeader = ({
  airportName,
  iataCode,
  subtitle = 'Flugplan aktuell',  // Default-Wert direkt hier
  showTime = false,               // Default-Wert
}: AirportHeaderProps) => {
  return (
    <header>
      <h1>✈ {airportName} ({iataCode})</h1>
      <p>{subtitle}</p>
      {/* Optionaler Zeitstempel */}
      {showTime && <p>{new Date().toLocaleTimeString('de-AT')}</p>}
    </header>
  );
};

// Verwendung – nur Pflichtfelder:
<AirportHeader airportName="Wien-Schwechat" iataCode="VIE" />

// Verwendung – mit optionalen Feldern:
<AirportHeader
  airportName="Wien-Schwechat"
  iataCode="VIE"
  subtitle="Live-Flugplan"
  showTime={true}
/>

Typdefinitionen in eigene Datei auslagern

Bevor wir die Flugtabelle in Komponenten zerlegen, brauchen wir ein gemeinsames Datenmodell. Wenn mehrere Komponenten dasselbe Interface verwenden, lagert man Typen in eine eigene Datei aus. Dadurch vermeiden wir Duplikation und haben eine einzige „Source of Truth“ für unser Datenmodell. Das Interface Flight beschreibt einen einzelnen Flug und wird in den folgenden Abschnitten von FlightCard und FlightBoard verwendet.

FlightCard – Eine Komponente pro Tabellenzeile

Anstatt die Tabelle mit hartkodierten <tr>-Elementen zu füllen, extrahieren wir jede Zeile in eine eigene FlightCard-Komponente. Die Komponente bekommt ein vollständiges Flight-Objekt als Prop.

src/components/FlightCard.tsx TypeScript 
import FlightStatusBadge from './FlightStatusBadge';
import { Flight } from '../types/flight';
import './FlightCard.css';

// Props-Interface: Ein einziges flight-Objekt als Prop
interface FlightCardProps {
  flight: Flight;
}

/**
 * Stellt einen einzelnen Flug als Tabellenzeile dar.
 */
const FlightCard = ({ flight }: FlightCardProps) => {
  // Zeitanzeige: Falls Verspätung vorliegt, beide Zeiten anzeigen
  const timeDisplay =
    flight.expectedTime && flight.expectedTime !== flight.scheduledTime
      ? `${flight.scheduledTime} (${flight.expectedTime})`
      : flight.scheduledTime;

  return (
    <tr>
      <td className="flight-cell">{flight.flightNumber}</td>
      <td className="flight-cell">{flight.airline}</td>
      <td className="flight-cell">{flight.airport}</td>
      <td className="flight-cell">{timeDisplay}</td>
      <td className="flight-cell">
        <FlightStatusBadge status={flight.status} />
      </td>
      <td className="flight-cell">{flight.terminal}</td>
      {/* Nullish Coalescing: falls gate undefined, zeige — */}
      <td className="flight-cell">{flight.gate ?? '—'}</td>
    </tr>
  );
};

export default FlightCard;

FlightBoard – Komponenten zusammensetzen

FlightBoard ist eine Container-Komponente: Sie erhält ein Array von Flügen und einen Titel als Props und rendert für jeden Flug eine FlightCard. Wie .map() und der key-Prop genau funktionieren, sehen wir weiter unten in dieser Lektion.

src/components/FlightBoard.tsx TypeScript 
import FlightCard from './FlightCard';
import { Flight } from '../types/flight';
import './FlightBoard.css';

interface FlightBoardProps {
  flights: Flight[];   // Array von Flügen
  title: string;       // Überschrift der Tabelle
}

/**
 * Tabellenansicht für eine Liste von Flügen.
 */
const FlightBoard = ({ flights, title }: FlightBoardProps) => {
  return (
    <section className="board-section">
      <h2 className="board-title">{title}</h2>
      <table className="flight-table">
        <thead>
          <tr>
            <th>Flug</th>
            <th>Airline</th>
            <th>Ziel</th>
            <th>Geplant</th>
            <th>Status</th>
            <th>Terminal</th>
            <th>Gate</th>
          </tr>
        </thead>
        <tbody>
          {flights.map((flight) => (
            // key ist Pflicht beim Rendern von Listen – mehr dazu weiter unten
            <FlightCard key={flight.id} flight={flight} />
          ))}
        </tbody>
      </table>
    </section>
  );
};

export default FlightBoard;

In App.tsx werden die Flüge nach Typ aufgeteilt und an zwei FlightBoard-Instanzen übergeben. Der AirportHeader aus Lektion 1.3 bleibt als Seitenkopf erhalten:

Children Props

Jede Komponente hat automatisch Zugriff auf ein spezielles Prop namens children. Es enthält alles, was zwischen dem öffnenden und schließenden Tag der Komponente steht – ähnlich wie der Inhalt eines HTML-Elements. Der Typ für children ist React.ReactNode.

Children Props Beispiel TypeScript 
import { ReactNode } from 'react';

// Props-Interface mit children
interface SectionProps {
  title: string;
  children: ReactNode;   // Alles was zwischen die Tags kommt
}

// Layout-Komponente, die Kinder-Elemente einbettet
const BoardSection = ({ title, children }: SectionProps) => (
  <section>
    <h2>{title}</h2>
    {children}
  </section>
);

// Verwendung: Alles zwischen den Tags wird als children übergeben
<BoardSection title="Abflüge">
  <FlightBoard flights={departures} title="Abflüge" />
  <p>{departures.length} Flüge angezeigt</p>
</BoardSection>

Listen mit .map() rendern

Im FlightBoard haben wir es schon verwendet: In React rendert man Listen, indem man ein Array mit der .map()-Methode in ein Array von JSX-Elementen umwandelt. React kann solche Arrays direkt rendern. Das key-Prop ist dabei Pflicht – es hilft React, die Elemente bei Änderungen eindeutig zu identifizieren.

Listen rendern – Grundlagen TypeScript 
// Einfaches Beispiel: Array von Strings
const staedte = ['Wien', 'Berlin', 'Paris'];

const Stadtliste = () => (
  <ul>
    {staedte.map((stadt) => (
      <li key={stadt}>{stadt}</li>
    ))}
  </ul>
);

// Mit Objekten: Immer eine eindeutige ID als key verwenden!
{flights.map((flight) => (
  <FlightCard key={flight.id} flight={flight} />
))}

// SCHLECHT: Index als key (nur ok, wenn sich die Liste nie ändert!)
{flights.map((flight, index) => (
  <FlightCard key={index} flight={flight} />
))}

Warum der Index als key problematisch ist, zeigt das folgende Beispiel. Noch ist unsere Flugliste statisch – ab Lektion 1.5 ändern sich Listen aber zur Laufzeit (Einträge werden gefiltert, entfernt, umsortiert).

key-Prop: Index vs. ID TypeScript 
// Ausgangsliste:
// [OS123 (id:1), LH456 (id:2), BA234 (id:4)]
//  key=0           key=1           key=2           (mit Index als key)
//  key=1           key=2           key=4           (mit ID als key)

// Nach Löschen von LH456 (id:2):
// [OS123 (id:1), BA234 (id:4)]

// MIT INDEX ALS KEY (falsch):
// React sieht: key=0 gleich, key=1 ANDERS (jetzt BA234 statt LH456)
// React denkt: key=1 wurde geändert, key=2 wurde entfernt
// Problem: BA234 erbt State/Fokus von LH456!

// MIT ID ALS KEY (richtig):
// React sieht: key=1 gleich, key=2 wurde entfernt, key=4 gleich
// React weiß: LH456 wurde entfernt, alle anderen bleiben unverändert

// Fazit: Bei statischen Listen (Reihenfolge ändert sich nie) ist Index ok.
//        Bei dynamischen Listen (hinzufügen, löschen, sortieren) immer eine stabile ID nutzen!
ℹ
key ist kein normales Prop

key wird von React intern verwendet und ist in der Komponente selbst nicht zugänglich. Wenn du die ID innerhalb der Komponente benötigst, übergib sie zusätzlich als normales Prop: <FlightCard key={flight.id} id={flight.id} flight={flight} />

Conditional Rendering – Drei Patterns

Einzelne Muster kennen wir schon: {showTime && ...} im AirportHeader und den Ternary-Operator für die Zeitanzeige in FlightCard. React rendert bedingt, indem JavaScript-Ausdrücke direkt in JSX verwendet werden. Es gibt drei gängige Patterns – jedes hat seine Berechtigung:

Pattern 1: && Operator TypeScript 
// Wenn die Bedingung wahr ist, wird der rechte Teil gerendert.
// Wenn falsch, wird nichts gerendert (undefined/false wird von React ignoriert).

{flight.status === 'delayed' && (
  <span className="time-delayed">
    Verspätet: {flight.expectedTime} Uhr
  </span>
)}

{flight.gate && (
  <span>Gate: {flight.gate}</span>
)}

// ACHTUNG: Zahlen! 0 wird als "0" gerendert, nicht als nichts!
// FALSCH:
{flights.length && <span>{flights.length} Flüge</span>}
// Wenn flights.length === 0, wird "0" im DOM angezeigt!

// RICHTIG:
{flights.length > 0 && <span>{flights.length} Flüge</span>}
Pattern 2: Ternary Operator TypeScript 
// Bedingung ? WennWahr : WennFalsch
// Gut, wenn es zwei alternative Darstellungen gibt.

{flight.gate ? (
  <span>Gate: {flight.gate}</span>
) : (
  <span>Kein Gate zugewiesen</span>
)}

// Auch für CSS-Klassen (statt Inline-Styles):
<span className={flight.status === 'cancelled' ? 'flight-num is-cancelled' : 'flight-num'}>
  {flight.flightNumber}
</span>
Pattern 3: Früher Return TypeScript 
// Für komplexere Logik: vor dem Haupt-JSX zurückkehren.
// Gut lesbar und vermeidet tief verschachtelte Bedingungen.

const FlightRow = ({ flight }: { flight: Flight }) => {
  // Annullierte Flüge bekommen eine spezielle Darstellung
  if (flight.status === 'cancelled') {
    return (
      <tr className="flight-row is-cancelled">
        <td colSpan={7} className="flight-cell">
          {flight.flightNumber} – {flight.airline} – Gestrichen
        </td>
      </tr>
    );
  }

  // Normaler Fall: vollständige Zeile
  return (
    <tr>
      {/* ... alle Spalten ... */}
    </tr>
  );
};

Listen sortieren ohne Mutation

JavaScript-Array-Methoden wie .filter() und .sort() eignen sich gut, um Flugdaten vor dem Rendern aufzubereiten. Aber Vorsicht: .filter() und .map() liefern ein neues Array, .sort() dagegen verändert das Original-Array. Deshalb zuerst mit dem Spread-Operator eine Kopie erstellen und erst die Kopie sortieren.

src/App.tsx – Flüge nach Zeit sortieren TypeScript 
import { sampleFlights } from './data/flights';
import { Flight } from './types/flight';
import AirportHeader from './components/AirportHeader';
import FlightBoard from './components/FlightBoard';
import './App.css';

// Kopie erstellen, dann sortieren – das Original bleibt unverändert.
// Stringvergleich funktioniert für das Format "HH:MM" korrekt.
const sortByTime = (flights: Flight[]): Flight[] =>
  [...flights].sort((a, b) => a.scheduledTime.localeCompare(b.scheduledTime));

function App() {
  const departures = sortByTime(sampleFlights.filter(f => f.type === 'departure'));
  const arrivals   = sortByTime(sampleFlights.filter(f => f.type === 'arrival'));

  return (
    <div className="app-page">
      <AirportHeader airportName="Flughafen Wien-Schwechat" />
      <FlightBoard flights={departures} title="Abflüge" />
      <FlightBoard flights={arrivals}   title="Ankünfte" />
    </div>
  );
}

export default App;

Empty States

Wenn eine Liste leer ist, sollte die App eine hilfreiche Nachricht anzeigen statt einer leeren Tabelle mit Kopfzeile. Das nennt sich Empty State. Die Komponente ist ein gutes Beispiel für ein optionales Prop mit Default-Wert:

src/components/EmptyState.tsx TypeScript 
import './EmptyState.css';

interface EmptyStateProps {
  message?: string;
}

/**
 * Zeigt einen Hinweis an, wenn eine Liste keine Einträge hat.
 */
const EmptyState = ({ message = 'Keine Flüge gefunden' }: EmptyStateProps) => (
  <div className="empty-state">
    <span className="empty-icon">✈</span>
    <p className="empty-text">{message}</p>
  </div>
);

export default EmptyState;

Komponenten extrahieren & Darstellung verfeinern

Wir zerlegen die monolithische App.tsx aus Lektion 1.2 in wiederverwendbare Komponenten. Am Ende dieser Lektion hat das Projekt folgende Struktur:

Neue Projektstruktur Bash 
src/
├── App.tsx                     ← Sortiert die Flüge, nutzt AirportHeader und FlightBoard
├── components/

✓
Wann eine Komponente auslagern?

Eine gute Faustregel: Lagere eine Komponente aus, wenn sie (a) an mehreren Stellen verwendet wird, (b) zu komplex wird um sie zu überblicken, oder (c) einen klar abgegrenzten Verantwortungsbereich hat. FlightStatusBadge ist ein perfektes Beispiel: klar definiert, wiederverwendbar, eigenständig testbar.

Darstellung verfeinern:

  • Alle Flüge sind nach scheduledTime aufsteigend sortiert (sortByTime in App.tsx)
  • Verspätete Flüge zeigen beide Zeiten: 11:15 → 11:45
  • Gestrichene Flüge werden durchgestrichen und gedämpft dargestellt
  • Bei leerer Liste zeigt FlightBoard den EmptyState
src/components/FlightCard.tsx – Zeitanzeige & gestrichene Flüge TypeScript 
const FlightCard = ({ flight }: FlightCardProps) => {
  const isCancelled = flight.status === 'cancelled';
  const isDelayed = flight.status === 'delayed';
  const isBoarding = flight.status === 'boarding';

  // CSS-Klassen bedingt setzen
  const rowClassName = isCancelled ? 'flight-row is-cancelled' : 'flight-row';
  const flightNumberClassName = isCancelled
    ? 'flight-num is-cancelled'
    : 'flight-num';

  // Zeitanzeige mit frühen Returns je nach Status
  const renderTime = () => {
    if (isDelayed && flight.expectedTime) {
      return (
        <span>
          <span className="time-old">{flight.scheduledTime}</span>
          <span className="time-delayed">→ {flight.expectedTime}</span>
        </span>
      );
    }
    if (isBoarding) {
      return <span className="time-boarding">{flight.scheduledTime}</span>;
    }
    return <span>{flight.scheduledTime}</span>;
  };

  return (
    <tr className={rowClassName}>
      <td className="flight-cell">
        <span className={flightNumberClassName}>{flight.flightNumber}</span>
      </td>
      <td className="flight-cell">{flight.airline}</td>
      <td className="flight-cell">{flight.airport}</td>
      <td className="flight-cell">{renderTime()}</td>
      <td className="flight-cell">
        <FlightStatusBadge status={flight.status} />
      </td>
      <td className="flight-cell">{flight.terminal}</td>
      <td className="flight-cell">{flight.gate ?? '—'}</td>
    </tr>
  );
};

Häufige Fehler

Fehler: Komponenten-Name beginnt mit Kleinbuchstabe

const flightCard = ... – React behandelt <flightCard /> als unbekannten HTML-Tag und gibt eine Warnung aus: "The tag flightCard is unrecognized in this browser." Die Komponente wird nicht korrekt gerendert.

Immer PascalCase verwenden: const FlightCard = ...

Fehler: Props-Typ nicht mit Interface definiert

Ohne TypeScript-Interface für Props hat man keinen Typen-Schutz. Tippfehler in Prop-Namen (flightt statt flight) oder falsche Typen werden erst zur Laufzeit auffallen – oder gar nicht.

Immer ein interface FooProps definieren und als Typ des Parameters angeben.

Fehler: key-Prop beim Rendern von Listen vergessen

Wenn man .map() verwendet und kein key-Prop angibt, erscheint in der Browser-Konsole: "Each child in a list should have a unique key prop." React kann die Liste dann nicht effizient aktualisieren. TypeScript prüft das nicht automatisch.

Beim .map() immer key={flight.id} setzen.

Fehler: Index als key bei dynamischen Listen

key={index} ist nur sicher, wenn die Liste statisch ist. Sobald Elemente hinzugefügt, gelöscht oder umsortiert werden, führt der Index als key zu falschen Updates und kann internen Komponenten-State durcheinanderbringen.

Bei dynamischen Listen immer eine stabile, eindeutige ID aus den Daten verwenden.

Fehler: && mit dem Wert 0

{flights.length && <span>...</span>} rendert den Wert 0 ins DOM, wenn flights.length === 0 ist. JavaScript wertet 0 && irgendwas als 0 aus, und React rendert Zahlen direkt.

Expliziten Vergleich verwenden: {flights.length > 0 && ...}

Fehler: Original-Array mit .sort() verändern

flights.sort(...) sortiert das Array in-place. Bei einem Props-Array verändert die Komponente damit Daten, die ihr nicht gehören – Props sind read-only.

Vor .sort() immer eine Kopie erstellen: [...flights].sort(...)

Fehler: export default vergessen

Ohne Export kann die Komponente nicht importiert werden. Der Fehler lautet: "Module has no default export."

Jede Komponentendatei benötigt export default KomponentenName; am Ende.
