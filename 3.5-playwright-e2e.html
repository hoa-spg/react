Lektion 3.5 — Teil 3: Next.js

Playwright End-to-End Tests

Next.js ca. 75 min

Lernziele

  • E2E-Tests von Komponententests (Lektion 2.6) abgrenzen
  • Playwright in einem Next.js-Projekt einrichten
  • Wichtige User-Flows als E2E-Tests formulieren
  • Locators und Assertions robust verwenden
  • Tests im Browser beobachten und Fehler finden

1 — Was ist E2E-Testen?

In Lektion 2.6 haben wir einzelne Komponenten mit Vitest und der React Testing Library getestet – in einem simulierten Browser (jsdom) und ohne Server. End-to-End-Tests (E2E) prüfen dagegen die ganze Anwendung: Ein echter Browser öffnet die laufende App, klickt und tippt wie ein Mensch und kontrolliert, was auf dem Bildschirm erscheint. Dabei laufen Routing, Server Components, Datenbank und Client Components zusammen.

E2E-Tests sind langsamer als Komponententests. Gute E2E-Tests sind deshalb wenige, decken aber die wichtigsten Abläufe ab: Hauptnavigation, Suche, Formulare und zentrale Fehlerfälle.

2 — Playwright einrichten

Playwright (von Microsoft) steuert Chromium, Firefox und WebKit. Wir installieren das Test-Paket und einen Browser:

Terminal Bash 
npm install --save-dev @playwright/test
npx playwright install chromium

In package.json kommt ein Skript zum Starten der Tests dazu:

package.json (Ausschnitt) JSON 
"scripts": {
  "dev": "next dev",
  "build": "next build",
  "start": "next start",
  "lint": "next lint",
  "test:e2e": "playwright test"
}

Die Einstellungen stehen in playwright.config.ts im Projektordner:

playwright.config.ts TypeScript 
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  // Hier liegen die E2E-Tests
  testDir: './tests',
  use: {
    // page.goto('/departures') öffnet http://localhost:3000/departures
    baseURL: 'http://localhost:3000',
  },
  // Startet vor den Tests den Next.js-Server (oder nutzt einen laufenden)
  webServer: {
    command: 'npm run dev',
    url: 'http://localhost:3000',
    reuseExistingServer: true,
  },
  // Vorerst nur in Chromium testen
  projects: [{ name: 'chromium', use: { ...devices['Desktop Chrome'] } }],
});
  • testDir: In diesem Ordner sucht Playwright nach Dateien mit der Endung .spec.ts.
  • baseURL: Damit reicht in den Tests ein relativer Pfad wie '/departures'.
  • webServer: Playwright startet vor den Tests npm run dev und wartet, bis die URL antwortet. Läuft der Server schon, wird er wiederverwendet.
  • projects: In welchen Browsern getestet wird — vorerst nur Chromium.

Playwright legt bei jedem Lauf Ergebnisse und einen Bericht ab. Die gehören nicht ins Repository:

.gitignore (Ergänzung) Text 
# Ergebnisse von Playwright
test-results/
playwright-report/

3 — Der erste E2E-Test

Ein Playwright-Test besteht aus wenigen Bausteinen, die du zum Teil aus Lektion 2.6 kennst:

  • test('Name', async ({ page }) => { … }) definiert einen Test. page ist ein Browser-Tab, den Playwright für jeden Test neu öffnet.
  • page.goto('/departures') öffnet eine Seite.
  • Locators finden Elemente wie die Testing Library: page.getByRole('link', { name: 'LH456' }), page.getByText(…) oder page.getByPlaceholder(…) für ein Eingabefeld über seinen Platzhaltertext.
  • fill('…') tippt Text in ein Feld, click() klickt.
  • expect(locator).toBeVisible() prüft, ob ein Element sichtbar ist, toHaveCount(0), dass es keines gibt.

Der erste Test prüft die Suche auf der Abflugseite aus Lektion 3.3:

tests/flugboard.spec.ts TypeScript 
import { test, expect } from '@playwright/test';

test('Suche filtert die Abflugliste', async ({ page }) => {
  await page.goto('/departures');
  await expect(page.getByRole('heading', { name: /Abflüge/ })).toBeVisible();

  await page.getByPlaceholder('Flug, Airline oder Ziel suchen...').fill('lufthansa');

  await expect(page.getByRole('link', { name: 'LH456' })).toBeVisible();
  await expect(page.getByRole('link', { name: 'OS123' })).toHaveCount(0);
});
Terminal Bash 
npm run test:e2e
💡
Automatisches Warten

Playwright wartet bei jedem expect und jeder Aktion automatisch, bis das Element da ist (standardmäßig bis zu 5 Sekunden). Nach dem Tippen in die Suche müssen wir also nicht selbst warten, bis React die Liste neu gerendert hat.

4 — Navigation und Fehlerfall testen

Zwei weitere Tests decken die Detailseite (Lektion 3.2) und die 404-Seite ab. expect(page).toHaveURL('/flight/1') prüft die Adresse im Browser — relativ zur baseURL.

tests/flugboard.spec.ts (Fortsetzung) TypeScript 
// ... (Import und erster Test wie oben)

test('Klick auf einen Flug öffnet die Detailseite', async ({ page }) => {
  await page.goto('/departures');

  await page.getByRole('link', { name: 'OS123' }).click();
  await expect(page).toHaveURL('/flight/1');
  await expect(page.getByText('Austrian Airlines')).toBeVisible();

  await page.getByRole('link', { name: '← Zurück' }).click();
  await expect(page).toHaveURL('/departures');
});

test('Unbekannter Flug zeigt die 404-Seite', async ({ page }) => {
  await page.goto('/flight/999');
  await expect(page.getByRole('heading', { name: 'Seite nicht gefunden' })).toBeVisible();
});

Die Tests verwenden die Startdaten aus flights-db.ts: Flug 1 ist OS123 von Austrian Airlines. Wer diesen Flug über die API löscht, bringt die Tests zum Scheitern — dann flugboard.sqlite löschen, beim nächsten Start wird sie neu befüllt.

5 — Debugging

Nützliche Befehle Bash 
# Browser sichtbar machen
npx playwright test --headed

# Nur eine Testdatei
npx playwright test tests/flugboard.spec.ts

# UI-Modus: Tests einzeln starten und Schritt für Schritt ansehen
npx playwright test --ui

# HTML-Bericht des letzten Laufs anzeigen
npx playwright show-report
⚠
Flaky Tests vermeiden

Ein Test ist flaky, wenn er mal grün und mal rot ist. Häufigste Ursache sind feste Wartezeiten wie page.waitForTimeout(1000). Besser: auf einen sichtbaren Zustand warten, also expect(…).toBeVisible().

Projektschritt

Projektschritt 3.5

E2E-Tests für das FlugBoard

Die App aus Lektion 3.4 bleibt unverändert — dazu kommen nur Playwright und drei Tests.

  1. Installieren: @playwright/test und Chromium installieren, Skript test:e2e in package.json ergänzen.
  2. Konfigurieren: playwright.config.ts mit baseURL und webServer anlegen, .gitignore ergänzen.
  3. Testen: tests/flugboard.spec.ts mit den Tests für Suche, Detailnavigation und 404-Seite schreiben.
  4. Prüfen: npm run test:e2e meldet drei bestandene Tests. Einen Test absichtlich kaputt machen (z. B. falsche Flugnummer) und den Fehler im HTML-Bericht ansehen.

Häufige Fehler

3 Fehler · zum Aufklappen klicken
Fehler: Base URL inkonsistent

Tests laufen lokal, aber in CI nicht, weil unterschiedliche Hosts/Ports genutzt werden.

Fix: Eine zentrale baseURL in der Playwright-Konfiguration setzen.

Fehler: Fragile CSS-Selektoren

Tests brechen bei kleinen Refactorings, weil sie auf Klassenketten basieren.

Fix: Auf semantische Locators wechseln (Role, Label, Text).

Fehler: Zu viele E2E-Szenarien

Jede Kleinigkeit wird als E2E-Test geschrieben. Die Pipeline wird langsam.

Fix: Nur Kernflüsse end-to-end testen; Details in Komponententests abdecken.

  • Danach muss der neue Flug als Link in der Abflugliste stehen.

Aufgabe 3 Vorbereitung für CI
  • Ergänze in der Config retries: process.env.CI ? 2 : 0 – auf einem Build-Server wird ein fehlgeschlagener Test bis zu zweimal wiederholt.
  • Setze trace: 'on-first-retry' unter use und sieh dir einen Trace mit npx playwright show-trace an.
  • Setze reuseExistingServer auf !process.env.CI. Warum ist das auf einem Build-Server sinnvoll?

Quiz

5 Fragen · zum Aufklappen klicken

Frage 1 Welche Aussagen über E2E-Tests im Vergleich zu Komponententests sind richtig?

Mehrere Antworten sind richtig.

Erklärung: E2E-Tests steuern einen echten Browser gegen die laufende App – inklusive Server und Datenbank. Dadurch prüfen sie das Zusammenspiel aller Teile, sind aber langsamer als Komponententests, die nur einzelne Komponenten in einer DOM-Simulation testen.

Frage 2 Warum braucht man nach dem Tippen in die Suche kein manuelles Warten?

Erklärung: Standardmäßig wartet Playwright bis zu 5 Sekunden.

Frage 3 Was macht Tests typischerweise flaky (mal grün, mal rot)?

Mehrere Antworten sind richtig.

Erklärung: Feste Wartezeiten wie page.waitForTimeout(1000) sind mal zu kurz, mal zu lang. Ebenso unzuverlässig sind Tests, die sich auf Daten verlassen, die ein anderer Test oder jemand anderes verändert haben könnte. Viele Assertions, Locators über Rollen oder mehrere Browser machen Tests nicht flaky.

Frage 4 Was prüft await expect(page).toHaveURL('/flight/1')?

Erklärung: Damit testet man z. B., dass ein Klick in der Liste zur richtigen Detailseite führt.

Frage 5 Warum schlagen die Tests fehl, nachdem jemand Flug 1 (OS123) über die API gelöscht hat?

Erklärung: E2E-Tests hängen vom Zustand der Daten ab. Abhilfe: flugboard.sqlite löschen – beim nächsten Start wird sie mit den Startdaten neu befüllt.
