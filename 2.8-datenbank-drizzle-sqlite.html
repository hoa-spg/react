Lektion 2.8 — Teil 2: React Praxis

Datenbankzugriff mit Drizzle + SQLite

Backend ca. 90 min

Lernziele

  • Verstehen, warum In-Memory-Daten für echte Apps nicht ausreichen
  • Ein Deno+Hono-Backend auf Drizzle ORM und SQLite umstellen
  • Seed-Daten einmalig in die Datenbank schreiben
  • GET-, POST-, PATCH- und DELETE-Endpunkte gegen die Datenbank ausführen

Warum jetzt eine Datenbank?

Bis Lektion 2.7 haben wir die Flugdaten im RAM gehalten. Das ist für den Einstieg perfekt, aber nach jedem Server-Neustart sind alle Änderungen weg. In dieser Lektion wechseln wir auf eine echte Persistenzschicht mit SQLite und Drizzle.

ℹ
Didaktischer Fokus

Wir behalten die API-Struktur aus den vorherigen Lektionen bei. Nur die Datenquelle ändert sich von Array-Operationen auf SQL-Operationen.

Drizzle + SQLite im Deno-Backend

SQLite speichert die ganze Datenbank in einer einzigen Datei – kein eigener Datenbankserver nötig. Drizzle ist ein ORM: Wir beschreiben die Tabelle in TypeScript und schreiben Abfragen als typisierte Funktionsaufrufe statt als SQL-Strings. Die Pakete lädt Deno direkt über npm:-Imports, eine Installation ist nicht nötig.

Der SQLite-Treiber libsql braucht mehr Rechte als unser bisheriges Backend (Dateizugriff und eine native Bibliothek, siehe „Häufige Fehler“):

backend/deno.json JSON 
{
  "tasks": {
    "start": "deno run --allow-net --allow-read --allow-write --allow-env --allow-sys --allow-ffi main.ts",
    "dev": "deno run --allow-net --allow-read --allow-write --allow-env --allow-sys --allow-ffi --watch main.ts"
  }
}

Die Tabelle beschreiben wir mit sqliteTable. In der Datenbank heißen die Spalten im üblichen snake_case, in TypeScript bleiben die Namen aus unserem Flight-Interface:

backend/db.ts (Verbindung und Tabelle) TypeScript 
import { createClient } from 'npm:@libsql/client';
import { and, eq } from 'npm:drizzle-orm';
import { drizzle } from 'npm:drizzle-orm/libsql';
import {
  integer,
  sqliteTable,
  text,
} from 'npm:drizzle-orm/sqlite-core';

import { Flight, FlightStatus, FlightType, seedFlights } from './data.ts';

const client = createClient({ url: 'file:./flugboard.db' });

export const flightsTable = sqliteTable('flights', {
  id: integer('id').primaryKey(),
  flightNumber: text('flight_number').notNull(),
  airline: text('airline').notNull(),
  type: text('type').notNull(),
  scheduledTime: text('scheduled_time').notNull(),
  expectedTime: text('expected_time'),
  status: text('status').notNull(),
  airport: text('airport').notNull(),
  terminal: text('terminal').notNull(),
  gate: text('gate'),
});

const db = drizzle(client);

Datenbankzeilen kennen kein undefined, sondern nur null. mapFlight wandelt eine Zeile deshalb in unser Flight-Objekt um:

backend/db.ts (Zeile → Flight) TypeScript 
const mapFlight = (row: typeof flightsTable.$inferSelect): Flight => ({
  id: row.id,
  flightNumber: row.flightNumber,
  airline: row.airline,
  type: row.type as FlightType,
  scheduledTime: row.scheduledTime,
  expectedTime: row.expectedTime ?? undefined,
  status: row.status as FlightStatus,
  airport: row.airport,
  terminal: row.terminal,
  gate: row.gate ?? undefined,
});

Initialisierung und Seed

Beim Start wird die Tabelle erzeugt (falls sie noch nicht existiert). Ist sie leer, kommen die Beispielflüge hinein. Dazu heißt das Array in data.ts jetzt seedFlights statt flights – es ist nur noch der Startbestand, nicht mehr die aktuelle Liste.

backend/db.ts – initializeDatabase TypeScript 
export const initializeDatabase = async () => {
  await client.execute(`
    CREATE TABLE IF NOT EXISTS flights (
      id INTEGER PRIMARY KEY,
      flight_number TEXT NOT NULL,
      airline TEXT NOT NULL,
      type TEXT NOT NULL,
      scheduled_time TEXT NOT NULL,
      expected_time TEXT,
      status TEXT NOT NULL,
      airport TEXT NOT NULL,
      terminal TEXT NOT NULL,
      gate TEXT
    )
  `);

  const countResult = await client.execute('SELECT COUNT(*) as count FROM flights');
  const count = Number(countResult.rows[0]?.count ?? 0);

  if (count === 0) {
    await db.insert(flightsTable).values(
      seedFlights.map((flight) => ({
        id: flight.id,
        flightNumber: flight.flightNumber,
        airline: flight.airline,
        type: flight.type,
        scheduledTime: flight.scheduledTime,
        expectedTime: flight.expectedTime ?? null,
        status: flight.status,
        airport: flight.airport,
        terminal: flight.terminal,
        gate: flight.gate ?? null,
      }))
    );
  }
};
ℹ
Warum CREATE TABLE per SQL?

Drizzle kennt das Schema zwar, legt die Tabelle aber nicht selbst an. Dafür gibt es das Werkzeug drizzle-kit, das aus dem Schema Migrationen erzeugt. Für unser kleines Projekt reicht ein CREATE TABLE IF NOT EXISTS beim Start – in größeren Projekten verwendet man Migrationen, damit Schemaänderungen nachvollziehbar bleiben.

Abfragen mit Drizzle

Für jeden Endpunkt gibt es eine Funktion. Wo vorher Array-Methoden standen (filter, find, push, splice), stehen jetzt select, insert, update und delete. Alle Funktionen sind async, weil die Datenbank asynchron antwortet.

backend/db.ts – Abfragen TypeScript 
export const listFlights = async (type?: string, status?: string): Promise<Flight[]> => {
  const filters = [];
  if (type) {
    filters.push(eq(flightsTable.type, type));
  }
  if (status) {
    filters.push(eq(flightsTable.status, status));
  }

  const rows = filters.length
    ? await db.select().from(flightsTable).where(and(...filters))
    : await db.select().from(flightsTable);

  return rows.map(mapFlight);
};

export const getFlightById = async (id: number): Promise<Flight | null> => {
  const rows = await db.select().from(flightsTable).where(eq(flightsTable.id, id)).limit(1);
  if (rows.length === 0) {
    return null;
  }
  return mapFlight(rows[0]);
};

export const createFlight = async (input: Omit<Flight, 'id' | 'status'>): Promise<Flight> => {
  const newFlight: Flight = {
    id: Date.now(),
    status: 'on-time',
    ...input,
  };

  await db.insert(flightsTable).values({
    id: newFlight.id,
    flightNumber: newFlight.flightNumber,
    airline: newFlight.airline,
    type: newFlight.type,
    scheduledTime: newFlight.scheduledTime,
    expectedTime: newFlight.expectedTime ?? null,
    status: newFlight.status,
    airport: newFlight.airport,
    terminal: newFlight.terminal,
    gate: newFlight.gate ?? null,
  });

  return newFlight;
};

export const updateFlightStatus = async (
  id: number,
  status: FlightStatus,
): Promise<Flight | null> => {
  const flight = await getFlightById(id);
  if (!flight) {
    return null;
  }

  await db.update(flightsTable).set({ status }).where(eq(flightsTable.id, id));
  return { ...flight, status };
};

export const deleteFlight = async (id: number): Promise<Flight | null> => {
  const flight = await getFlightById(id);
  if (!flight) {
    return null;
  }

  await db.delete(flightsTable).where(eq(flightsTable.id, id));
  return flight;
};

Routen bleiben gleich

Die API-Endpunkte bleiben identisch – dadurch muss das React-Frontend aus Lektion 2.7 nicht geändert werden:

  • GET /api/flights mit optionalen Query-Parametern
  • GET /api/flights/:id
  • POST /api/flights
  • PATCH /api/flights/:id (Status ändern, seit Lektion 2.3)
  • DELETE /api/flights/:id

In main.ts ersetzen die Funktionen aus db.ts die Array-Operationen. Die Handler werden async, und vor dem Serverstart wird die Datenbank initialisiert:

backend/main.ts TypeScript 
import { Hono } from 'npm:hono';
import { cors } from 'npm:hono/cors';
import {
  createFlight,
  deleteFlight,
  getFlightById,
  initializeDatabase,
  listFlights,
  updateFlightStatus,
} from './db.ts';

const app = new Hono();
const sleep = (ms: number) => new Promise((resolve) => setTimeout(resolve, ms));

app.use('*', cors({
  // Entwicklung: jedes Frontend auf localhost erlauben, egal auf welchem Port
  // (Vite weicht auf 5174, 5175, ... aus, wenn 5173 schon belegt ist)
  origin: (origin) =>
    /^http:\/\/(localhost|127\.0\.0\.1):\d+$/.test(origin) ? origin : null,
}));

app.get('/api/flights', async (c) => {
  await sleep(1000);
  const type = c.req.query('type');
  const status = c.req.query('status');
  const result = await listFlights(type ?? undefined, status ?? undefined);
  return c.json(result);
});

app.get('/api/flights/:id', async (c) => {
  const id = Number(c.req.param('id'));
  const flight = await getFlightById(id);
  if (!flight) return c.json({ error: 'Flug nicht gefunden' }, 404);
  return c.json(flight);
});

app.post('/api/flights', async (c) => {
  const body = await c.req.json();
  if (!body.flightNumber || !body.airline || !body.scheduledTime) {
    return c.json({ error: 'Pflichtfelder fehlen' }, 400);
  }
  const newFlight = await createFlight({
    flightNumber: body.flightNumber,
    airline: body.airline,
    type: body.type ?? 'departure',
    scheduledTime: body.scheduledTime,
    expectedTime: body.expectedTime,
    airport: body.airport,
    terminal: body.terminal ?? 'T1',
    gate: body.gate,
  });
  return c.json(newFlight, 201);
});

app.patch('/api/flights/:id', async (c) => {
  const id = Number(c.req.param('id'));
  const body = await c.req.json();
  if (!body.status) return c.json({ error: 'status fehlt' }, 400);
  const updated = await updateFlightStatus(id, body.status);
  if (!updated) return c.json({ error: 'Nicht gefunden' }, 404);
  return c.json(updated);
});

app.delete('/api/flights/:id', async (c) => {
  const id = Number(c.req.param('id'));
  const deleted = await deleteFlight(id);
  if (!deleted) return c.json({ error: 'Nicht gefunden' }, 404);
  return c.json(deleted);
});

await initializeDatabase();

Deno.serve({ port: 8000 }, app.fetch);
console.log('FlugBoard API (Drizzle + SQLite) läuft auf http://localhost:8000');

Projektschritt 2.8

Persistenz aktivieren

FlugBoard auf Drizzle + SQLite umstellen

Wir bauen das Backend aus Lektion 2.7 um. Das Frontend bleibt unverändert.

  1. backend/deno.json: Rechte für dev und start ergänzen (siehe oben).
  2. backend/data.ts: export let flights in export const seedFlights umbenennen.
  3. backend/db.ts anlegen: Tabelle, mapFlight, initializeDatabase und die fünf Abfragefunktionen – auch updateFlightStatus, sonst funktioniert die Statusänderung aus Lektion 2.3 nicht mehr.
  4. backend/main.ts: Funktionen aus db.ts verwenden, Handler async machen, vor Deno.serve await initializeDatabase() aufrufen.
  5. backend/.gitignore mit der Zeile flugboard.db anlegen – die Datei entsteht beim ersten Start von selbst und gehört nicht ins Repository.
  6. Im Ordner backend/ mit deno task dev starten, im Frontend einen Flug anlegen und einen Status ändern, Backend neu starten: Beides muss erhalten bleiben.

Häufige Fehler

Fehlende Deno-Rechte (NotCapable)

Die Datenbank-Datei braucht Lese- und Schreibrechte. Zusätzlich lädt der SQLite-Treiber libsql eine native Bibliothek und liest dabei Umgebungsvariablen und Systeminfos. Fehlt ein Recht, bricht der Start mit „NotCapable: Requires env access …“ (bzw. sys) ab oder Deno fragt im Terminal nach.

Starte Deno mit --allow-net --allow-read --allow-write --allow-env --allow-sys --allow-ffi. Am einfachsten trägst du die Rechte in backend/deno.json ein und startest mit deno task dev.

Geänderte Daten sind nach dem Neustart weg

Der Pfad file:./flugboard.db gilt relativ zu dem Ordner, in dem Deno gestartet wird. Wer z.B. aus dem Projektordner deno run ... backend/main.ts startet, bekommt dort eine zweite, neue Datenbank mit den Beispielflügen.

Immer im Ordner backend/ mit deno task dev starten.

status ändern liefert 500, Backend meldet flights is not defined

Beim Umbau wurden GET, POST und DELETE umgestellt, der PATCH-Endpunkt aus Lektion 2.3 greift aber noch auf das alte Array zu.

updateFlightStatus in db.ts anlegen und im PATCH-Handler verwenden.

Aufgaben

1 Filter mit SQL testen

Teste ?type=departure und ?status=delayed gegen die DB.

2 Neuen Flug speichern

Lege einen Flug an, ändere bei einem anderen den Status und verifiziere, dass beides nach einem Neustart des Backends weiterhin gilt.

★ Sortieren in der Datenbank

Bisher sortiert das Frontend die Flüge (sortByTime in useFlightFilters). Lass die Datenbank sortieren: In listFlights an beide Abfragen .orderBy(asc(flightsTable.scheduledTime)) anhängen (asc zusätzlich aus npm:drizzle-orm importieren). Prüfe mit curl http://localhost:8000/api/flights, dass die Liste nach Zeit sortiert ankommt.

Quiz

5 Fragen · zum Aufklappen klicken

Frage 1 Warum stellen wir das Backend auf eine Datenbank um?

Erklärung: Bis Lektion 2.7 lagen die Flüge in einem Array im RAM – jede Änderung war nach einem Neustart weg.

Frage 2 Was ist eine Besonderheit von SQLite?

Erklärung: Ideal für kleine Projekte und Entwicklung. Drizzle beschreibt die Tabellen dazu in TypeScript.

Frage 3 Warum braucht es eine Funktion wie mapFlight, die eine Datenbankzeile in ein Flight-Objekt umwandelt?

Erklärung: Die Umwandlung hält das Datenmodell der API gleich, egal wie die Datenbank intern speichert.

Frage 4 Muss das React-Frontend nach der Umstellung auf Drizzle geändert werden?

Erklärung: Eine stabile API entkoppelt Frontend und Backend. Das Frontend greift nie direkt auf die Datenbank zu.

Frage 5 Welche Drizzle-Operationen ersetzen die Array-Methoden filter, push, Ändern und splice?

Erklärung: Alle Abfragen sind asynchron; deshalb werden die Hono-Handler async.
