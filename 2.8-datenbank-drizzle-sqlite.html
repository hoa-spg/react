Lektion 2.8 — Teil 2: React Praxis

Datenbankzugriff mit Drizzle + SQLite

Backend ca. 90 min

Lernziele

  • Verstehen, warum In-Memory-Daten für echte Apps nicht ausreichen
  • Ein Deno+Hono-Backend auf Drizzle ORM und SQLite umstellen
  • Seed-Daten einmalig in die Datenbank schreiben
  • GET/POST/DELETE-Endpunkte gegen die Datenbank ausführen

Warum jetzt eine Datenbank?

Bis Lektion 2.7 haben wir die Flugdaten im RAM gehalten. Das ist für den Einstieg perfekt, aber nach jedem Server-Neustart sind alle Änderungen weg. In dieser Lektion wechseln wir auf eine echte Persistenzschicht mit SQLite und Drizzle.

ℹ
Didaktischer Fokus

Wir behalten die API-Struktur aus den vorherigen Lektionen bei. Nur die Datenquelle ändert sich von Array-Operationen auf SQL-Operationen.

Drizzle + SQLite im Deno-Backend

Das Beispielprojekt liegt unter beispiele/2.8. Der Backend-Teil nutzt Drizzle mit einer lokalen SQLite-Datei flugboard.db.

backend/db.ts (Auszug) TypeScript 
import { createClient } from 'npm:@libsql/client';
import { drizzle } from 'npm:drizzle-orm/libsql';
import { sqliteTable, integer, text } from 'npm:drizzle-orm/sqlite-core';

const client = createClient({ url: 'file:./flugboard.db' });
const db = drizzle(client);

export const flightsTable = sqliteTable('flights', {
  id: integer('id').primaryKey(),
  flightNumber: text('flight_number').notNull(),
  airline: text('airline').notNull(),
  type: text('type').notNull(),
  scheduledTime: text('scheduled_time').notNull(),
  expectedTime: text('expected_time'),
  status: text('status').notNull(),
  airport: text('airport').notNull(),
  terminal: text('terminal').notNull(),
  gate: text('gate'),
});

Initialisierung und Seed

Beim Start wird die Tabelle erzeugt (falls sie noch nicht existiert). Wenn die Tabelle leer ist, werden die Seed-Flüge eingefügt.

backend/db.ts – initializeDatabase TypeScript 
export const initializeDatabase = async () => {
  await client.execute(`
    CREATE TABLE IF NOT EXISTS flights (
      id INTEGER PRIMARY KEY,
      flight_number TEXT NOT NULL,
      airline TEXT NOT NULL,
      type TEXT NOT NULL,
      scheduled_time TEXT NOT NULL,
      expected_time TEXT,
      status TEXT NOT NULL,
      airport TEXT NOT NULL,
      terminal TEXT NOT NULL,
      gate TEXT
    )
  `);

  const countResult = await client.execute('SELECT COUNT(*) as count FROM flights');
  const count = Number(countResult.rows[0]?.count ?? 0);
  if (count === 0) {
    // seedFlights in DB schreiben
  }
};

Routen bleiben gleich

Die API-Endpunkte bleiben identisch. Dadurch muss das React-Frontend nicht umgebaut werden. Die in 2.7 eingeführte Router-Struktur bleibt ebenfalls: separate Seiten für Abflüge und Ankünfte, mit Suche + Statusfilter (kein zusätzlicher Typ-Filter).

  • GET /api/flights mit optionalen Query-Parametern
  • GET /api/flights/:id
  • POST /api/flights
  • DELETE /api/flights/:id
✓
Wichtiger Architekturpunkt

Erst die API stabilisieren, dann die Datenquelle austauschen. So bleibt die Frontend- Integration robust und testbar.

Projektschritt 2.8

Persistenz aktivieren

FlugBoard auf Drizzle + SQLite umstellen

  1. Starte das Backend: cd beispiele/2.8/backend && deno task dev
  2. Teste die API: http://localhost:8000/api/flights
  3. Lege einen neuen Flug per POST an und starte den Server neu
  4. Prüfe: der neue Flug bleibt in der Liste erhalten

Häufige Fehler

Keine Schreibrechte auf DB-Datei

Starte Deno mit --allow-read --allow-write. In dieser Lektion sind die Rechte bereits in backend/deno.json eingetragen.

Tabelle wird immer wieder neu angelegt

Achte auf den konstanten DB-Pfad file:./flugboard.db im Backend-Ordner.

Aufgaben

1 Filter mit SQL testen

Teste ?type=departure und ?status=delayed gegen die DB.

2 Neuen Flug speichern

Lege einen Flug an und verifiziere, dass er nach Neustart weiterhin existiert.

★ PATCH-Endpunkt bauen

Erweitere das Backend um PATCH /api/flights/:id für Status-Änderungen.
