Lektion 3.6 — Teil 3: Next.js

Deployment

Next.js ca. 75 min

Lernziele

Nach dieser Lektion kannst du folgendes:

  • Eine Next.js-Anwendung auf Vercel deployen
  • Umgebungsvariablen mit .env.local verwalten und sicher einsetzen
  • Den Unterschied zwischen NEXT_PUBLIC_-Variablen und Server-only-Variablen erklären
  • Die Build-Ausgabe von npm run build lesen und interpretieren
  • CI/CD mit Vercel und GitHub verstehen und einrichten
  • Eine Produktionscheckliste vor dem Go-Live durcharbeiten

1 — Was ist Vercel?

Vercel ist das Unternehmen hinter Next.js und bietet gleichzeitig die optimale Hosting-Plattform dafür. Während du Next.js theoretisch überall hosten kannst (Node-Server, Docker, statisch), ist Vercel so tief in den Framework-Entwicklungsprozess integriert, dass es das einfachste und leistungsfähigste Deployment bietet.

Vercel-Features im Überblick

Feature Beschreibung Relevanz für FlugBoard
Auto-Deployments Jeder Git-Push auf main triggert automatisch einen Build Kein manuelles Deployment nötig
Edge CDN Statische Seiten weltweit verteilt ausgeliefert Schnelle Ladezeiten für alle Nutzer
Serverless Functions API Routes laufen als isolierte Funktionen Unsere route.ts-Handler
Preview Deployments Jeder Pull Request bekommt eine eigene URL Testen vor dem Merge
Analytik Performance-Metriken direkt im Dashboard Core Web Vitals überwachen
Free Tier Kostenlos für private Projekte Ideal für Kurs und Demos

Der Deployment-Ablauf

CI/CD Pipeline mit Vercel Bash 
# 1. Du pushst Code auf GitHub

# 2. Vercel erkennt den Push automatisch
# 3. Build startet (npm run build)

# 5. Statische Seiten werden vorgerendert

# 7. Neue Version ist live unter https://flugboard.vercel.app
ℹ
Preview Deployments

Wenn du einen Pull Request auf GitHub eröffnest, erstellt Vercel automatisch eine temporäre URL für diesen Branch — z. B. https://flugboard-git-feature-xyz-yourname.vercel.app. So kannst du Änderungen testen und reviewen, bevor sie auf main landen. Das ist einer der größten Produktivitätsgewinne im Team-Workflow.

2 — Umgebungsvariablen sicher verwalten

Umgebungsvariablen speichern Konfigurationswerte, die sich zwischen Entwicklung und Produktion unterscheiden — API-Keys, Datenbank-Verbindungsstrings, externe Service-URLs. In Next.js gibt es verschiedene Dateien für verschiedene Umgebungen.

Datei-Hierarchie

Env-Dateien und ihre Priorität (höchste zuerst) Bash 
.env.local          # Höchste Priorität – NIE in Git! Lokale Overrides
.env.development    # Nur im Development-Modus (npm run dev)
.env.production     # Nur im Production-Modus (npm run build)
.env                # Alle Umgebungen, kann in Git eingecheckt werden
.env.local — Lokale Entwicklungsvariablen Bash 
# ACHTUNG: Diese Datei NIEMALS in Git commiten!
# Sie enthält Secrets und persönliche Konfiguration.

# Datenbankzugriff (nur Server-seitig)
# Lokal (Kapitel 12-17): SQLite-Datei
SQLITE_DB_PATH=./flugboard.sqlite

# Optional für Production mit Turso/libSQL
TURSO_DATABASE_URL=libsql://dein-projekt.turso.io
TURSO_AUTH_TOKEN=dein-token

# Externer API-Schlüssel (nur Server-seitig)
FLIGHT_DATA_API_KEY=sk_live_abc123xyz

# Interne API-URL (Server-seitig)
API_BASE_URL=http://localhost:3000/api
.env — Öffentliche Variablen (kann in Git) Bash 
# NEXT_PUBLIC_ Prefix = wird an den Browser gesendet
# Nur nicht-sensitive Konfiguration hier!

NEXT_PUBLIC_APP_NAME=FlugBoard
NEXT_PUBLIC_APP_VERSION=1.0.0
NEXT_PUBLIC_API_URL=http://localhost:3000

# In Produktion überschreiben:
# NEXT_PUBLIC_API_URL=https://flugboard.vercel.app

NEXT_PUBLIC_ vs. Server-only

Zugriff auf Env-Variablen TypeScript 
// ✅ Server Component: kann ALLE Variablen nutzen
export default async function ServerComponent() {
  const sqliteDb = process.env.SQLITE_DB_PATH;      // ✅ Server only
  const tursoUrl = process.env.TURSO_DATABASE_URL;  // ✅ Server only
  const apiKey   = process.env.FLIGHT_DATA_API_KEY; // ✅ Server only
  const appName  = process.env.NEXT_PUBLIC_APP_NAME; // ✅ auch Server
  // ...
}

// ⚠️ Client Component: nur NEXT_PUBLIC_ Variablen!
'use client';
export default function ClientComponent() {
  const appName = process.env.NEXT_PUBLIC_APP_NAME; // ✅ ok
  const sqliteDb = process.env.SQLITE_DB_PATH;      // ❌ undefined!
  // Server-only Variablen werden aus dem Client-Bundle entfernt.
}

.gitignore korrekt konfigurieren

.gitignore Bash 
# Dependencies
node_modules/

# Build-Ausgabe

# Umgebungsvariablen – KRITISCH!

⚠
Secrets nie in Git committen

Wenn du versehentlich .env.local in Git eingecheckt hast, reicht ein git rm --cached .env.local nicht aus — die Datei bleibt in der Git-Historie. Alle betroffenen Secrets müssen sofort rotiert (geändert) werden. Tools wie git-secrets oder GitHub's Secret Scanning können dabei helfen, solche Fehler früh zu erkennen.

3 — Build-Ausgabe analysieren

Bevor du deployest, solltest du immer npm run build lokal ausführen. Next.js bricht den Build ab, wenn es TypeScript-Fehler oder ESLint-Verstöße gibt — das schützt dich vor fehlerhaften Deployments.

Bedeutung der Symbole

Symbol Name Bedeutung
○ Static Statisch vorgerendert beim Build — schnellstmöglich
● SSG mit Data Statisch, aber mit Datenabruf beim Build (generateStaticParams)
ƒ Dynamic Dynamisch gerendert pro Request (SSR) oder hat dynamische Segmente
ISR Incremental Statisch, aber mit automatischer Revalidierung nach X Sekunden

TypeScript separat prüfen

Terminal — TypeScript ohne Build prüfen Bash 
# Nur TypeScript-Fehler prüfen, kein Build
npx tsc --noEmit

# ESLint separat ausführen
npx next lint

# Beides zusammen (empfohlen vor jedem Commit)
npx tsc --noEmit && npx next lint
✓
Build-Fehler lokal finden

Der lokale Dev-Server (npm run dev) zeigt viele Fehler nicht an, die erst beim Build auftauchen — zum Beispiel fehlende generateStaticParams-Rückgaben oder falsch konfiguriertes Caching. Führe daher immer einmal npm run build durch, bevor du deinen Code pusht.

Preview vs. Production Umgebung

In Vercel gibt es drei Umgebungen: Production (Branch main), Preview (alle anderen Branches / Pull Requests) und Development (lokal mit vercel env pull). Du kannst für jede Umgebung eigene Werte setzen — z. B. eine Test-Datenbank für Previews und die echte Datenbank nur für Production. Wichtig: Eine lokale SQLite-Datei ist auf Vercel nicht dauerhaft persistent.

5 — Produktionscheckliste

Bevor du FlugBoard öffentlich erreichbar machst, arbeite diese Checkliste Punkt für Punkt durch. Ein einziger übersehener Punkt kann zu Sicherheitslücken oder schlechter Performance führen.

✓
Produktionscheckliste
  • ☐ .env.local ist in .gitignore eingetragen
  • ☐ Keine Secrets oder API-Keys direkt im Quellcode
  • ☐ Alle NEXT_PUBLIC_-Variablen enthalten keine sensitiven Daten
  • ☐ npm run build schließt ohne Fehler ab
  • ☐ npx tsc --noEmit meldet keine TypeScript-Fehler
  • ☐ npx next lint zeigt keine Fehler
  • ☐ Alle Umgebungsvariablen sind im Vercel Dashboard konfiguriert
  • ☐ NEXT_PUBLIC_API_URL zeigt auf die Produktions-URL, nicht auf localhost
  • ☐ Keine console.log-Statements mit sensitiven Daten im Code
  • ☐ not-found.tsx für 404-Seiten vorhanden
  • ☐ error.tsx für Fehlerbehandlung vorhanden
  • ☐ Metadaten (title, description) für alle Seiten gesetzt

Localhost aus dem Code entfernen

Vorher: Hardcodierte localhost-URL TypeScript 
// ❌ FALSCH: Funktioniert nicht in Produktion!
const res = await fetch('http://localhost:3000/api/flights');
Nachher: Umgebungsvariable verwenden TypeScript 
// ✅ RICHTIG: Funktioniert in Entwicklung und Produktion
const baseUrl = process.env.NEXT_PUBLIC_API_URL ?? 'http://localhost:3000';
const res = await fetch(`${baseUrl}/api/flights`);

// Noch besser für Server Components: direkt importieren!
import { listFlights } from '@/lib/flights-db';
// Kein fetch nötig, kein URL-Problem.

Häufige Fehler

Fehler: .env.local versehentlich in Git commitet

Du hast .env.local zum Repository hinzugefügt. Die Datei ist jetzt in der Git-Historie und alle Secrets sind für jeden sichtbar, der Zugriff auf das Repository hat — auch nach dem Löschen.

Fix: Sofort alle betroffenen Secrets rotieren (neue API-Keys generieren, Passwörter ändern). Die Datei aus der Git-Historie entfernen: git rm --cached .env.local, dann .gitignore prüfen und git push. Für vollständiges Entfernen aus der Historie: git filter-branch oder das BFG Repo-Cleaner-Tool verwenden.

Fehler: NEXT_PUBLIC_-Prefix vergessen

Du definierst API_URL=https://... in .env und versuchst in einer Client Component mit process.env.API_URL darauf zuzugreifen. Der Wert ist undefined, weil Server-only-Variablen aus dem Client-Bundle entfernt werden.

Fix: Benenne die Variable in NEXT_PUBLIC_API_URL um. Alternativ: Wenn die Variable sensitiv ist, verwende sie nur in Server Components oder Route Handlers.

Fehler: Build-Fehler ignoriert und direkt gepusht

Du pushst Code auf main, ohne vorher npm run build lokal ausgeführt zu haben. Vercel versucht den Build, scheitert an TypeScript-Fehlern, und die Änderungen sind nicht live.

Fix: Gewöhne dir an, vor jedem Push einmalig npm run build auszuführen. Noch besser: Richte einen Git Pre-Push-Hook ein: echo "npm run build" > .git/hooks/pre-push && chmod +x .git/hooks/pre-push.

Fehler: localhost in Produktions-Umgebungsvariable

Du setzt NEXT_PUBLIC_API_URL=http://localhost:3000 in den Vercel-Produktions-Einstellungen. Alle API-Aufrufe von der Live-Seite zeigen auf localhost, das im Browser des Besuchers nicht existiert.

Fix: Setze in Vercel für die Production-Umgebung die vollständige Live-URL: NEXT_PUBLIC_API_URL=https://flugboard.vercel.app. localhost nur in der Development-Umgebung verwenden.

Aufgaben

Aufgabe 1 .env.local einrichten und URLs ersetzen

Bereite das Projekt für verschiedene Umgebungen vor.

  • Erstelle .env.local mit NEXT_PUBLIC_API_URL und NEXT_PUBLIC_APP_NAME
  • Prüfe, dass .env.local in .gitignore steht
  • Ersetze alle hardcodierten localhost:3000-URLs durch die Umgebungsvariable
  • Starte den Dev-Server neu und prüfe, ob alles noch funktioniert
Aufgabe 2 npm run build durchführen und analysieren

Führe einen vollständigen Produktions-Build durch und verstehe die Ausgabe.

  • Führe npm run build aus und behebe alle auftretenden Fehler
  • Notiere dir, welche Seiten als ○ Static und welche als ƒ Dynamic markiert sind
  • Führe npx tsc --noEmit aus und prüfe auf TypeScript-Fehler
  • Diskutiere: Warum ist /flight/[id] dynamisch, aber /departures statisch?
Aufgabe 3 GitHub Repository erstellen und Code pushen

Bereite das Repository für das Deployment vor.

  • Erstelle ein neues public Repository auf GitHub.com
  • Initialisiere Git lokal und erstelle einen ersten Commit
  • Push den Code auf GitHub (main-Branch)
  • Prüfe auf GitHub, dass .env.local nicht im Repository enthalten ist
Aufgabe 4 — Bonus FlugBoard auf Vercel deployen und Live-URL teilen

Bringe FlugBoard ans Netz und teile die Live-URL mit der Klasse.

  • Verbinde das GitHub-Repository mit einem Vercel-Account
  • Konfiguriere alle Umgebungsvariablen für die Production-Umgebung

  • Teste alle Seiten auf der Live-URL: Startseite, Abflüge, Ankünfte, Detailseite
