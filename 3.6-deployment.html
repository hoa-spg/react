Lektion 3.6 — Teil 3: Next.js

Deployment

Next.js ca. 75 min

Lernziele

Nach dieser Lektion kannst du folgendes:

  • Entwicklungs- und Produktionsbetrieb unterscheiden und eine passende Hosting-Art wählen
  • Einen Produktions-Build erstellen und die Build-Ausgabe lesen
  • Umgebungsvariablen verwenden und NEXT_PUBLIC_- von Server-Variablen unterscheiden
  • FlugBoard auf einem eigenen Linux-Server mit Node.js betreiben
  • Eine Produktionscheckliste vor dem Go-Live durcharbeiten

1 — Von der Entwicklung in den Betrieb

Bisher lief FlugBoard mit npm run dev. Der Entwicklungsserver übersetzt jede Seite erst beim Aufruf, zeigt Fehler im Browser an und lädt bei jeder Änderung neu — praktisch zum Entwickeln, aber langsam. Für den Betrieb gibt es zwei andere Befehle:

  • npm run build (next build) übersetzt und optimiert die ganze App einmal und rendert statische Seiten vor. Das Ergebnis liegt im Ordner .next/.
  • npm start (next start) startet einen schnellen Produktionsserver, der dieses Ergebnis ausliefert.

Wo läuft FlugBoard?

Unsere App braucht einen laufenden Node.js-Server (Server Components, Route Handlers, Server Actions) und speichert seit Lektion 2.8 in einer SQLite-Datei. Das entscheidet über die Hosting-Art:

Hosting-Art Beispiele Passt für FlugBoard?
Eigener Node-Server Linux-VM, Schulserver, Raspberry Pi Ja — die SQLite-Datei bleibt auf der Festplatte des Servers erhalten
Serverless-Plattform Vercel, Netlify Nur mit gehosteter Datenbank — das Dateisystem ist nicht dauerhaft, eine SQLite-Datei würde verloren gehen
Statisches Hosting GitHub Pages Nein — dort läuft kein Server-Code

Wir betreiben FlugBoard deshalb auf einem eigenen Linux-Server.

2 — Der Produktions-Build

Vor jedem Deployment läuft der Build zuerst lokal. Next.js prüft dabei auch die TypeScript-Typen und bricht bei Fehlern ab — so kommt fehlerhafter Code gar nicht erst auf den Server.

Terminal — Build von FlugBoard (gekürzt) Text 
npm run build

Route (app)                                 Size  First Load JS  Revalidate  Expire
┌ ○ /                                      171 B         106 kB         30s      1y
├ ○ /_not-found                            136 B         103 kB
├ ƒ /api/flights                           136 B         103 kB
├ ƒ /api/flights/[id]                      136 B         103 kB
├ ○ /arrivals                              983 B         107 kB         30s      1y
├ ○ /departures                            983 B         107 kB         30s      1y
└ ƒ /flight/[id]                           171 B         106 kB

○  (Static)   prerendered as static content
ƒ  (Dynamic)  server-rendered on demand
Symbol Bedeutung Im FlugBoard
○ Static Beim Build vorgerendert. Mit Wert in der Spalte Revalidate wird die Seite danach höchstens so oft neu erzeugt (Lektion 3.3). Startseite, Abflüge, Ankünfte (30 s)
ƒ Dynamic Wird bei jedem Request auf dem Server gerendert. Detailseite (eigene ID pro Aufruf), Route Handlers

Danach lässt sich der Produktionsbetrieb lokal ausprobieren:

Terminal Bash 
npm start             # Produktionsserver auf http://localhost:3000
PORT=8080 npm start   # anderer Port
✓
Build-Fehler lokal finden

Manche Fehler zeigt npm run dev nicht, weil der Entwicklungsserver nur die aufgerufenen Seiten übersetzt. Führe deshalb vor jedem Push einmal npm run build aus — und die E2E-Tests aus Lektion 3.5.

3 — Umgebungsvariablen

Manche Einstellungen unterscheiden sich zwischen deinem Rechner und dem Server — Pfade, Passwörter, API-Schlüssel. Sie gehören nicht in den Code, sondern in Umgebungsvariablen. Im Code liest man sie mit process.env.NAME; fehlt die Variable, ist der Wert undefined.

Beispiel: Pfad zur Datenbank

Bisher legt FlugBoard flugboard.sqlite im Projektordner an. Auf dem Server soll die Datei in einem eigenen Ordner liegen, damit sie bei einem Update des Codes nicht verloren geht. Dafür reichen zwei Zeilen in der DB-Schicht:

src/lib/flights-db.ts TypeScript 
// ... (Imports, Tabelle, Seed-Daten wie bisher)

declare global {
  // eslint-disable-next-line no-var
  var __flugboardDb: Database.Database | undefined;
}

// Pfad zur Datenbankdatei: auf dem Server per Umgebungsvariable einstellbar
const dbPath = process.env.DATABASE_PATH ?? 'flugboard.sqlite';
const sqlite = global.__flugboardDb ?? new Database(dbPath);
if (!global.__flugboardDb) {
  global.__flugboardDb = sqlite;
}

// ... (Rest unverändert)

Ohne Variable bleibt alles wie bisher. Mit DATABASE_PATH=/var/lib/flugboard/flugboard.sqlite verwendet die App die Datei in diesem Ordner.

Variablen setzen

Terminal — Variable für einen Befehl setzen Bash 
DATABASE_PATH=./test.sqlite npm run dev

Bequemer sind Dateien im Projektordner, die Next.js beim Start automatisch einliest:

Env-Dateien (wichtigste zuerst) Text 
.env.local          # lokale Einstellungen und Geheimnisse – nie in Git!
.env.development    # nur bei npm run dev
.env.production     # nur bei npm run build / npm start
.env                # für alle Umgebungen, darf in Git
.env.local Text 
DATABASE_PATH=./flugboard-lokal.sqlite

Damit .env.local nie im Repository landet, kommt sie in die .gitignore:

.gitignore (Ergänzung) Text 
# Lokale Umgebungsvariablen (können Geheimnisse enthalten)
.env*.local

NEXT_PUBLIC_ vs. Server-only

  • Normale Variablen wie DATABASE_PATH gibt es nur auf dem Server: in Server Components, Route Handlers, Server Actions und der DB-Schicht.
  • Variablen mit dem Präfix NEXT_PUBLIC_ (z. B. NEXT_PUBLIC_APP_NAME) baut Next.js beim Build in den JavaScript-Code für den Browser ein. Nur sie sind auch in Client Components verfügbar — und damit für jeden Besucher sichtbar.
⚠
Geheimnisse nie in Git und nie mit NEXT_PUBLIC_

Passwörter und API-Schlüssel gehören in .env.local bzw. auf den Server, nie in den Code und nie in eine NEXT_PUBLIC_-Variable. Wurde eine solche Datei doch committet, bleibt sie in der Git-Historie — dann müssen die Geheimnisse sofort geändert werden.

4 — Deployment auf einem Linux-Server

Voraussetzung ist ein Linux-Server mit SSH-Zugang, auf dem Node.js (LTS) und Git installiert sind. Der Code kommt über ein Git-Repository auf den Server — deshalb zuerst lokal committen und auf GitHub pushen, inklusive package-lock.json.

Erstes Deployment

Terminal — auf dem Server Bash 
# Code holen
git clone https://github.com/DEIN-NAME/flugboard.git
cd flugboard

# Abhängigkeiten exakt nach package-lock.json installieren
npm ci

# Ordner für die Datenbank anlegen und Variable setzen
mkdir -p /var/lib/flugboard
export DATABASE_PATH=/var/lib/flugboard/flugboard.sqlite

# Bauen und starten
npm run build
npm start
  • npm ci installiert genau die Versionen aus package-lock.json — anders als npm install ändert es die Datei nie. So läuft auf dem Server derselbe Stand wie lokal.
  • export setzt die Variable für alle folgenden Befehle im Terminal. Auch der Build braucht sie, weil er die statischen Seiten mit Daten aus der Datenbank vorrendert.
  • Der Ordner /var/lib/flugboard muss für den Benutzer beschreibbar sein, unter dem die App läuft.

Dauerbetrieb mit systemd

Mit npm start im Terminal endet der Server, sobald du dich abmeldest. Auf Linux übernimmt systemd den Dauerbetrieb: Es startet die App beim Hochfahren und nach einem Absturz neu. Dafür legt man eine Dienst-Datei an:

/etc/systemd/system/flugboard.service INI 
[Unit]
Description=FlugBoard (Next.js)
After=network.target

[Service]
User=flugboard
WorkingDirectory=/home/flugboard/flugboard
Environment=DATABASE_PATH=/var/lib/flugboard/flugboard.sqlite
Environment=PORT=3000
ExecStart=/usr/bin/npm start
Restart=always

[Install]
WantedBy=multi-user.target
Terminal — Dienst aktivieren Bash 
sudo systemctl daemon-reload            # neue Dienst-Datei einlesen
sudo systemctl enable --now flugboard   # jetzt und bei jedem Hochfahren starten
sudo systemctl status flugboard         # läuft der Dienst?
journalctl -u flugboard -f              # Ausgaben (Logs) live ansehen

Updates einspielen

Terminal — auf dem Server Bash 
cd ~/flugboard
git pull
npm ci
DATABASE_PATH=/var/lib/flugboard/flugboard.sqlite npm run build
sudo systemctl restart flugboard
ℹ
Ausblick: Reverse Proxy und HTTPS

Im echten Betrieb läuft die App nicht direkt auf Port 80/443, sondern hinter einem Reverse Proxy wie Caddy oder nginx. Er nimmt die Anfragen aus dem Internet an, kümmert sich um HTTPS-Zertifikate und leitet an localhost:3000 weiter.

5 — Produktionscheckliste

✓
Vor dem Go-Live
  • ☐ npm run build läuft lokal ohne Fehler
  • ☐ npm run test:e2e meldet nur bestandene Tests
  • ☐ Keine Passwörter oder API-Schlüssel im Code, .env*.local steht in .gitignore
  • ☐ NEXT_PUBLIC_-Variablen enthalten nichts Geheimes
  • ☐ package-lock.json ist committet
  • ☐ DATABASE_PATH zeigt auf einen Ordner außerhalb des Projekts; von der Datei gibt es eine Sicherung
  • ☐ not-found.tsx und error.tsx sind vorhanden

Projektschritt

Projektschritt 3.6

FlugBoard in Betrieb nehmen

Im letzten Projektschritt von Teil 3 ändern sich am Code nur zwei Zeilen. Der Rest ist Betrieb: bauen, auf den Server bringen, dauerhaft starten.

  1. Umgebungsvariable: In src/lib/flights-db.ts den Pfad aus DATABASE_PATH lesen (Abschnitt 3) und .env*.local in .gitignore eintragen.
  2. Lokal prüfen: npm run build und npm start ausführen, die Build-Ausgabe lesen und die E2E-Tests laufen lassen.
  3. Repository: Projekt mit package-lock.json auf GitHub pushen.
  4. Server: Klonen, npm ci, mit DATABASE_PATH bauen und starten (Abschnitt 4).
  5. Dauerbetrieb: systemd-Dienst einrichten. Test: einen Flug anlegen, den Dienst neu starten — der Flug ist noch da.

Steht kein Server zur Verfügung, lassen sich die Schritte 4 und 5 auch auf dem eigenen Rechner oder in einer virtuellen Maschine nachvollziehen.

Häufige Fehler

4 Fehler · zum Aufklappen klicken
Fehler: Could not find a production build

npm start bricht sofort ab, weil im Ordner .next/ noch kein Build liegt.

Fix: Zuerst npm run build, dann npm start — auch nach jedem git pull.

Fehler: Neue Flüge nach einem Update verschwunden

Die Datenbank lag im Projektordner. Beim neuen Klonen oder Aufräumen des Ordners wurde sie gelöscht.

Fix: DATABASE_PATH auf einen Ordner außerhalb des Projekts setzen und die Datei regelmäßig sichern.

Fehler: App läuft nur, solange das Terminal offen ist

Nach dem Abmelden von der SSH-Verbindung ist die Seite nicht mehr erreichbar.

Fix: Die App als systemd-Dienst betreiben (Abschnitt 4).

Fehler: NEXT_PUBLIC_-Präfix vergessen

Eine Client Component liest process.env.APP_NAME und bekommt undefined.

Fix: Werte für den Browser heißen NEXT_PUBLIC_APP_NAME — aber nur, wenn sie nicht geheim sind. Nach einer Änderung neu bauen, weil sie beim Build eingesetzt werden.

Quiz

5 Fragen · zum Aufklappen klicken

Frage 1 Warum betreiben wir das FlugBoard auf einem eigenen Node-Server und nicht auf GitHub Pages?

Mehrere Antworten sind richtig.

Erklärung: Das FlugBoard führt Server-Code aus – Server Components, Route Handlers, Server Actions – und schreibt in eine SQLite-Datei. GitHub Pages liefert nur statische Dateien aus, dort läuft kein Server-Code. Geschwindigkeit, HTTPS oder das Betriebssystem sind nicht der Grund.

Frage 2 Warum passt eine Serverless-Plattform wie Vercel nur eingeschränkt zum FlugBoard?

Erklärung: Mit einer gehosteten Datenbank wäre Serverless möglich. Auf einem eigenen Server bleibt die SQLite-Datei auf der Festplatte erhalten.

Frage 3 npm start meldet „Could not find a production build“. Was fehlt?

Erklärung: npm start startet den fertigen Build aus .next/. Der Build prüft außerdem die TypeScript-Typen.

Frage 4 Eine Client Component liest process.env.APP_NAME und bekommt undefined. Was stimmt?

Mehrere Antworten sind richtig.

Erklärung: Nur Variablen mit dem Präfix NEXT_PUBLIC_ werden in den Browser-Code eingebaut. Alle anderen sind nur im Server-Code lesbar – deshalb liefert process.env.APP_NAME in einer Client Component undefined. Groß-/Kleinschreibung oder Tests haben damit nichts zu tun.

Frage 5 Warum legt man die Datenbank auf dem Server über DATABASE_PATH außerhalb des Projektordners ab?

Erklärung: Liegt die Datenbank im Projektordner, gehen beim Aufräumen alle Änderungen verloren. Zusätzlich sollte man sie regelmäßig sichern.
