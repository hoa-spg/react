Lektion 2.9 — Teil 2: React Praxis

State Management mit Redux (Überblick)

Architektur ca. 35 min

Lernziele

  • Verstehen, wann globales State Management sinnvoll ist
  • Die Kernideen von Redux einordnen: Store, Actions, Reducer, Dispatch, Selector
  • Den unidirektionalen Datenfluss in Redux nachvollziehen
  • Die Rolle von Redux Toolkit in modernen React-Projekten kennen

Wichtiger Hinweis: kein eigenes Beispielprojekt

Diese Lektion hat kein eigenes Beispielprojekt unter beispiele/2.9. Wir arbeiten also nicht mit einem neuen Projektordner, zeigen aber bewusst mehrere konkrete Code-Ausschnitte, damit das Redux-Modell nicht zu abstrakt bleibt.

ℹ
Didaktischer Fokus

Nach Context, Router und Datenbank geht es jetzt um die Architekturfrage: Wie verwalten wir viel gemeinsamen Zustand sauber, testbar und vorhersehbar?

Warum überhaupt Redux?

In kleinen Apps reichen lokaler State und Context oft aus. In größeren Apps steigen jedoch Komplexität und Nebenwirkungen: viele Datenquellen, parallele Updates, Caching, Berechtigungen, Undo/Redo oder reproduzierbare Fehleranalyse.

  • Vorhersehbarkeit: Jede Zustandsänderung ist explizit beschrieben.
  • Nachvollziehbarkeit: Actions bilden eine klare Historie von Ereignissen.
  • Skalierbarkeit: Fachlogik wird zentral und konsistent organisiert.
  • Testbarkeit: Reducer sind reine Funktionen mit klaren Ein-/Ausgaben.

Kernbausteine im Redux-Modell

Baustein Aufgabe Merksatz
Store Zentrale Quelle des globalen States Single Source of Truth
Action Beschreibt ein Ereignis in der App „Was ist passiert?“
Reducer Leitet aus altem State + Action den neuen State ab Reine Funktion ohne Nebenwirkungen
Dispatch Sendet eine Action in den Store Startet den Update-Zyklus
Selector Liest abgeleitete Daten aus dem Store „Was braucht diese UI wirklich?“

So läuft ein Update in Redux ab

  1. Ein Nutzer-Ereignis tritt auf (z. B. Filter geändert, Flug gespeichert).
  2. Die UI löst eine Action aus.
  3. Der Store gibt Action + aktuellen State an den passenden Reducer.
  4. Der Reducer berechnet den neuen State deterministisch.
  5. Alle betroffenen Komponenten lesen den neuen Wert über Selectors.

Dieser Fluss bleibt immer gleich. Genau deshalb ist Redux bei komplexen Oberflächen gut debugbar und im Team leichter wartbar.

Code-Skizze: Store mit Redux Toolkit

Typischer Einstieg: ein zentraler Store, der alle fachlichen Slices kombiniert.

src/store/index.ts (Skizze) TypeScript 
import { configureStore } from '@reduxjs/toolkit';
import flightsReducer from './flights-slice';
import filterReducer from './filter-slice';

export const store = configureStore({
  reducer: {
    flights: flightsReducer,
    filter: filterReducer,
  },
});

export type RootState = ReturnType<typeof store.getState>;
export type AppDispatch = typeof store.dispatch;

Code-Skizze: Slice mit Actions + Reducer

Ein Slice kapselt den State-Bereich, die Action Creator und den Reducer an einer Stelle.

src/store/flights-slice.ts (Skizze) TypeScript 
import { createSlice, PayloadAction } from '@reduxjs/toolkit';

type Flight = { id: number; flightNumber: string; status: string };

type FlightsState = {
  items: Flight[];
  loading: boolean;
};

const initialState: FlightsState = {
  items: [],
  loading: false,
};

const flightsSlice = createSlice({
  name: 'flights',
  initialState,
  reducers: {
    flightsRequested(state) {
      state.loading = true;
    },
    flightsReceived(state, action: PayloadAction<Flight[]>) {
      state.items = action.payload;
      state.loading = false;
    },
    flightStatusChanged(
      state,
      action: PayloadAction<{ id: number; status: string }>
    ) {
      const flight = state.items.find((f) => f.id === action.payload.id);
      if (flight) flight.status = action.payload.status;
    },
  },
});

export const {
  flightsRequested,
  flightsReceived,
  flightStatusChanged,
} = flightsSlice.actions;

export default flightsSlice.reducer;

Code-Skizze: Nutzung in einer React-Komponente

Die UI liest Daten mit Selectors und löst Änderungen per Dispatch aus.

src/features/flight-board.tsx (Skizze) TSX 
import { useDispatch, useSelector } from 'react-redux';
import type { RootState, AppDispatch } from '../store';
import { flightStatusChanged } from '../store/flights-slice';

export function FlightBoard() {
  const dispatch = useDispatch<AppDispatch>();
  const flights = useSelector((state: RootState) => state.flights.items);
  const delayedCount = useSelector(
    (state: RootState) =>
      state.flights.items.filter((f) => f.status === 'delayed').length
  );

  return (
    <section>
      <h2>Verspätete Flüge: {delayedCount}</h2>
      {flights.map((f) => (
        <button
          key={f.id}
          onClick={() =>
            dispatch(flightStatusChanged({ id: f.id, status: 'boarding' }))
          }
        >
          {f.flightNumber} → {f.status}
        </button>
      ))}
    </section>
  );
}

Wie würde das im FlugBoard aussehen?

Der globale State könnte in fachliche Bereiche getrennt werden, zum Beispiel Flugdaten, aktive Filter, UI-Status (Loading/Errors) und Nutzerkontext.

  • Flights: Liste, Sortierung, Status-Änderungen, letzte Aktualisierung
  • Filter: Terminal, Status, Suchbegriff, Sortiermodus
  • UI: Ladezustände pro Bereich, Fehlerzustände, offene Dialoge
  • Session: Rollen/Permissions und evtl. Feature-Flags
💡
Redux Toolkit statt „klassischem“ Redux

In aktuellen Projekten wird fast immer Redux Toolkit eingesetzt, weil es Boilerplate reduziert und robuste Standardmuster mitliefert.

Häufige Architekturfehler

Zu früh Redux einführen

Erst mit lokalem State + Context starten. Redux einführen, wenn Komplexität und Teamgröße den Mehraufwand wirklich rechtfertigen.

Zu viel in den globalen Store legen

Kurzlebiger UI-State bleibt lokal. Global nur Zustand, den mehrere Bereiche wirklich teilen oder nachvollziehbar versionieren müssen.

Store als Ersatz für API-Design missbrauchen

Redux ersetzt kein Backend-Konzept. Eine saubere API und Datenmodellierung bleiben weiterhin entscheidend.

Aufgaben (ohne eigenes Projekt)

1 State-Inventur

Liste für FlugBoard auf, welche Zustände lokal bleiben und welche global werden sollten.

2 Action-Sprache

Formuliere fünf fachliche Ereignisse als Actions und ordne sie einem Slice zu.

★ Team-Entscheidung

Definiert Kriterien, ab wann ihr von Context auf Redux Toolkit wechseln würdet, und skizziert dafür 3 konkrete Migrationsschritte.
