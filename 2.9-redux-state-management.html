Lektion 2.9 — Teil 2: React Praxis

State Management mit Redux (Überblick)

Architektur ca. 35 min

Lernziele

  • Verstehen, wann globales State Management sinnvoll ist
  • Die Kernideen von Redux einordnen: Store, Actions, Reducer, Dispatch, Selector
  • Den unidirektionalen Datenfluss in Redux nachvollziehen
  • Die Rolle von Redux Toolkit in modernen React-Projekten kennen

Wichtiger Hinweis: kein eigenes Beispielprojekt

Diese Lektion hat kein eigenes Beispielprojekt unter beispiele/2.9. Wir arbeiten also nicht mit einem neuen Projektordner, zeigen aber bewusst mehrere konkrete Code-Ausschnitte, damit das Redux-Modell nicht zu abstrakt bleibt.

ℹ
Didaktischer Fokus

Nach Context, Router und Datenbank geht es jetzt um die Architekturfrage: Wie verwalten wir viel gemeinsamen Zustand sauber, testbar und vorhersehbar?

Warum überhaupt Redux?

In kleinen Apps reichen lokaler State und Context oft aus. In größeren Apps steigen jedoch Komplexität und Nebenwirkungen: viele Datenquellen, parallele Updates, Caching, Berechtigungen, Undo/Redo oder reproduzierbare Fehleranalyse.

  • Vorhersehbarkeit: Jede Zustandsänderung ist explizit beschrieben.
  • Nachvollziehbarkeit: Actions bilden eine klare Historie von Ereignissen.
  • Skalierbarkeit: Fachlogik wird zentral und konsistent organisiert.
  • Testbarkeit: Reducer sind reine Funktionen mit klaren Ein-/Ausgaben.

Kernbausteine im Redux-Modell

Baustein Aufgabe Merksatz
Store Zentrale Quelle des globalen States Single Source of Truth
Action Beschreibt ein Ereignis in der App „Was ist passiert?“
Reducer Leitet aus altem State + Action den neuen State ab Reine Funktion ohne Nebenwirkungen
Dispatch Sendet eine Action in den Store Startet den Update-Zyklus
Selector Liest abgeleitete Daten aus dem Store „Was braucht diese UI wirklich?“

So läuft ein Update in Redux ab

  1. Ein Nutzer-Ereignis tritt auf (z. B. Filter geändert, Flug gespeichert).
  2. Die UI löst eine Action aus.
  3. Der Store gibt Action + aktuellen State an den passenden Reducer.
  4. Der Reducer berechnet den neuen State deterministisch.
  5. Alle betroffenen Komponenten lesen den neuen Wert über Selectors.

Dieser Fluss bleibt immer gleich. Genau deshalb ist Redux bei komplexen Oberflächen gut debugbar und im Team leichter wartbar.

Code-Skizze: Store mit Redux Toolkit

Typischer Einstieg: ein zentraler Store, der alle fachlichen Slices kombiniert.

src/store/index.ts (Skizze) TypeScript 
import { configureStore } from '@reduxjs/toolkit';
import flightsReducer from './flights-slice';
import filterReducer from './filter-slice';

export const store = configureStore({
  reducer: {
    flights: flightsReducer,
    filter: filterReducer,
  },
});

export type RootState = ReturnType<typeof store.getState>;
export type AppDispatch = typeof store.dispatch;

Code-Skizze: Slice mit Actions + Reducer

Ein Slice kapselt den State-Bereich, die Action Creator und den Reducer an einer Stelle. Die Typen Flight und FlightStatus kommen wie im FlugBoard aus src/types/flight.ts.

src/store/flights-slice.ts (Skizze) TypeScript 
import { createSlice, PayloadAction } from '@reduxjs/toolkit';
import { Flight, FlightStatus } from '../types/flight';

type FlightsState = {
  items: Flight[];
  loading: boolean;
};

const initialState: FlightsState = {
  items: [],
  loading: false,
};

const flightsSlice = createSlice({
  name: 'flights',
  initialState,
  reducers: {
    flightsRequested(state) {
      state.loading = true;
    },
    flightsReceived(state, action: PayloadAction<Flight[]>) {
      state.items = action.payload;
      state.loading = false;
    },
    flightStatusChanged(
      state,
      action: PayloadAction<{ id: number; status: FlightStatus }>,
    ) {
      // Immer-Magie: sieht aus wie Mutation, erzeugt aber einen neuen State
      const flight = state.items.find((f) => f.id === action.payload.id);
      if (flight) flight.status = action.payload.status;
    },
  },
});

export const {
  flightsRequested,
  flightsReceived,
  flightStatusChanged,
} = flightsSlice.actions;

export default flightsSlice.reducer;

Code-Skizze: Nutzung in einer React-Komponente

Die UI liest Daten mit Selectors und löst Änderungen per Dispatch aus.

src/features/delayed-flights-panel.tsx (Skizze) TSX 
import { useDispatch, useSelector } from 'react-redux';
import type { RootState, AppDispatch } from '../store';
import { flightStatusChanged } from '../store/flights-slice';

export function DelayedFlightsPanel() {
  const dispatch = useDispatch<AppDispatch>();
  const flights = useSelector((state: RootState) => state.flights.items);
  const delayedCount = useSelector(
    (state: RootState) =>
      state.flights.items.filter((f) => f.status === 'delayed').length,
  );

  return (
    <section>
      <h2>Verspätete Flüge: {delayedCount}</h2>
      {flights.map((f) => (
        <button
          key={f.id}
          onClick={() =>
            dispatch(flightStatusChanged({ id: f.id, status: 'boarding' }))
          }
        >
          {f.flightNumber} → {f.status}
        </button>
      ))}
    </section>
  );
}

Wie würde das im FlugBoard aussehen?

Unser FlugBoard verwaltet seinen Zustand nach Lektion 2.8 an mehreren Stellen. So würde Redux Toolkit das übernehmen:

ZustandHeute (Lektion)Mit Redux Toolkit
Flugliste, Laden, Fehler, Polling useFlights im Layout, per <Outlet context> verteilt (2.5, 2.7) RTK Query: getFlights mit pollingInterval
Anlegen, Löschen, Status ändern Funktionen aus useFlights (POST/DELETE/PATCH, 2.2–2.5) RTK-Query-Mutations oder createAsyncThunk
Suche und Status-Filter useFlightFilters mit useLocalStorage (2.5) filter-Slice; das Speichern im Browser müsste man selbst anbinden
Einzelner Flug auf der Detailseite FlightDetailPage lädt per useParams (2.7) RTK Query getFlight(id), nutzt denselben Cache
Dark/Light-Theme ThemeContext (2.4) könnte in einen ui-Slice – bleibt aber besser Context, ändert sich selten
Formular offen/zu lokaler useState in FlightListPage (2.1) bleibt lokal – betrifft nur eine Komponente
💡
Fazit für unser Projekt

Für das FlugBoard reichen Context und Custom Hooks. Redux Toolkit lohnt sich, wenn viele Bereiche denselben Zustand lesen und ändern, wenn man Änderungen nachvollziehen muss (DevTools, Undo) oder wenn mehrere Leute an einer großen App arbeiten. In aktuellen Projekten wird dabei fast immer Redux Toolkit statt „klassischem“ Redux eingesetzt.

Und das Backend?

Der Reducer flightStatusChanged aus der Slice-Skizze ändert nur den Store. Das kennen wir aus Lektion 2.3: Ohne Speichern im Backend wäre die Änderung beim nächsten Laden wieder weg. Reducer dürfen aber keine Requests schicken – sie müssen reine Funktionen bleiben. Dafür gibt es asynchrone Actions mit createAsyncThunk:

src/store/flights-slice.ts (Ergänzung, Skizze) TypeScript 
// Asynchrone Action: erst PATCH ans Backend, dann den Store ändern
export const changeFlightStatus = createAsyncThunk(
  'flights/changeStatus',
  async ({ id, status }: { id: number; status: FlightStatus }) => {
    const res = await fetch(`http://localhost:8000/api/flights/${id}`, {
      method: 'PATCH',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ status }),
    });
    if (!res.ok) throw new Error('Fehler beim Ändern des Status');
    return (await res.json()) as Flight;
  },
);

  // im createSlice zusätzlich: auf das Ergebnis der asynchronen Action reagieren
  extraReducers: (builder) => {
    builder.addCase(changeFlightStatus.fulfilled, (state, action) => {
      const flight = state.items.find((f) => f.id === action.payload.id);
      if (flight) flight.status = action.payload.status;
    });
  },

Die Komponente ruft dann dispatch(changeFlightStatus({ id, status })) auf. Für das Laden mit Polling bräuchte man zusätzlich Thunks für GET, POST und DELETE.

Einfacher geht es mit RTK Query, das in Redux Toolkit enthalten ist. Es ist das Gegenstück zu unserem useFlights: Laden, Cache, Polling und das Neuladen nach Änderungen sind schon eingebaut.

src/store/flights-api.ts (Skizze) TypeScript 
import { createApi, fetchBaseQuery } from '@reduxjs/toolkit/query/react';
import { Flight, FlightStatus } from '../types/flight';

export const flightsApi = createApi({
  reducerPath: 'flightsApi',
  baseQuery: fetchBaseQuery({ baseUrl: 'http://localhost:8000/api' }),
  tagTypes: ['Flight'],
  endpoints: (build) => ({
    getFlights: build.query<Flight[], void>({
      query: () => '/flights',
      providesTags: ['Flight'],
    }),
    updateFlightStatus: build.mutation<Flight, { id: number; status: FlightStatus }>({
      query: ({ id, status }) => ({
        url: `/flights/${id}`,
        method: 'PATCH',
        body: { status },
      }),
      invalidatesTags: ['Flight'], // danach lädt getFlights automatisch neu
    }),
  }),
});

export const { useGetFlightsQuery, useUpdateFlightStatusMutation } = flightsApi;
src/store/index.ts (Ergänzung, Skizze) TypeScript 
export const store = configureStore({
  reducer: {
    [flightsApi.reducerPath]: flightsApi.reducer,
  },
  middleware: (getDefaultMiddleware) =>
    getDefaultMiddleware().concat(flightsApi.middleware),
});
Verwendung in einer Seite (Skizze) TypeScript 
// ersetzt useFlights(): Laden, Cache und Polling alle 30 Sekunden
const { data: flights = [], isLoading, error, refetch } =
  useGetFlightsQuery(undefined, { pollingInterval: 30_000 });
const [updateFlightStatus] = useUpdateFlightStatusMutation();

// statt updateStatus(id, status) aus useFlights:
const handleStatusChange = (id: number, status: FlightStatus) => {
  updateFlightStatus({ id, status });
};

Häufige Architekturfehler

3 Fehler · zum Aufklappen klicken

Zu früh Redux einführen

Erst mit lokalem State + Context starten. Redux einführen, wenn Komplexität und Teamgröße den Mehraufwand wirklich rechtfertigen.

Zu viel in den globalen Store legen

Kurzlebiger UI-State bleibt lokal. Global nur Zustand, den mehrere Bereiche wirklich teilen oder nachvollziehbar versionieren müssen.

Store als Ersatz für API-Design missbrauchen

Redux ersetzt kein Backend-Konzept. Eine saubere API und Datenmodellierung bleiben weiterhin entscheidend.

Quiz

5 Fragen · zum Aufklappen klicken

Frage 1 Welche Aufgabe hat ein Reducer in Redux?

Erklärung: Reducer sind reine Funktionen: gleicher State und gleiche Action ergeben immer denselben neuen State, ohne Seiteneffekte.

Frage 2 Wie läuft eine Änderung im Redux-Store ab?

Mehrere Antworten sind richtig.

Erklärung: Die Komponente schickt mit dispatch eine Action. Der Store ruft daraufhin den Reducer auf, der aus altem State und Action den neuen State berechnet. Den Store ändert die Komponente nie direkt, und den Reducer ruft sie nicht selbst auf.

Frage 3 Wofür verwendet man einen Selector, und was bewirkt er?

Mehrere Antworten sind richtig.

Erklärung: Ein Selector liest gezielt einen Teil des Store-States, z. B. mit useSelector. Ändert sich genau dieser Teil, rendert die Komponente neu. Mit CSS hat er nichts zu tun, und Actions erzeugt er nicht.

Frage 4 Warum darf man in einem Reducer von Redux Toolkits createSlice scheinbar mutierenden Code wie state.items.push(…) schreiben?

Erklärung: Außerhalb von createSlice (z. B. in useState) gilt weiterhin: State nie direkt verändern.

Frage 5 Wann lohnt sich globales State Management mit Redux?

Erklärung: In kleinen Apps reichen lokaler State und Context meist aus. Redux bringt zusätzliche Struktur und Aufwand.
