Lektion 3.2 — Teil 3: Next.js

Routing & Layouts

Next.js ca. 90 min

Lernziele

Nach dieser Lektion kannst du folgendes:

  • Alle speziellen Dateikonventionen des App Routers benennen und erklären
  • Verschachtelte Layouts mit Route Groups organisieren
  • loading.tsx für automatisches Suspense-Handling einsetzen
  • error.tsx als Error Boundary für einzelne Routen implementieren
  • Dynamische Routen mit [id] und den params-Prop nutzen
  • generateMetadata für dynamische SEO-Metadaten verwenden

1 — Dateikonventionen im App Router

Der App Router erkennt bestimmte Dateinamen und gibt ihnen automatisch eine besondere Rolle. Diese Dateikonventionen müssen exakt eingehalten werden — Groß- und Kleinschreibung inklusive.

Dateiname Rolle Besonderheit
page.tsx Öffentliche UI der Route Wird zur URL; ohne diese Datei keine öffentliche Seite
layout.tsx Gemeinsames Layout für Unterseiten Persistiert bei Navigation — wird nicht neu gemountet
loading.tsx Lade-UI Automatisch in <Suspense> eingebettet
error.tsx Fehlerbehandlung Muss Client Component sein ('use client')
not-found.tsx 404-Seite Wird durch notFound() ausgelöst
route.ts API-Endpunkt Kein JSX — gibt NextResponse zurück
template.tsx Wie Layout, aber ohne Persistenz Wird bei jeder Navigation neu gemountet

Ordner-Konventionen

Ordnername Bedeutung Beispiel URL
departures/ Normales URL-Segment /departures
[id]/ Dynamisches Segment /flight/1 → id = '1'
(board)/ Route Group (unsichtbar in URL) kein Einfluss auf URL
_components/ Private Ordner (kein Routing) nicht erreichbar

2 — Verschachtelte Layouts mit Route Groups

Route Groups erlauben dir, mehrere Seiten unter ein gemeinsames Layout zu stellen, ohne dieses Segment in der URL sichtbar zu machen. Für FlugBoard bietet sich eine (board)-Gruppe an, die /departures und /arrivals mit einer geteilten Navigationsleiste verbindet.

Verzeichnisstruktur mit Route Group Bash 
src/app/
├── layout.tsx              ← Globales Layout (alle Seiten)
├── page.tsx                ← Startseite: /
├── (board)/
│   ├── layout.tsx          ← Board-Layout: nur /departures + /arrivals
│   ├── departures/
│   │   ├── page.tsx        ← /departures
│   │   ├── loading.tsx     ← Lade-UI für /departures
│   │   └── error.tsx       ← Fehler-UI für /departures
│   └── arrivals/
│       ├── page.tsx        ← /arrivals
│       ├── loading.tsx
│       └── error.tsx
└── flight/
    └── [id]/
        └── page.tsx        ← /flight/1

Die Route Group (board) erscheint nicht in der URL. /departures bleibt /departures — nicht /board/departures.

Das geteilte Board-Layout

Das Layout für die (board)-Gruppe zeigt eine Tab-Navigation, die zwischen Abflügen und Ankünften wechselt. Diese Leiste bleibt bei der Navigation zwischen den Tabs bestehen — kein Flackern, kein Neu-Laden.

src/app/(board)/layout.tsx TypeScript 
import Link from 'next/link';

export default function BoardLayout({
  children,
}: {
  children: React.ReactNode;
}) {
  return (
    <div className="board-layout">
      <header className="board-header">
        <Link href="/" className="board-logo">
          ✈ FlugBoard München
        </Link>
        <nav className="board-tabs">
          <Link href="/departures" className="board-tab">
            ➔ Abflüge
          </Link>
          <Link href="/arrivals" className="board-tab">
            ➔ Ankünfte
          </Link>
        </nav>
      </header>
      <main className="board-content">
        {children}
      </main>
    </div>
  );
}
ℹ
Layouts persistieren

Wenn du von /departures zu /arrivals navigierst, wird (board)/layout.tsx nicht neu gemountet. Das ist ein wichtiger Unterschied zu React Router — der Header und alle Zustände im Layout bleiben vollständig erhalten.

3 — loading.tsx für automatisches Suspense

In React müsstest du manuell einen isLoading-State verwalten und Ladeanimationen bedingt rendern. Next.js erledigt das automatisch: Wenn du loading.tsx in einem Ordner anlegst, umhüllt Next.js die page.tsx automatisch mit einem <Suspense>-Boundary und zeigt dein Loading-UI, solange die Seite lädt.

src/app/(board)/departures/loading.tsx TypeScript 
export default function Loading() {
  return (
    <div className="board-loading board-loading--muted">
      <div className="state-icon">✈</div>
      <p>Flugdaten werden geladen…</p>
    </div>
  );
}

Da Next.js das Suspense automatisch einfügt, musst du nichts an page.tsx ändern. Das Loading-UI erscheint sofort beim Navigieren und verschwindet, sobald die Seite fertig gerendert ist.

✓
Skeleton-Loading statt Spinner

Für eine bessere User Experience kannst du statt eines einfachen Spinners sogenannte Skeleton Screens einsetzen: Platzhalter-Blöcke in der Form der späteren Inhalte. Nutze CSS-Animationen mit animation: pulse, um die Skelett-Elemente sanft aufleuchten zu lassen.

4 — error.tsx als Error Boundary

Wenn beim Laden einer Seite ein Fehler auftritt (z. B. API nicht erreichbar), fängt error.tsx diesen Fehler auf und zeigt eine benutzerfreundliche Fehlermeldung — anstatt die gesamte Anwendung abstürzen zu lassen.

⚠
error.tsx muss eine Client Component sein

Im Gegensatz zu loading.tsx und page.tsx muss error.tsx mit 'use client' markiert werden. Das liegt daran, dass Error Boundaries in React nur in Client-seitigem Code funktionieren.

src/app/(board)/departures/error.tsx TypeScript 
'use client';

import { useEffect } from 'react';

interface ErrorProps {
  error: Error & { digest?: string };
  reset: () => void;
}

export default function DeparturesError({ error, reset }: ErrorProps) {
  useEffect(() => {
    // Fehler in einem Logging-Service erfassen
    console.error('Fehler beim Laden der Abflüge:', error);
  }, [error]);

  return (
    <div className="error-container">
      <div className="error-icon">⚠</div>
      <h2>Flüge konnten nicht geladen werden</h2>
      <p className="error-message">
        {error.message || 'Ein unbekannter Fehler ist aufgetreten.'}
      </p>
      <button
        className="error-reset-btn"
        onClick={reset}
      >
        Erneut versuchen
      </button>
    </div>
  );
}

Der reset-Prop ist eine Funktion, die Next.js bereitstellt. Beim Klick auf „Erneut versuchen“ wird die Seite neu gerendert — ohne vollständigen Seiten-Reload.

5 — Dynamische Routen und params

Dynamische Segmente in eckigen Klammern ([id]) erlauben es, beliebige Werte als URL-Parameter zu empfangen. Die Flugdetailseite nutzt das, um den konkreten Flug anhand der ID zu laden.

⚠
Next.js 15: params ist ein Promise!

Ab Next.js 15 ist params (und searchParams) ein Promise. Du musst es explizit mit await auflösen, bevor du auf die Werte zugreifen kannst. In älteren Next.js-Versionen war params ein direktes Objekt.

src/app/flight/[id]/page.tsx TypeScript 
import { notFound } from 'next/navigation';
import { listFlights } from '@/lib/flights-db';
import type { Metadata } from 'next';

interface PageProps {
  params: Promise<{ id: string }>;
}

export default async function FlightDetailPage({ params }: PageProps) {
  // params MUSS in Next.js 15 awaited werden
  const { id } = await params;

  const flight = listFlights().find(f => f.id === Number(id));

  if (!flight) {
    // Löst die not-found.tsx aus
    notFound();
  }

  return (
    <article className="flight-detail">
      <h1>Flug {flight.flightNumber}</h1>
      <dl className="flight-detail-grid">
        <dt>Airline</dt>
        <dd>{flight.airline}</dd>
        <dt>Typ</dt>
        <dd>{flight.type}</dd>
        <dt>Airport</dt>
        <dd>{flight.airport}</dd>
        <dt>Geplant</dt>
        <dd>{flight.scheduledTime}</dd>
        <dt>Status</dt>
        <dd className={`status status-${flight.status}`}>
          {flight.status}
        </dd>
        {flight.gate && (
          <>
            <dt>Gate</dt>
            <dd>{flight.gate}</dd>
          </>
        )}
      </dl>
    </article>
  );
}

6 — Dynamische Metadaten mit generateMetadata

Für dynamische Seiten (wie die Flugdetailseite) reicht ein statisches metadata-Objekt nicht aus — der Seitentitel soll die konkrete Flugnummer enthalten. generateMetadata löst dieses Problem: die Funktion erhält dieselben Props wie die Seitenkomponente und kann asynchron Daten laden.

src/app/flight/[id]/page.tsx — mit generateMetadata TypeScript 
import { notFound } from 'next/navigation';
import { listFlights } from '@/lib/flights-db';
import type { Metadata } from 'next';

interface PageProps {
  params: Promise<{ id: string }>;
}

// Wird VOR dem Rendern aufgerufen und setzt <title> + <meta>
export async function generateMetadata(
  { params }: PageProps
): Promise<Metadata> {
  const { id } = await params;
  const flight = listFlights().find(f => f.id === Number(id));

  if (!flight) {
    return { title: 'Flug nicht gefunden' };
  }

  return {
    title: `Flug ${flight.flightNumber} – ${flight.airport}`,
    description: `Details zu Flug ${flight.flightNumber} (${flight.type}) am Flughafen Wien.`,
  };
}

export default async function FlightDetailPage({ params }: PageProps) {
  const { id } = await params;
  const flight = listFlights().find(f => f.id === Number(id));

  if (!flight) notFound();

  return (
    <article className="flight-detail">
      <h1>{flight.flightNumber}</h1>
      {/* ... Restliche Anzeige */}
    </article>
  );
}
ℹ
Daten-Deduplication

Wenn generateMetadata und die Seitenkomponente denselben fetch-Aufruf machen, dedupliziert Next.js die Anfrage automatisch. Die API wird also nur einmal aufgerufen, nicht zweimal. Bei direktem Datenimport (wie hier mit listFlights().find()) entfällt dieses Problem vollständig.

Projektschritt

Projektschritt 3.2

Routing-Struktur und Layouts aufbauen

In diesem Projektschritt baust du die vollständige Routing-Architektur für FlugBoard auf — mit Route Groups, geteiltem Layout, Lade-UIs und einer vollständigen Detailseite.

  1. Route Group erstellen: Lege den Ordner src/app/(board)/ an und verschiebe departures/ und arrivals/ hinein. Prüfe, dass die URLs gleich bleiben.
  2. Board-Layout: Erstelle src/app/(board)/layout.tsx mit dem Header und der Tab-Navigation (Abflüge / Ankünfte).
  3. loading.tsx hinzufügen: Erstelle loading.tsx für departures/ und arrivals/ mit einem Lade-Indikator.
  4. error.tsx hinzufügen: Erstelle error.tsx (mit 'use client') für beide Seiten mit Reset-Button.
  5. Detailseite: Erstelle src/app/flight/[id]/page.tsx mit generateMetadata und notFound()-Aufruf.
  6. Testen: Rufe /flight/1 auf, prüfe den Seitentitel im Browser-Tab, und teste eine nicht-existierende ID.

Häufige Fehler

Fehler: params nicht awaited

Du schreibst const { id } = params; anstatt const { id } = await params;. TypeScript zeigt keinen Fehler, aber id ist ein unaufgelöstes Promise-Objekt — dein find()-Aufruf findet nichts und die Seite zeigt immer „Flug nicht gefunden“.

Fix: Markiere die Komponente als async und verwende const { id } = await params;. Dies gilt in Next.js 15 sowohl für params als auch für searchParams.

Fehler: error.tsx ohne 'use client'

Du vergisst 'use client' in error.tsx. Next.js zeigt beim Build einen Fehler: „Error boundaries require 'use client'“.

Fix: Füge 'use client'; als allererste Zeile in error.tsx ein. Das ist die einzige Datei im App Router, die zwingend eine Client Component sein muss.

Fehler: Layout-Verschachtelung vergessen

Du erstellst (board)/layout.tsx, aber die Seiten befinden sich noch im alten departures/-Ordner außerhalb der Route Group. Das geteilte Layout wird nie angezeigt.

Fix: Verschiebe die Seiten-Ordner in den (board)/-Ordner: src/app/(board)/departures/. Prüfe die Struktur mit ls src/app/(board)/.

Fehler: (board) erscheint in der URL

Du erwartest, dass die URL /departures lautet, aber der Browser zeigt /(board)/departures — das ist ein Zeichen, dass der Ordner ohne runde Klammern angelegt wurde.

Fix: Achte auf die runden Klammern: der Ordner muss exakt (board) heißen. Ohne Klammern ist es ein normales URL-Segment. Benenne den Ordner um und starte den Dev-Server neu.

Aufgaben

Aufgabe 1 Route Group und geteiltes Layout

Organisiere die Routing-Struktur mit einer Route Group und einem gemeinsamen Layout.

  • Erstelle den Ordner src/app/(board)/
  • Verschiebe departures/ und arrivals/ in die Route Group
  • Erstelle (board)/layout.tsx mit Header und Tab-Navigation
  • Hebe den aktiven Tab visuell hervor (verwende usePathname())
Aufgabe 2 loading.tsx und error.tsx implementieren

Füge automatisches Lade- und Fehler-Handling zu beiden Board-Seiten hinzu.

  • Erstelle loading.tsx für Abflüge und Ankünfte
  • Erstelle error.tsx für beide Seiten (nicht vergessen: 'use client')
  • Teste das Fehler-UI, indem du einen throw new Error() in page.tsx einfügst
  • Prüfe, ob der Reset-Button die Seite korrekt neu lädt
Aufgabe 3 Flugdetailseite mit params und notFound()

Implementiere die dynamische Flugdetailseite vollständig.

  • Erstelle src/app/flight/[id]/page.tsx
  • Awaite params korrekt und lese id aus
  • Zeige alle Flugdetails an (Flugnummer, Airline, Route, Status, Gate)
  • Rufe notFound() auf, wenn kein Flug gefunden wurde
  • Füge von den Abflug-Listenseiten Links zu /flight/{'{flight.id}'} hinzu
Aufgabe 4 — Bonus generateStaticParams für statisches Vorrendern

Mit generateStaticParams kannst du alle möglichen Routen beim Build vorrendern lassen — maximale Performance ohne dynamisches Rendering.

  • Exportiere generateStaticParams aus flight/[id]/page.tsx
  • Gib alle Flug-IDs aus der SQLite-Datenquelle als { id: string }[] zurück
  • Führe npm run build aus und beobachte, welche Routen als „Static“ markiert werden
  • Erkläre: Wann ist generateStaticParams sinnvoll, wann nicht?
