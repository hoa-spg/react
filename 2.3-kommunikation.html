Lektion 2.3 — Teil 2: React Praxis

Komponentenkommunikation

React ca. 90 min

Lernziele

  • Daten und Callbacks korrekt zwischen Komponenten weitergeben
  • Prop Drilling erkennen und verstehen
  • State in die gemeinsame Elternkomponente heben (Lifting State Up)
  • Callback Props für die Kommunikation von Kind zu Elternkomponente nutzen
  • Geschwisterkomponenten über den gemeinsamen Elternteil koordinieren

1. „Lifting State Up“ – State nach oben heben

In React fließen Daten immer in eine Richtung: von der Elternkomponente zur Kindkomponente, via Props. Was passiert aber, wenn zwei Geschwisterkomponenten auf denselben Wert zugreifen oder ihn verändern müssen? Die Antwort ist Lifting State Up: Der State wird in die gemeinsame Elternkomponente verschoben. Die Elternkomponente gibt den Wert als Prop nach unten weiter und stellt einen Callback bereit, über den Kinder Änderungen nach oben melden können.

Im FlugBoard-Projekt ist ein typisches Beispiel die Flugauswahl: Klickt der Nutzer auf eine Zeile in FlightBoard, soll FlightDetail den ausgewählten Flug anzeigen. Beide Komponenten sind Geschwister unter App – also muss selectedFlight als State in App leben.

ℹ
Faustregel

Platziere State immer so tief wie möglich im Komponentenbaum – aber so hoch wie nötig, damit alle Komponenten, die ihn brauchen, Zugriff haben.

💡
Smart vs. Dumb Components (Einordnung)

Dieses Muster entspricht grob dem bekannten Konzept Container/Smart (State + Logik) und Presentational/Dumb (Darstellung via Props). Im modernen React wird das meist pragmatisch umgesetzt: Logik in Elternkomponenten oder Custom Hooks, UI-Komponenten möglichst schlank.

src/App.tsx TypeScript 
import { useState } from 'react';
import { Flight } from './types/flight';
import FlightBoard from './components/FlightBoard';
import FlightDetail from './components/FlightDetail';

function App() {
  // selectedFlight lebt in App, weil sowohl FlightBoard
  // als auch FlightDetail darauf zugreifen müssen.
  const [selectedFlight, setSelectedFlight] = useState<Flight | null>(null);
  const [flights, setFlights] = useState<Flight[]>(sampleFlights);

  const departures = flights.filter(f => f.type === 'departure');
  const arrivals   = flights.filter(f => f.type === 'arrival');

  return (
    <div className="app">
      <FlightBoard
        title="Abflüge"
        flights={departures}
        onFlightSelect={setSelectedFlight}
        selectedFlightId={selectedFlight?.id}
      />
      <FlightBoard
        title="Ankünfte"
        flights={arrivals}
        onFlightSelect={setSelectedFlight}
        selectedFlightId={selectedFlight?.id}
      />
      {selectedFlight && (
        <FlightDetail
          flight={selectedFlight}
          onClose={() => setSelectedFlight(null)}
        />
      )}
    </div>
  );
}

FlightBoard erhält onFlightSelect als Prop und reicht diesen Callback an jede FlightCard weiter. Die Karte selbst „weiß nichts“ über den globalen State – sie ruft einfach den Callback auf, wenn der Nutzer klickt.

isSelected-Highlighting

Der selectedFlightId-Prop in FlightBoard erlaubt es, die aktive Zeile visuell hervorzuheben, ohne dass FlightCard selbst den State kennen muss. Das ist ein gutes Beispiel für kontrollierte Komponenten: Die Karte hat keinen eigenen „selected“-State, sie rendert einfach das, was sie übergeben bekommt.

2. Prop Drilling – Das Problem

Prop Drilling bezeichnet das Phänomen, bei dem ein Prop durch mehrere Zwischenkomponenten hindurchgereicht werden muss, obwohl nur die tiefste Ebene ihn tatsächlich benötigt. Die Zwischenkomponenten fungieren lediglich als „Durchleitungen“.

Beispiel: theme-Prop durch alle Ebenen TypeScript 
// Problem: theme muss durch alle Ebenen gereicht werden
<App theme="dark">                {/* Hier definiert      */}
  <FlightBoard theme="dark">      {/* Nur weitergereicht  */}
    <FlightCard theme="dark">     {/* Nur weitergereicht  */}
      <StatusIcon theme="dark" /> {/* Hier erst gebraucht */}
    </FlightCard>
  </FlightBoard>
</App>

// FlightBoard und FlightCard müssen theme in ihrer
// Props-Definition führen, obwohl sie es selbst nie nutzen.
interface FlightBoardProps {
  flights: Flight[];
  title: string;
  onFlightSelect: (flight: Flight) => void;
  theme: 'dark' | 'light'; // <-- nur wegen Drilling hier
}

interface FlightCardProps {
  flight: Flight;
  isSelected: boolean;
  onSelect: (flight: Flight) => void;
  theme: 'dark' | 'light'; // <-- nur wegen Drilling hier
}

Bei zwei oder drei Ebenen ist das noch handhabbar. Wird die Komponentenhierarchie tiefer, wird Prop Drilling zum echten Problem:

  • Jede Zwischenkomponente muss das Interface um den Prop erweitern – viel Boilerplate
  • Eine Umbenennung des Props muss an jeder Ebene durchgeführt werden
  • Die Zwischenkomponenten werden schlechter lesbar, weil Props auftauchen, die sie nicht nutzen
  • Refactoring wird schwierig: Wird eine Ebene verschoben, bricht die Kette
ℹ
Lösung: Context API

In Lektion 2.4 lösen wir Prop Drilling mit der React Context API. Context funktioniert wie eine „Rohrleitung“, die Daten direkt von einem Provider zu einem beliebig tief geschachtelten Consumer transportiert – ohne Zwischenkomponenten.

3. Typisierung von Callbacks

TypeScript ermöglicht präzise Typen für Callback-Props. Das ist besonders wichtig, um sicherzustellen, dass die aufgerufene Funktion die richtigen Argumente erhält und den richtigen Rückgabetyp hat. Niemals Function als Typ verwenden – das ist zu unspezifisch und verhindert die TypeScript-Prüfung.

Callback-Typen im Überblick TypeScript 
import { Flight, FlightStatus } from '../types/flight';

interface FlightCardProps {
  flight: Flight;
  isSelected: boolean;

  // Callback mit einem Parameter, gibt nichts zurück
  onSelect: (flight: Flight) => void;

  // Callback ohne Parameter, gibt nichts zurück
  onClose: () => void;

  // Asynchroner Callback (gibt Promise zurück)
  onDelete: (id: number) => Promise<void>;

  // Callback mit mehreren Parametern
  onStatusChange: (id: number, status: FlightStatus) => void;
}

// Verwendung in der Komponente:
const FlightCard = ({
  flight,
  isSelected,
  onSelect,
  onDelete,
  onStatusChange,
}: FlightCardProps) => {

  const handleDelete = async () => {
    if (window.confirm(`Flug ${flight.flightNumber} wirklich löschen?`)) {
      await onDelete(flight.id); // TypeScript prüft: id muss number sein
    }
  };

  const handleStatusChange = (e: React.ChangeEvent<HTMLSelectElement>) => {
    onStatusChange(flight.id, e.target.value as FlightStatus);
  };

  return (
    <tr onClick={() => onSelect(flight)}>
      ...
      <td>
        <select value={flight.status} onChange={handleStatusChange}>
          <option value="on-time">Pünktlich</option>
          <option value="delayed">Verspätet</option>
          <option value="boarding">Boarding</option>
          <option value="departed">Abgeflogen</option>
          <option value="cancelled">Gestrichen</option>
        </select>
      </td>
      <td>
        <button onClick={handleDelete}>Löschen</button>
      </td>
    </tr>
  );
};
💡
React.ChangeEvent vs. Event

Bei React-Eventhandlern immer den React-spezifischen Eventtyp verwenden: React.ChangeEvent<HTMLSelectElement>, React.MouseEvent<HTMLButtonElement>, React.FormEvent<HTMLFormElement> usw. Diese Typen kennen das target-Objekt korrekt und ermöglichen typsichere Zugriffe auf Werte wie e.target.value.

4. Kommunikationsmuster im Überblick

Es gibt drei grundsätzliche Richtungen, in denen Komponenten miteinander kommunizieren können. Jede hat ein klares Muster in React:

Richtung Mechanismus Beispiel
Eltern → Kind Props App gibt flights an FlightBoard
Kind → Eltern Callback Props FlightCard ruft onSelect(flight) auf
Geschwister ↔ Geschwister Shared State im Elternteil FlightBoard und FlightDetail via App

Das Muster für die Geschwisterkommunikation lässt sich schrittweise beschreiben:

  1. Geschwister A (z.B. FlightBoard) ruft einen Callback auf: onFlightSelect(flight)
  2. Der Callback gehört dem Elternteil (App) und aktualisiert dessen State: setSelectedFlight(flight)
  3. React re-rendert App und alle Kinder, die von diesem State abhängen
  4. Geschwister B (FlightDetail) erhält den neuen Wert als Prop und rendert sich neu
Datenfluss visualisiert TypeScript 
// App (gemeinsamer Elternteil)
//  ├── selectedFlight: Flight | null   <── State lebt hier
//  │
//  ├── FlightBoard
//  │    ├── props: flights, onFlightSelect, selectedFlightId
//  │    │                  ↑ Callback nach oben        ↑ Daten nach unten
//  │    └── FlightCard (×n)
//  │         └── onClick: () => onSelect(flight)  // gibt an Board weiter
//  │
//  └── FlightDetail
//       └── props: flight={selectedFlight}  <── bekommt State als Prop

Projektschritt

Projektschritt 2.3

Filter-State strukturieren & Callbacks verknüpfen

In dieser Lektion bringen wir Ordnung in die Kommunikationsstruktur von App.tsx. Der Filter-State wird sauber typisiert, die Kontroll-Komponenten werden über echte Callback Props gesteuert, und FlightCard erhält die Fähigkeit, den Status direkt zu ändern.

Schritt 1: FilterState-Interface definieren

src/types/filters.ts TypeScript 
import { FlightStatus } from './flight';

export interface FilterState {
  searchQuery: string;
  typeFilter: 'all' | 'departure' | 'arrival';
  statusFilter: FlightStatus | 'all';
}

export const DEFAULT_FILTERS: FilterState = {
  searchQuery: '',
  typeFilter: 'all',
  statusFilter: 'all',
};

Schritt 2: Filter-Hilfsfunktion extrahieren

src/utils/filterFlights.ts TypeScript 
import { Flight } from '../types/flight';
import { FilterState } from '../types/filters';

export const filterFlights = (
  flights: Flight[],
  filters: FilterState
): Flight[] => {
  return flights.filter(flight => {
    const matchesSearch =
      flight.flightNumber.toLowerCase().includes(filters.searchQuery.toLowerCase()) ||
      flight.airline.toLowerCase().includes(filters.searchQuery.toLowerCase()) ||
      flight.airport.toLowerCase().includes(filters.searchQuery.toLowerCase());

    const matchesType =
      filters.typeFilter === 'all' || flight.type === filters.typeFilter;

    const matchesStatus =
      filters.statusFilter === 'all' || flight.status === filters.statusFilter;

    return matchesSearch && matchesType && matchesStatus;
  });
};

Schritt 3: App.tsx mit sauberer Callback-Struktur

src/App.tsx (aktualisiert) TypeScript 
import { useState } from 'react';
import { Flight, FlightStatus } from './types/flight';
import { FilterState, DEFAULT_FILTERS } from './types/filters';
import { filterFlights } from './utils/filterFlights';
import FlightBoard from './components/FlightBoard';
import FlightDetail from './components/FlightDetail';
import FilterBar from './components/FilterBar';
import SearchBar from './components/SearchBar';

function App() {
  const [flights, setFlights]             = useState<Flight[]>(sampleFlights);
  const [filters, setFilters]             = useState<FilterState>(DEFAULT_FILTERS);
  const [selectedFlight, setSelectedFlight] = useState<Flight | null>(null);

  // Filter-Callbacks: jeder ändert nur einen Teil des FilterState
  const handleSearchChange = (query: string) =>
    setFilters(f => ({ ...f, searchQuery: query }));

  const handleStatusFilterChange = (status: FlightStatus | 'all') =>
    setFilters(f => ({ ...f, statusFilter: status }));

  // Status eines Flugs immutabel aktualisieren
  const handleStatusChange = (id: number, newStatus: FlightStatus) => {
    setFlights(prev =>
      prev.map(f => (f.id === id ? { ...f, status: newStatus } : f))
    );
  };

  // Flug aus dem Array entfernen
  const handleDelete = (id: number) => {
    setFlights(prev => prev.filter(f => f.id !== id));
    if (selectedFlight?.id === id) setSelectedFlight(null);
  };

  const allFiltered = filterFlights(flights, filters);
  const departures  = allFiltered.filter(f => f.type === 'departure');
  const arrivals    = allFiltered.filter(f => f.type === 'arrival');

  return (
    <div className="app">
      <SearchBar value={filters.searchQuery} onChange={handleSearchChange} />
      <FilterBar
        currentStatus={filters.statusFilter}
        onStatusChange={handleStatusFilterChange}
      />
      <FlightBoard
        title="Abflüge"
        flights={departures}
        totalCount={flights.filter(f => f.type === 'departure').length}
        onFlightSelect={setSelectedFlight}
        onStatusChange={handleStatusChange}
        onDelete={handleDelete}
        selectedFlightId={selectedFlight?.id}
      />
      <FlightBoard
        title="Ankünfte"
        flights={arrivals}
        totalCount={flights.filter(f => f.type === 'arrival').length}
        onFlightSelect={setSelectedFlight}
        onStatusChange={handleStatusChange}
        onDelete={handleDelete}
        selectedFlightId={selectedFlight?.id}
      />
      {selectedFlight && (
        <FlightDetail
          flight={selectedFlight}
          onClose={() => setSelectedFlight(null)}
        />
      )}
    </div>
  );
}
💡
Immutables State-Update

prev.map(f => f.id === id ? { ...f, status: newStatus } : f) erstellt ein neues Array, ohne das Original zu verändern. React erkennt die neue Referenz und löst ein Re-Render aus. Niemals direkt mutieren: flight.status = newStatus würde React nicht triggern.

Häufige Fehler

Fehler: Callback sofort aufrufen statt übergeben

onClick={onSelect(flight)} ruft onSelect sofort beim Rendern auf, nicht beim Klick. Das führt zu unendlichen Re-Renders und falschen Werten.

Fix: Immer eine Arrow-Function als Handler verwenden: onClick={() => onSelect(flight)}. Die Arrow-Function wird erst beim Klick ausgeführt.

Fehler: State zu tief in der Komponente

Ein State wird in FlightCard definiert, aber später wird klar, dass FlightBoard oder App diesen Wert ebenfalls benötigt. Jetzt muss der State mühsam nach oben „migriert“ werden.

Fix: Vor der Implementierung überlegen: Welche Komponenten brauchen diesen State? State gehört in den niedrigsten gemeinsamen Vorfahren aller beteiligten Komponenten.

Fehler: Zu viele Props (Prop Drilling) ohne Lösung

Props werden über drei oder mehr Ebenen weitergereicht, obwohl nur die unterste Ebene sie benötigt. Das macht den Code schwer wartbar.

Fix: Ab ca. drei Ebenen die Context API (Lektion 2.4) verwenden. Alternativ: Komponenten-Komposition prüfen – kann die Kindkomponente direkt als children oder Slot-Prop übergeben werden?

Fehler: Function als Callback-Typ

onSelect: Function ist zu unspezifisch. TypeScript prüft weder die Parametertypen noch den Rückgabetyp. Fehler werden zur Laufzeit statt beim Kompilieren entdeckt.

Fix: Immer den genauen Funktionstyp angeben: onSelect: (flight: Flight) => void. TypeScript kann dann falsche Aufrufe sofort beim Schreiben markieren.

Aufgaben

Aufgabe 1 Flugstatus ändern

Füge eine Inline-Statusänderung direkt in der Flugtabelle hinzu.

  • Erweitere FlightCardProps um onStatusChange: (id: number, status: FlightStatus) => void
  • Füge in jede FlightCard-Zeile ein <select>-Dropdown ein, das alle möglichen Status-Werte auflistet
  • Verhindere, dass der Klick auf das Dropdown die Zeile auswählt: e.stopPropagation()
  • In App.tsx: aktualisiere das flights-Array immutabel mit .map()
Aufgabe 2 Flug löschen

Ermögliche das Löschen von Flügen direkt aus der Tabelle.

  • Erweitere FlightCardProps und FlightBoardProps um onDelete: (id: number) => void
  • Füge einen Löschen-Button in jede Tabellenzeile ein
  • Zeige vor dem Löschen einen Bestätigungsdialog mit window.confirm()
  • In App.tsx: entferne den Flug mit prev.filter(f => f.id !== id)
  • Falls der gelöschte Flug gerade ausgewählt ist, setze selectedFlight auf null
Aufgabe 3 Gefilterte Anzahl anzeigen

Der FlightBoard-Header soll zeigen, wie viele Flüge gefiltert angezeigt werden.

  • Erweitere FlightBoardProps um totalCount: number
  • Zeige im Board-Header: „Abflüge (3 von 5)“ – gefilterte Anzahl vs. Gesamtanzahl
  • Wenn kein Filter aktiv ist (beide Zahlen gleich), nur „Abflüge (5)“ anzeigen
  • Übergebe in App.tsx sowohl flights={departures} als auch totalCount={allDepartures.length}
Bonus FlightActions-Komponente

Erstelle eine separate FlightActions-Komponente, die alle Aktionen für einen Flug bündelt.

  • FlightActions erhält als Props: flight, onStatusChange, onDelete
  • Die Komponente rendert das Status-Dropdown und den Löschen-Button
  • FlightCard gibt die Callbacks an FlightActions weiter – demonstriere so das Weitergeben von Callbacks über zwei Ebenen
  • Erkläre im Code-Kommentar, warum dies noch kein Prop Drilling ist (es ist nur eine Ebene Weitergabe für eine echte Aufgabe)
