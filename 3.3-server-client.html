Lektion 3.3 — Teil 3: Next.js

Server & Client Components

Next.js ca. 105 min

Lernziele

Nach dieser Lektion kannst du folgendes:

  • Den fundamentalen Unterschied zwischen Server und Client Components erklären
  • Wissen, wann 'use client' notwendig ist — und wann nicht
  • Daten direkt in Server Components fetchen, ohne useEffect
  • Die Kompositionsregel verstehen: Server kann Client rendern, nicht umgekehrt
  • Die verschiedenen Caching-Strategien für fetch in Next.js einsetzen
  • URL-basierte Filter mit useSearchParams in Client Components implementieren

1 — Server Components — der neue Standard

Im App Router ist jede Komponente standardmäßig eine Server Component. Das ist der wichtigste Paradigmenwechsel gegenüber klassischem React. Server Components laufen ausschließlich auf dem Server und senden fertiges HTML zum Browser — ohne JavaScript-Bundle für diese Komponente.

Was Server Components können:

  • async/await direkt in der Komponente verwenden
  • Direkt auf Datenbanken, Dateisystem oder interne APIs zugreifen
  • Secrets und API-Keys sicher nutzen (nie an den Browser gesendet)
  • Vollständiges SEO-freundliches HTML generieren
  • Andere Server und Client Components rendern

Was Server Components nicht können:

  • useState, useEffect oder andere Client-Hooks nutzen
  • Event-Handler wie onClick, onChange definieren
  • Browser-APIs wie window, localStorage, document nutzen
  • Context-Provider oder Context-Consumer einsetzen

Vorher (React mit Vite) vs. Nachher (Next.js Server Component)

VORHER: src/pages/DeparturePage.tsx (React + Vite) TypeScript 
import { useState, useEffect } from 'react';
import FlightBoard from '../components/FlightBoard';
import type { Flight } from '../types/flight';

export default function DeparturePage() {
  const [flights, setFlights]   = useState<Flight[]>([]);
  const [isLoading, setLoading] = useState(true);
  const [error, setError]       = useState<string | null>(null);

  useEffect(() => {
    setLoading(true);
    fetch('http://localhost:3000/api/flights?type=departure')
      .then(res => {
        if (!res.ok) throw new Error('Fehler beim Laden');
        return res.json();
      })
      .then((data: Flight[]) => setFlights(data))
      .catch(err => setError(err.message))
      .finally(() => setLoading(false));
  }, []);

  if (isLoading) return <p>Lade Flugdaten…</p>;
  if (error)     return <p>Fehler: {error}</p>;

  return <FlightBoard flights={flights} />;
}
NACHHER: src/app/(board)/departures/page.tsx (Next.js) TypeScript 
import FlightBoard from '@/components/FlightBoard';
import type { Flight } from '@/types/flight';

export default async function DeparturePage() {
  const response = await fetch(
    'http://localhost:3000/api/flights?type=departure',
    { next: { revalidate: 30 } }  // ISR: alle 30 Sekunden neu laden
  );

  if (!response.ok) {
    throw new Error('Fehler beim Laden der Abflugdaten');
  }

  const flights: Flight[] = await response.json();

  return <FlightBoard flights={flights} />;
}

Aus ~40 Zeilen werden ~15 Zeilen. Kein State, kein Effect, kein Lade-Spinner-Management. Next.js übernimmt das Lade-UI automatisch über loading.tsx und das Fehler-Handling über error.tsx.

✓
Fehler müssen geworfen werden

In einer Server Component wirfst du Fehler mit throw new Error(). Du fängst sie nicht mit try/catch ab (außer du möchtest spezifische Fallbacks). Das nächste error.tsx in der Ordnerhierarchie fängt den Fehler automatisch auf.

2 — Client Components und 'use client'

Du markierst eine Komponente als Client Component, indem du 'use client' als allererste Zeile der Datei schreibst. Alle Komponenten, die diese Datei importieren, werden ebenfalls zu Client Components.

Wann brauchst du 'use client'?

Fähigkeit / Feature Server Component Client Component
useState / useReducer ❌ nicht möglich ✓ möglich
useEffect / useLayoutEffect ❌ nicht möglich ✓ möglich
Event-Handler (onClick, onChange) ❌ nicht möglich ✓ möglich
Browser-APIs (window, localStorage) ❌ nicht möglich ✓ möglich
async Datenabruf ✓ direkt möglich ✓ via useEffect
Backend-Zugriff (DB, Dateisystem) ✓ sicher möglich ❌ nie direkt
SEO-HTML beim ersten Laden ✓ immer ❌ nur nach JS-Ausführung
Secrets / API-Keys ✓ sicher (nicht im Bundle) ❌ werden an Browser gesendet!

Beispiel: SearchBar als Client Component

src/components/SearchBar.tsx TypeScript 
'use client';

import { useState } from 'react';

interface SearchBarProps {
  onSearch: (query: string) => void;
  placeholder?: string;
}

export default function SearchBar({ onSearch, placeholder }: SearchBarProps) {
  const [value, setValue] = useState('');

  function handleChange(e: React.ChangeEvent<HTMLInputElement>) {
    setValue(e.target.value);
    onSearch(e.target.value);
  }

  return (
    <div className="search-bar">
      <input
        type="search"
        value={value}
        onChange={handleChange}
        placeholder={placeholder ?? 'Flugnummer oder Ziel suchen…'}
        className="search-input"
      />
      {value && (
        <button
          onClick={() => { setValue(''); onSearch(''); }}
          className="search-clear"
          aria-label="Suche zurücksetzen"
        >
          ×
        </button>
      )}
    </div>
  );
}

3 — Kompositionsregel: Server und Client kombinieren

Die Grundregel ist: Server Components können Client Components rendern, aber nicht umgekehrt. Sobald eine Komponente mit 'use client' markiert ist, werden auch alle importierten Komponenten zu Client Components — auch wenn sie selbst kein 'use client' haben.

Das „Leaf“-Pattern

Verschiebe 'use client' so weit wie möglich nach „unten“ im Komponentenbaum — an die „Blätter“ (Leaf Components). Größere Container-Komponenten können Server Components bleiben und damit das HTML vorrendern.

src/components/SearchWrapper.tsx — Client Component als Hülle TypeScript 
'use client';

import { useState } from 'react';
import SearchBar from './SearchBar';
import type { Flight } from '@/types/flight';

interface SearchWrapperProps {
  // Flüge werden als Props vom Server Component übergeben
  allFlights: Flight[];
  children: (filtered: Flight[]) => React.ReactNode;
}

export default function SearchWrapper(
  { allFlights, children }: SearchWrapperProps
) {
  const [query, setQuery] = useState('');

  const filtered = allFlights.filter(f =>
    f.flightNumber.toLowerCase().includes(query.toLowerCase()) ||
    f.airport.toLowerCase().includes(query.toLowerCase()) ||
    f.airline.toLowerCase().includes(query.toLowerCase())
  );

  return (
    <>
      <SearchBar onSearch={setQuery} />
      {children(filtered)}
    </>
  );
}
src/app/(board)/departures/page.tsx — Server Component nutzt Client Hülle TypeScript 
import SearchWrapper from '@/components/SearchWrapper';
import FlightTable from '@/components/FlightTable';
import { listFlights } from '@/lib/flights-db';

export default async function DeparturePage() {
  const res = await fetch(
    'http://localhost:3000/api/flights?type=departure',
    { next: { revalidate: 30 } }
  );
  const flights: Flight[] = await res.json();

  return (
    <section>
      <h1>Abflüge ({flights.length})</h1>
      {/*
        Server Component übergibt Daten an Client Component.
        FlightTable ist eine Server Component (kein 'use client').
      */}
      <SearchWrapper allFlights={flights}>
        {(filtered) => <FlightTable flights={filtered} />}
      </SearchWrapper>
    </section>
  );
}
ℹ
Daten fließen nur eine Richtung: Server → Client

Du kannst Daten als Props von Server nach Client Components übergeben. Aber nur Daten, die sich serialisieren lassen (JSON-kompatible Werte): Strings, Zahlen, Arrays, einfache Objekte. Keine Funktionen (außer Server Actions), keine Klassen-Instanzen, keine React-Elemente von Server Components.

4 — Caching-Strategien für fetch

Next.js erweitert die native fetch-API um ein Caching-System. Mit dem zweiten Argument von fetch steuerst du, wie lange die Antwort gecacht werden soll.

Caching-Optionen im Überblick TypeScript 
// 1. Kein Cache – immer frische Daten (SSR bei jedem Request)
const res = await fetch('/api/flights', {
  cache: 'no-store',
});

// 2. ISR – alle 30 Sekunden im Hintergrund neu laden
const res = await fetch('/api/flights', {
  next: { revalidate: 30 },
});

// 3. Statisch – nur beim Build (SSG, maximale Performance)
const res = await fetch('/api/flights', {
  cache: 'force-cache',
});

// 4. On-Demand Revalidation per Tag
const res = await fetch('/api/flights', {
  next: { tags: ['flights'] },
});
// Zum Invalidieren (z.B. nach einem POST):
// import { revalidateTag } from 'next/cache';
// revalidateTag('flights');
Strategie Wann sinnvoll? FlugBoard Verwendung
cache: 'no-store' Daten ändern sich bei jedem Request (Benutzerdaten, Echtzeit) Persönliche Buchungsdetails
revalidate: 30 Daten ändern sich regelmäßig, aber nicht jede Sekunde Abflug- und Ankunftslisten
force-cache Daten ändern sich selten oder nie Flughafen-Informationen, FAQ
⚠
Cache-Verhalten hat sich in Next.js 15 geändert

In Next.js 14 war fetch standardmäßig gecacht (force-cache). In Next.js 15 ist der Standard cache: 'no-store' für dynamische Routen. Schreibe die Cache-Option immer explizit, um Verwirrung zu vermeiden und das Verhalten unabhängig von der Next.js-Version zu kontrollieren.

5 — URL-basierte Filter mit useSearchParams

Statt Filter-State in einer Client Component zu speichern, kannst du ihn in die URL auslagern. Das hat große Vorteile: Die Seite ist bookmarkbar, der Zurück-Button des Browsers funktioniert korrekt, und Nutzer können die gefilterte Ansicht teilen.

src/components/FilterBar.tsx TypeScript 
'use client';

import { useSearchParams, useRouter, usePathname } from 'next/navigation';

const STATUS_OPTIONS = [
  { value: '',          label: 'Alle Flüge' },
  { value: 'on-time',   label: 'Pünktlich' },
  { value: 'delayed',   label: 'Verspätet' },
  { value: 'boarding',  label: 'Boarding' },
  { value: 'cancelled', label: 'Annulliert' },
];

export default function FilterBar() {
  const searchParams = useSearchParams();
  const router       = useRouter();
  const pathname     = usePathname();

  const currentStatus = searchParams.get('status') ?? '';

  function handleStatusChange(status: string) {
    const params = new URLSearchParams(searchParams.toString());

    if (status) {
      params.set('status', status);
    } else {
      params.delete('status');
    }

    router.replace(`${pathname}?${params.toString()}`);
  }

  return (
    <div className="filter-bar">
      <span className="filter-label">Status:</span>
      {STATUS_OPTIONS.map(opt => (
        <button
          key={opt.value}
          className={`filter-btn ${currentStatus === opt.value ? 'active' : ''}`}
          onClick={() => handleStatusChange(opt.value)}
        >
          {opt.label}
        </button>
      ))}
    </div>
  );
}

Die Server Component kann dann searchParams direkt lesen und nur die passenden Flüge laden oder filtern — ohne jeden Client-State.

src/app/(board)/departures/page.tsx — mit searchParams TypeScript 
import FilterBar from '@/components/FilterBar';
import FlightTable from '@/components/FlightTable';
import type { Flight } from '@/types/flight';

interface PageProps {
  searchParams: Promise<{ status?: string }>;
}

export default async function DeparturePage({ searchParams }: PageProps) {
  const { status } = await searchParams;

  const flights = listFlights('departure').filter(
    (flight) => !status || flight.status === status
  );

  return (
    <section>
      <h1>Abflüge</h1>
      <FilterBar />
      <FlightTable flights={flights} />
    </section>
  );
}

Häufige Fehler

Fehler: useState in einer Server Component

Du vergisst 'use client' hinzuzufügen, aber verwendest useState in der Komponente. Next.js zeigt: „You're importing a component that needs useState. It only works in a Client Component but none of its parents are marked with 'use client'.“

Fix: Füge 'use client'; als allererste Zeile ein. Wenn die Komponente auch serverseitig rendern soll, extrahiere den interaktiven Teil in eine separate Client Component nach dem Leaf-Pattern.

Fehler: Sensitive Daten in Client Components exponiert

Du verwendest einen API-Key oder Datenbank-String in einer Client Component. Der Key wird in das JavaScript-Bundle eingebettet und ist für jeden Besucher sichtbar — ein gravierendes Sicherheitsproblem.

Fix: API-Keys und Credentials gehören ausschließlich in Server Components oder Route Handlers. Env-Variablen ohne NEXT_PUBLIC_-Prefix sind nur auf dem Server verfügbar.

Fehler: Context Provider in Server Component

Du versuchst einen React Context Provider (<MyContext.Provider>) in einer Server Component zu verwenden. Next.js wirft einen Fehler, da Context auf Seiten-State basiert, der nur im Browser existiert.

Fix: Erstelle eine separate Providers.tsx-Datei mit 'use client', die alle Context Provider enthält. Importiere sie im layout.tsx und umschließe damit {children}.

Fehler: fetch ohne Cache-Strategie in produktionskritischen Seiten

Du verwendest fetch ohne Cache-Option. In Next.js 15 ist der Default je nach Kontext unterschiedlich — das führt zu unerwartetem Verhalten und potenziell übermäßig vielen API-Anfragen.

Fix: Setze die Cache-Strategie immer explizit: {'{ next: { revalidate: 30 } }'} für ISR, {'{ cache: "no-store" }'} für echtes SSR oder {'{ cache: "force-cache" }'} für statische Daten.
