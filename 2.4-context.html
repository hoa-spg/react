Lektion 2.4 — Teil 2: React Praxis

Context API

React ca. 90 min

Lernziele

  • Das Problem von Prop Drilling verstehen und mit Context lösen
  • Einen Context mit createContext erstellen
  • Einen Provider einrichten und Werte bereitstellen
  • useContext in beliebig tief verschachtelten Komponenten verwenden
  • Einen Theme-Context für Dark/Light-Mode implementieren

1. Was ist der React Context?

Der React Context ist ein Mechanismus, mit dem Daten „durch den Komponentenbaum hindurch“ weitergegeben werden können – ohne dass jede Zwischenebene explizit als Prop weiterreichen muss. Man kann sich Context wie eine Art sichtbare Umgebungsvariable vorstellen, die für alle Komponenten innerhalb eines Providers zugänglich ist.

React selbst verwendet Context intern, z.B. für die SuspenseContext oder den Router-Context von React Router. Wir können eigene Contexts für anwendungsspezifische Belange erstellen.

Die Verwendung von Context besteht immer aus drei Schritten:

Schritt API Ort
1. Context erstellen createContext(defaultValue) Außerhalb der Komponente, eigene Datei
2. Wert bereitstellen <Context.Provider value={...}> In der Eltern- oder Root-Komponente
3. Wert konsumieren useContext(Context) In beliebig tiefer Kindkomponente
ℹ
Context vs. Props

Context ersetzt nicht alle Props. Für Daten, die nur eine Ebene überbrücken, sind Props die richtige Wahl – sie machen den Datenfluss explizit und leicht nachvollziehbar. Context eignet sich für Daten, die wirklich „global“ für einen Teilbaum sind.

2. Einfaches Beispiel: ThemeContext

Das klassische Beispiel für Context ist ein Theme-Switcher. Das Theme wird in der Root-Komponente verwaltet und muss für potenziell jede Komponente im Baum verfügbar sein. Ohne Context müsste theme durch alle Zwischenebenen gereicht werden.

src/context/ThemeContext.tsx TypeScript 
import { createContext, useContext, useState, ReactNode } from 'react';

type Theme = 'dark' | 'light';

interface ThemeContextType {
  theme: Theme;
  toggleTheme: () => void;
}

// Schritt 1: Context erstellen mit sinnvollem Default-Wert.
// Der Default-Wert wird nur verwendet, wenn kein Provider in der
// Komponentenhierarchie vorhanden ist.
const ThemeContext = createContext<ThemeContextType>({
  theme: 'dark',
  toggleTheme: () => {},
});

// Schritt 2: Provider-Komponente erstellen.
// Diese Komponente kapselt den useState-Aufruf und den Provider.
// "children" repräsentiert alle Kindkomponenten.
export const ThemeProvider = ({ children }: { children: ReactNode }) => {
  const [theme, setTheme] = useState<Theme>('dark');

  const toggleTheme = () => setTheme(t => (t === 'dark' ? 'light' : 'dark'));

  return (
    <ThemeContext.Provider value={{ theme, toggleTheme }}>
      {children}
    </ThemeContext.Provider>
  );
};

// Schritt 3 (optional, aber empfohlen): Custom Hook für einfachen Zugriff.
// So importiert jede Komponente nur diesen Hook, nicht den Context direkt.
export const useTheme = () => useContext(ThemeContext);

Der ThemeProvider wird in main.tsx um die gesamte App gewickelt, sodass alle Komponenten Zugriff auf den Theme-Context haben:

src/main.tsx TypeScript 
import ReactDOM from 'react-dom/client';
import { ThemeProvider } from './context/ThemeContext';
import App from './App';
import './index.css';

ReactDOM.createRoot(document.getElementById('root')!).render(
  <React.StrictMode>
    <ThemeProvider>
      <App />
    </ThemeProvider>
  </React.StrictMode>
);

Jetzt kann jede Komponente – egal wie tief sie im Baum sitzt – auf das Theme zugreifen, ohne dass irgendjemand es als Prop weiterreichen muss:

src/components/FlightStatusBadge.tsx TypeScript 
import { useTheme } from '../context/ThemeContext';
import { FlightStatus } from '../types/flight';

const STATUS_CONFIG: Record<FlightStatus, { label: string; darkBg: string; lightBg: string }> = {
  'on-time':   { label: 'Pünktlich',   darkBg: '#1a3a2a', lightBg: '#d1fae5' },
  'delayed':   { label: 'Verspätet',   darkBg: '#3a2a1a', lightBg: '#fef3c7' },
  'boarding':  { label: 'Boarding',    darkBg: '#1a2a3a', lightBg: '#dbeafe' },
  'departed':  { label: 'Abgeflogen',  darkBg: '#1e2a1e', lightBg: '#f0fdf4' },
  'landed':    { label: 'Gelandet',    darkBg: '#1e2a1e', lightBg: '#f0fdf4' },
  'cancelled': { label: 'Gestrichen', darkBg: '#3a1a1a', lightBg: '#fee2e2' },
};

interface FlightStatusBadgeProps {
  status: FlightStatus;
}

const FlightStatusBadge = ({ status }: FlightStatusBadgeProps) => {
  // Kein Prop Drilling nötig! Direkt aus dem Context lesen.
  const { theme } = useTheme();

  const config = STATUS_CONFIG[status];
  const bgColor = theme === 'dark' ? config.darkBg : config.lightBg;

  return (
    <span
      style={{
        background: bgColor,
        padding: '0.2rem 0.6rem',
        borderRadius: '4px',
        fontSize: '0.85rem',
        fontWeight: 600,
      }}
    >
      {config.label}
    </span>
  );
};
💡
Custom Hook statt direktem useContext

Durch das Exportieren von useTheme() statt ThemeContext direkt hat man einen zentralen Ort, um später zusätzliche Logik hinzuzufügen (z.B. Fehlerprüfung, wenn kein Provider vorhanden). Die Komponenten wissen nicht, wie der Context intern implementiert ist – nur dass sie useTheme() aufrufen können.

3. Context mit mehreren Werten

Für komplexere Anwendungsfälle kann ein Context mehrere zusammengehörige Werte bündeln. Im FlugBoard-Projekt könnte ein FlugBoardContext den zentralen Anwendungszustand bereitstellen:

src/context/FlugBoardContext.tsx TypeScript 
import {
  createContext, useContext, useState,
  useEffect, ReactNode, useMemo
} from 'react';
import { Flight } from '../types/flight';

interface FlugBoardContextType {
  // Daten
  flights: Flight[];
  isLoading: boolean;
  error: string | null;
  // Suche & Filter
  searchQuery: string;
  setSearchQuery: (q: string) => void;
  // Auswahl
  selectedFlight: Flight | null;
  setSelectedFlight: (f: Flight | null) => void;
}

// null als Default-Wert: Klarer Fehler wenn kein Provider vorhanden
const FlugBoardContext = createContext<FlugBoardContextType | null>(null);

export const FlugBoardProvider = ({ children }: { children: ReactNode }) => {
  const [flights, setFlights]               = useState<Flight[]>([]);
  const [isLoading, setIsLoading]           = useState(true);
  const [error, setError]                   = useState<string | null>(null);
  const [searchQuery, setSearchQuery]       = useState('');
  const [selectedFlight, setSelectedFlight] = useState<Flight | null>(null);

  useEffect(() => {
    fetch('http://localhost:8000/api/flights')
      .then(r => r.json())
      .then(data => { setFlights(data); setIsLoading(false); })
      .catch(e  => { setError(e.message); setIsLoading(false); });
  }, []);

  // useMemo verhindert, dass bei jedem Render ein neues Objekt
  // erstellt wird – das würde alle Consumer unnötig re-rendern.
  const value = useMemo<FlugBoardContextType>(() => ({
    flights, isLoading, error,
    searchQuery, setSearchQuery,
    selectedFlight, setSelectedFlight,
  }), [flights, isLoading, error, searchQuery, selectedFlight]);

  return (
    <FlugBoardContext.Provider value={value}>
      {children}
    </FlugBoardContext.Provider>
  );
};

// Custom Hook mit Fehlerprüfung
export const useFlugBoard = (): FlugBoardContextType => {
  const ctx = useContext(FlugBoardContext);
  if (!ctx) {
    throw new Error('useFlugBoard muss innerhalb von FlugBoardProvider verwendet werden');
  }
  return ctx;
};

Durch useMemo wird das value-Objekt nur dann neu erstellt, wenn sich einer der Werte tatsächlich geändert hat. Ohne useMemo würde bei jedem Render des Providers ein neues Objekt entstehen, was alle Consumer neu rendern würde – auch wenn sich die Daten nicht geändert haben.

4. Wann Context verwenden – und wann nicht

Context ist ein mächtiges Werkzeug, aber es ist kein Allheilmittel. Eine falsche Nutzung kann zu schwer nachvollziehbarem Datenfluss und unnötigen Re-Renders führen.

✅
Gute Anwendungsfälle für Context

Theme / Erscheinungsbild: Dark/Light-Mode, Farbschemas, Schriftgrößen.
Authentifizierter Nutzer: Nutzerprofil, Berechtigungen – wird in vielen Teilen der App benötigt.
Sprache / Locale: Übersetzungen, Datumsformate, Währungssymbole.
Globaler App-State: Einstellungen, Feature-Flags, die selten ändern.

⚠
Schlechte Anwendungsfälle für Context

Daten, die nur 1–2 Ebenen wandern: Hier sind Props klarer und expliziter.
Häufig ändernde Daten: Jede Änderung re-rendert alle Consumer. Für höchst frequente Updates (z.B. Mausposition) besser useRef oder eine externe State-Bibliothek wie Zustand oder Redux verwenden.
Lokaler Komponenten-State: State, der wirklich nur eine Komponente betrifft, gehört in diese Komponente – nicht in einen Context.

Entscheidungsbaum: Props vs. Context TypeScript 
// Frage: Wie viele Ebenen müssen überbrückt werden?

// 1-2 Ebenen: Props verwenden (explizit, leicht nachvollziehbar)
<FlightBoard flights={flights} />          // OK: direkte Weitergabe
<FlightCard flight={flight} />             // OK: direkte Weitergabe

// 3+ Ebenen mit gleichen Daten: Context verwenden
// statt: App --theme--> Board --theme--> Card --theme--> Badge
// besser:
const { theme } = useTheme();  // direkt in Badge, ohne Drilling

// Alternative: Komponentenkomposition prüfen
// Manchmal kann man Prop Drilling durch das Übergeben von
// Komponenten als "children" oder Slot-Props vermeiden:
<FlightBoard>
  <FlightCard flight={flight} />  {/* Badge ist schon drin */}
</FlightBoard>

Projektschritt

Projektschritt 2.4

Dark/Light Theme Toggle für FlugBoard

Wir fügen FlugBoard einen vollständigen Dark/Light-Theme-Toggle hinzu, der ohne Prop Drilling auskommt. Der Theme-State lebt im Context und wird über einen Button im Header umgeschaltet.

Schritt 1: ThemeContext anlegen

src/context/ThemeContext.tsx TypeScript 
import { createContext, useContext, useState, ReactNode } from 'react';

type Theme = 'dark' | 'light';

interface ThemeContextType {
  theme: Theme;
  toggleTheme: () => void;
}

const ThemeContext = createContext<ThemeContextType>({
  theme: 'dark',
  toggleTheme: () => {},
});

export const ThemeProvider = ({ children }: { children: ReactNode }) => {
  // Initialen Wert aus localStorage lesen (für Aufgabe 1)
  const [theme, setTheme] = useState<Theme>(() => {
    const saved = localStorage.getItem('flugboard-theme');
    return (saved === 'light' ? 'light' : 'dark');
  });

  const toggleTheme = () => {
    setTheme(t => {
      const next = t === 'dark' ? 'light' : 'dark';
      localStorage.setItem('flugboard-theme', next);
      return next;
    });
  };

  return (
    <ThemeContext.Provider value={{ theme, toggleTheme }}>
      {children}
    </ThemeContext.Provider>
  );
};

export const useTheme = () => useContext(ThemeContext);

ℹ
Warum der Provider in main.tsx und nicht in App.tsx?

Der Provider könnte auch in App.tsx stehen. Das Problem: Wenn App selbst den Theme-Context konsumieren will (für den Hintergrund), muss der Provider übergeordnet sein. Durch den Aufbau in main.tsx ist die gesamte App im Provider-Scope – auch zukünftige Komponenten auf derselben Ebene wie App (z.B. ein Modals-Portal).

Häufige Fehler

Fehler: Context außerhalb des Providers verwenden

Eine Komponente verwendet useTheme(), wird aber außerhalb des ThemeProvider gerendert. React gibt leise den Default-Wert zurück – kein Fehler, aber falsches Verhalten. Besonders heimtückisch, wenn der Default plausibel wirkt.

Fix: Den Custom Hook mit einer Prüfung schützen. Default-Wert auf null setzen: createContext<Type | null>(null). Im Custom Hook: if (!ctx) throw new Error('Außerhalb des Providers!'). So wird der Fehler sofort während der Entwicklung sichtbar.

Fehler: Neues Objekt als value bei jedem Render

<Context.Provider value={{ theme, toggleTheme }}> erstellt bei jedem Render des Providers ein neues Objekt, auch wenn sich theme und toggleTheme nicht geändert haben. React führt einen Referenzvergleich durch – neues Objekt bedeutet neue Referenz, bedeutet alle Consumer re-rendern.

Fix: Das value-Objekt mit useMemo memoizieren: const value = useMemo(() => ({ theme, toggleTheme }), [theme, toggleTheme]); Jetzt wird ein neues Objekt nur bei echter Änderung erstellt.

Fehler: Zu viel in einem Context

Alles in einen einzigen AppContext gepackt: Flights-Daten, Filter-State, Theme, Nutzerprofil, Notifications. Jede Änderung an irgendeinem dieser Werte löst ein Re-Render bei allen Consumern aus, auch bei denen, die nur das Theme brauchen.

Fix: Contexts nach Update-Frequenz aufteilen. Theme ändert sich selten → eigener Context. Flights ändern sich häufiger → eigener Context. So re-rendern Theme-Consumer nicht, wenn sich Flights ändern.

Fehler: Fehlender Default-Wert führt zu TypeScript-Fehler

createContext<ThemeContextType>() ohne Default-Wert ist in TypeScript nicht erlaubt, da der Typ kein undefined enthält. Das führt zu einem Kompilierfehler.

Fix: Entweder ein echtes Default-Objekt angeben createContext<ThemeContextType>({ theme: 'dark', toggleTheme: () => {} }) oder den Typ explizit auf null erweitern: createContext<ThemeContextType | null>(null) und im Custom Hook prüfen.

Aufgaben

Aufgabe 1 ThemeContext mit localStorage-Persistenz

Implementiere den vollständigen ThemeContext mit Persistenz im Browser.

  • Erstelle src/context/ThemeContext.tsx mit ThemeProvider und useTheme
  • Lese beim initialen Laden den gespeicherten Wert aus localStorage.getItem('flugboard-theme')
  • Speichere jeden Wechsel mit localStorage.setItem('flugboard-theme', next)
  • Wickle App in main.tsx in den Provider ein
  • Teste: Nach einem Seitenneuladen soll das zuletzt gewählte Theme aktiv sein
Aufgabe 2 Theme in Komponenten anwenden

Wende das Theme auf die wichtigsten Komponenten an, ohne Prop Drilling.

  • AirportHeader: Hintergrund Dark #161b22 / Light #ffffff, Toggle-Button rechts
  • FlightBoard: Tabellen-Header Dark #161b22 / Light #f6f8fa
  • FlightCard: Zeilen-Hover Dark #1c2128 / Light #f6f8fa
  • App: Seitenhintergrund Dark #0d1117 / Light #ffffff
  • Verwende in jeder Komponente nur const { theme } = useTheme() – keine Theme-Props!
Aufgabe 3 LanguageContext für Statustextübersetzungen

Erstelle einen einfachen LanguageContext für Deutsch/Englisch.

  • Erstelle src/context/LanguageContext.tsx mit LanguageProvider und useLanguage
  • Der Context stellt lang: 'de' | 'en' und toggleLang: () => void bereit
  • Übersetze die Statustexte in FlightStatusBadge: on-time → „Pünktlich“ / „On Time“, delayed → „Verspätet“ / „Delayed“, cancelled → „Gestrichen“ / „Cancelled“
  • Füge einen Sprache-Umschalter im Header hinzu (DE / EN)
Bonus useReducer im ThemeContext

Ersetze den useState-Aufruf im ThemeContext durch useReducer.

  • Definiere einen ThemeAction-Typ: { type: 'TOGGLE' } | { type: 'SET'; payload: Theme }
  • Implementiere einen themeReducer, der beide Actions verarbeitet
  • Ersetze useState<Theme> durch useReducer(themeReducer, 'dark')
  • Erkläre im Code-Kommentar, wann useReducer gegenüber useState vorzuziehen ist: bei State-Logik mit mehreren Aktionen, bedingten Übergängen, oder wenn der nächste State vom vorherigen abhängt
